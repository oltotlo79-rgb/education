# 第13巻: 完全コード — 演習・解答・用語集・索引

## この巻で身に付けること

第12巻までで、RustNote を設計し（第9巻）、作り（第10巻）、確かめ（第11巻）、公開する（第12巻）までの流れを学びました。どの巻も、説明に必要な部分だけを抜き出して見せています。だから、「全部をつなげると、結局どのファイルに何が書いてあるのか」は、まだぼんやりしているかもしれません。

この巻は、教材のフォルダに入っている**完成した RustNote のソース**（`Rust/rustnote/`）を、**全部のファイルについて**、上から順に読んでいく巻です。ただ貼り付けて眺めるのではなく、ファイルごとに次の3つを確かめます。

- そのファイルは、**何を守るために**あるのか（どんな事故を防いでいるのか）
- **誰が読む**のか（cargo・rustup・rustc・ブラウザ・Docker・Fly.io など）
- 書き間違えたり消したりすると、**何が起きる**のか（実際のエラーで確かめる）

巻の最後には、全巻をまたぐ総合演習と解答、全巻の用語集、索引を置きます。

### 到達目標

この巻を終えると、次のことができるようになります。

- RustNote の 42 個のファイルについて、それぞれの役割と、読む道具（cargo・rustc・Docker など）を説明できる
- 教材と同じ版の道具と依存クレートで、RustNote を自分の PC でゼロからビルドし、テスト・整形・Clippy の確かめを通せる
- 1つのファイルを書き換えたときに、どのコマンドの、どんなエラーで気づけるかを予想し、実際に確かめられる
- 総合演習で、新しい機能を足すときの置き場所と、壊していないことの確かめ方を、自分で決められる

1. **読む:** ファイルの全文と解説を読みます。
2. **予想する:** 「この行を消したら、どのコマンドが、どんなエラーを出すか」を、先に予想します。
3. **動かす:** 教材のコマンドをそのまま実行し、結果が教材と同じか比べます。
4. **1か所だけ壊す:** 「よくあるエラーと読み方」の節のとおりに、1か所だけ書き換えて、エラーを自分の目で見ます。
5. **元に戻す:** 書き換えたファイルを元に戻し、次の3つのコマンドが全部通ることを確かめてから、次のファイルへ進みます。

```powershell
# 見た目が Rust の標準の形か（直すときは --check を外す）
cargo fmt --check
# よくある書き間違いを、警告ではなくエラーとして止める。--locked は Cargo.lock を書き換えさせない
cargo clippy --all-targets --locked -- -D warnings
# テストを全部実行する
cargo test --locked
```

### まず動かす最小コード

この単元の「コード」は、設定ファイルそのものです。まず全文を読み、次に、その設定で RustNote がビルドでき、確かめの3つのコマンドが通ることを確かめます。

#### 例1-1: Cargo.toml の全文

> **▼ このファイルがやること（先に日本語で）:** パッケージの名前と版、使う Rust の最低の版（1.99）、使うクレート（9個）とテストでだけ使うクレート（1個）を、版を `=` で1つに固定して書きます。tokio と serde には、使う機能（features）も書きます。

```toml
[package]
name = "rustnote"
version = "0.1.0"
edition = "2024"
# Topcoat 0.11 は Rust 1.99 以上が必要（動作確認は 1.99.1）
rust-version = "1.99"
description = "RustNote: Topcoat + libSQL で作るログイン付きメモアプリ（教材のサンプル）"
publish = false
default-run = "rustnote"

# 教材と同じ結果になるよう、直接使うクレートの版は `=` で固定している。
# 間接的に使われるクレートの版は Cargo.lock で固定される。
[dependencies]
# アプリの入口（main）でエラーに文脈を付けて表示する
anyhow = "=1.0.104"
# パスワードのハッシュ化（Argon2id）
argon2 = "=0.6.0"
# trait に async fn を書き、dyn（Arc<dyn NoteRepository + Send + Sync>）で使えるようにする
async-trait = "=0.1.92"
# .env ファイルを環境変数として読み込む（開発用）
dotenvy = "=0.15.7"
# Turso / libSQL のクライアント（ローカルファイルとリモートの両方）
libsql = "=0.10.0"
# フォームや JSON を構造体に変換する
serde = { version = "=1.0.229", features = ["derive"] }
# エラー型を短く書く
thiserror = "=2.0.21"
# 非同期ランタイム
tokio = { version = "=1.54.1", features = ["rt-multi-thread", "macros"] }
# Web フレームワーク
topcoat = "=0.11.0"

[dev-dependencies]
# テストごとに使い捨ての一時フォルダ（DB ファイル置き場）を作る
tempfile = "=3.27.0"
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: [package] は、このパッケージの名札

- `name = "rustnote"` は、パッケージの名前です。ライブラリを外から使うときの `rustnote::domain` の `rustnote` は、この名前です（第9巻 UNIT 04）。
- `edition = "2024"` は、Rust の書き方の世代です。同じ Rust 1.99.1 でも、edition が違うと、使える書き方や警告が少し変わります。
- `rust-version = "1.99"` は、「このパッケージをビルドするには、Rust 1.99 以上が必要」という宣言です。Topcoat 0.11 が 1.99 以上を求めているので、それに合わせています。これより古い Rust でビルドしようとすると、コンパイルを始める前に止まります（エラー1）。
- `publish = false` は、`cargo publish` で crates.io（クレートの公開場所）に**うっかり公開しない**ための印です。RustNote は教材のアプリなので、公開しません。
- `default-run = "rustnote"` は、`cargo run` で動かす実行ファイルを決めます。RustNote の実行ファイルは `src/main.rs` の1つだけなので、無くても同じように動きます。あとで `src/bin/` に道具の実行ファイルを足したときも、`cargo run` が RustNote 本体を選ぶように、先に書いてあります。

##### 解説2: "=1.54.1" は「この版だけ」

- `anyhow = "=1.0.104"` のように、版の前に `=` を付けると、**その版だけ**を使います。`=` を付けずに `"1.0.104"` と書くと、「1.0.104 以上、2.0.0 未満」の意味になり、cargo はその範囲で新しい版を選んでよくなります（例1-3で確かめます）。
- RustNote は、教材の出力と同じ結果になるように、直接使うクレートを全部 `=` で固定しています。`Cargo.toml` の上のコメント「教材と同じ結果になるよう、直接使うクレートの版は `=` で固定している」が、その理由です。
- 一方で、間接的に使われるクレートの版は、`Cargo.toml` には書きません。それを固定するのが `Cargo.lock` です（解説4）。

##### 解説3: features は、クレートの機能のスイッチ

- `tokio = { version = "=1.54.1", features = ["rt-multi-thread", "macros"] }` は、tokio の機能のうち、複数のスレッドで動くランタイム（`rt-multi-thread`）と、`#[tokio::main]` や `#[tokio::test]` を書くためのマクロ（`macros`）を使う、という意味です（第4巻 UNIT 07、第5巻 UNIT 02）。
- `serde = { version = "=1.0.229", features = ["derive"] }` の `derive` は、`#[derive(Deserialize)]` と書いてフォームの値を構造体に変える機能です。
- 機能を細かく選べるのは、使わない機能のぶんだけ、コンパイルの時間と、できあがるプログラムの大きさを減らせるからです。ただし、features には「依存のつながり全体で足し算される」という性質があります（例1-4）。

##### 解説4: [dev-dependencies] は、テストのときだけ

- `tempfile` は、テストごとに使い捨ての一時フォルダを作るクレートです。`[dev-dependencies]` に書いたクレートは、`tests/`・`examples/`・`#[cfg(test)]` のテストからだけ使えます。本番の実行ファイルには入りません（問1で確かめます）。

#### 例1-2: rust-toolchain.toml と rustfmt.toml の全文

> **▼ このファイルがやること（先に日本語で）:** `rust-toolchain.toml` は、このフォルダの中で `cargo` や `rustc` を実行したときに使う Rust の版を 1.99.1 に決め、rustfmt と clippy も一緒に入れるよう指定します。`rustfmt.toml` は、`cargo fmt` が edition 2024 の決まりで整形するよう指定します。

```toml
# このフォルダの中で cargo を実行すると、Rust 1.99.1 が使われる
# （既定のツールチェーンは変更しない）
[toolchain]
channel = "1.99.1"
components = ["rustfmt", "clippy"]
```

```toml
# rustfmt（cargo fmt / topcoat fmt --rustfmt）の設定
edition = "2024"
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: overridden by は「フォルダの設定で上書きした」

- `rustup show active-toolchain` の `(overridden by '...\rustnote\rust-toolchain.toml')` は、「PC の既定の版ではなく、このファイルで決めた版を使っています」という意味です。この PC の既定の版は 1.97.1 ですが、RustNote のフォルダでは 1.99.1 が使われています。
- だから、PC ごとに既定の版が違っても、RustNote のフォルダの中では、全員が同じ 1.99.1 でビルドします。

##### 解説2: --locked は「Cargo.lock を書き換えるな」

- `cargo build` は、`Cargo.toml` と `Cargo.lock` が食い違っていると、`Cargo.lock` を自動で書き直してからビルドします。`--locked` を付けると、書き直す必要があるときは、ビルドせずにエラーで止まります（エラー3）。
- 「レシートと違う物を、黙って買ってこない」ための指定です。RustNote の `Dockerfile`（`cargo build --release --locked`）と `ci.yml` も、`--locked` を付けています。

##### 解説3: 3つの確かめは、全部「何も言われない」が合格

- `cargo fmt --check` は、何も表示しないのが合格です。`cargo clippy ... -- -D warnings` は、警告が1つでもあればエラーにします。`Finished` で終われば合格です。`cargo test --locked` は、全部の `test result:` が `ok.` なら合格です。
- RustNote のテストは、ユニットテスト 19 件、`tests/http.rs` の 14 件、`tests/repository.rs` の 8 件、合わせて 41 件です。

```text
.env

```

```text
# RustNote の環境変数の見本。
```

- `.gitignore` の `*.db` は「名前が `.db` で終わるファイル全部」です。開発で作った DB には、自分で試しに登録したメールアドレスなどが入るので、Git に入れません。`*.db-shm`・`*.db-wal`・`*.db-journal` は、SQLite が DB の横に作る作業用のファイルです。

```text
  topcoat-view-macro@0.11.0 requires rustc 1.99
```

- **何が起きたか:** 「rustc 1.97.1 は、次のパッケージに対応していません」というエラーです。`rustnote@0.1.0 requires rustc 1.99` は、RustNote の `Cargo.toml` の `rust-version = "1.99"`、`topcoat@0.11.0 requires rustc 1.99` は、Topcoat 側の同じ宣言です。同じ名前が何回か出ていますが、読むのは、パッケージの名前と `requires rustc 1.99` の部分だけで十分です。
- このエラーは、**コンパイルを始める前に**出ます。古い Rust で途中まで長いコンパイルをして、分かりにくいエラーで止まるより、ずっと親切です。`rust-version` を書いておく理由がこれです。
- **直し方:** RustNote のフォルダでは、`+stable` を付けずに `cargo check --locked` とします。`rust-toolchain.toml` があるので 1.99.1 が使われます。1.99.1 がまだ入っていない PC では、`rustup toolchain install 1.99.1 --profile minimal --component rustfmt,clippy` で入れます（既定の版は変わりません）。

> **注意:** `cargo +1.97.1 check` のように、PC に入っていない版の名前を指定すると、この PC の rustup は、その版を**自動でダウンロードして入れました**（`warn: the missing active toolchain ... has been auto-installed` と表示されます）。版を試すときは、`rustup toolchain list` で入っている版を確かめてから指定しましょう。入れてしまった版は、`rustup toolchain uninstall 版の名前` で消せます。

#### エラー2: 機能の名前を打ち間違えた

`Cargo.toml` の tokio の `"macros"` を、`"macro"`（`s` が無い）と打ち間違えた場合です。

```toml
tokio = { version = "=1.54.1", features = ["rt-multi-thread", "macro"] }
```

```powershell
cargo build --locked
```

```text
error: failed to select a version for `tokio`.
    ... required by package `rustnote v0.1.0 (...\rustnote)`
versions that meet the requirements `=1.54.1` (locked to 1.54.1) are: 1.54.1

package `rustnote` depends on `tokio` with feature `macro` but `tokio` does not have that feature.
help: there is a feature `macros` with a similar name


failed to select a version for `tokio` which could resolve this conflict
```

- **何が起きたか:** 「tokio の版を選べませんでした」というエラーです。その下の `package rustnote depends on tokio with feature macro but tokio does not have that feature.`（RustNote は tokio の `macro` という機能を求めていますが、tokio にその機能はありません）が本当の理由です。
- `versions that meet the requirements =1.54.1 (locked to 1.54.1) are: 1.54.1` は、「条件に合う版は 1.54.1 だけで、その版には `macro` という機能が無いので、選べる版がもう無い」という意味です。
- **直し方:** `help: there is a feature macros with a similar name`（似た名前の `macros` という機能があります）のとおり、`"macros"` に直します。機能の名前は、クレートの docs.rs のページの「Feature flags」で確かめられます。

#### エラー3: --locked なのに、Cargo.lock を書き換える必要がある

`Cargo.toml` の dotenvy の版を、`"=0.15.7"` から `"=0.15.6"` に変えて、`--locked` でビルドした場合です。

```powershell
cargo build --locked
```

```text
    Updating crates.io index
error: cannot update the lock file ...\rustnote\Cargo.lock because --locked was passed to prevent this
help: to generate the lock file without accessing the network, remove the --locked flag and use --offline instead.
```

- **何が起きたか:** 「`--locked` が指定されたので、Cargo.lock を書き換えられません」というエラーです。`Cargo.toml` は 0.15.6 を求めているのに、`Cargo.lock` には 0.15.7 が書いてあるので、ビルドするには `Cargo.lock` を書き直す必要がありました。
- **これはエラーで正しい:** CI や Docker のビルドで、`Cargo.lock` と違う版が黙って使われるのを止めるために、わざと `--locked` を付けています。
- **直し方:** 版を本当に変えたいときは、`--locked` を付けずに `cargo build`（または `cargo update -p dotenvy`）を実行して `Cargo.lock` を更新し、`Cargo.toml` と `Cargo.lock` を**一緒に**コミットします。この練習では、`Cargo.toml` を `"=0.15.7"` に戻します。
- `help:` の `--offline`（ネットにつながずに作る）の案内は、ネットを使わずに `Cargo.lock` を作り直したいときの方法です。今回は版を戻せばよいので、使いません。

#### エラー4: Cargo.lock の指紋（checksum）が違う

`Cargo.lock` の dotenvy の `checksum` の、先頭の1文字だけを書き換えた場合です。

```toml
[[package]]
name = "dotenvy"
version = "0.15.7"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "0aaf95b3e5c8f23aa320147307562d361db0ae0d51242340f558153b4eb2439b"
```

```powershell
cargo build --locked
```

```text
error: checksum for `dotenvy v0.15.7` changed between lock files

this could be indicative of a few possible errors:

    * the lock file is corrupt
    * a replacement source in use (e.g., a mirror) returned a different checksum
    * the source itself may be corrupt in one way or another

unable to verify that `dotenvy v0.15.7` is the same as when the lockfile was generated
```

- **何が起きたか:** 「dotenvy 0.15.7 の checksum が、ロックファイルの間で変わりました」というエラーです。`checksum` は、crates.io から取ってきたクレートの中身から計算した**指紋**（SHA-256）です。本物の指紋は `1aaf95b3…` で始まるのに、`Cargo.lock` には `0aaf95b3…` と書いてあったので、cargo は「同じ物か確かめられない」と止まりました。
- その下の3つの点は、考えられる原因です。ロックファイルが壊れている、ミラー（代わりの取得先）が違う中身を返した、取得先そのものが壊れている、のどれかです。
- **これはエラーで正しい:** 途中で中身をすり替えられたクレートを、気づかずにビルドしてしまう事故を防いでいます。`Cargo.lock` を Git で共有すると、この指紋も全員で共有されます。
- **直し方:** `Cargo.lock` は手で書き換えるファイルではありません（先頭に `It is not intended for manual editing.` と書いてあります）。教材のフォルダから `Cargo.lock` をコピーし直します。

#### エラー5: 誰も macros を有効にしていない（E0433・E0752）

例1-6で、RustNote では `"macros"` を消してもビルドが通ることを見ました。では、ほかのクレートが助けてくれない場合はどうなるでしょう。tokio だけを使う小さなプロジェクト（`feat_demo`）で試します。

```toml
[package]
name = "feat_demo"
version = "0.1.0"
edition = "2024"

[dependencies]
# RustNote と同じ版の tokio を、macros なしで使う
tokio = { version = "=1.54.1", features = ["rt-multi-thread"] }
```

```rust
// #[tokio::main] は、tokio の macros の機能が有効なときだけ使える
#[tokio::main]
async fn main() {
    println!("tokio のランタイムの中で動いています");
}
```

```powershell
cargo build
```

```text
   Compiling tokio v1.54.1
   Compiling feat_demo v0.1.0 (...\feat_demo)
error[E0433]: cannot find `main` in `tokio`

  |
2 | #[tokio::main]
  |          ^^^^ could not find `main` in `tokio`

error[E0752]: `main` function is not allowed to be `async`
```

- **何が起きたか:** 1つ目の `error[E0433]: cannot find main in tokio` は、「tokio の中に `main` が見つかりません」です。`#[tokio::main]` は、`macros` の機能を有効にしたときだけ tokio の中に現れるので、機能が無いと「無い物を使った」エラーになります。

### RustNote ではここで使う

この単元のファイルは、RustNote のほかのファイルから、次のように使われています。

| 使う場所 | 書いてあること | つながるファイル |
|---|---|---|
| `Dockerfile` | `FROM rust:1.99.1-bookworm AS builder` | `rust-toolchain.toml` と同じ 1.99.1 |
| `Dockerfile` | `RUN cargo install topcoat-cli --version 0.11.0 --locked` | `Cargo.toml` の topcoat と同じ 0.11.0 |
| `Dockerfile` | `RUN cargo build --release --locked` | `Cargo.lock`（`--locked`） |
| `ci.yml` | `toolchain: 1.99.1` と `components: rustfmt, clippy` | `rust-toolchain.toml` |
| `ci.yml` | `cargo clippy --all-targets --locked -- -D warnings`・`cargo test --locked` | `Cargo.lock` |
| `.dockerignore` | `target/`・`*.db`・`.env` を送らない | `.gitignore` と同じ考え方 |
| `src/main.rs` | `dotenvy::dotenv().ok();` | `.env.example` をコピーした `.env` |

- Rust の版（1.99.1）は、`rust-toolchain.toml`・`Dockerfile`・`ci.yml` の3か所に書いてあります。版を上げるときは、この3か所を**一緒に**変えます。1か所だけ変えると、「自分の PC では通るのに、CI では通らない」という食い違いが起きます。
- topcoat の版（0.11.0）も、`Cargo.toml` のクレートと、`Dockerfile` の CLI の2か所です。クレートと CLI は同じ Topcoat の一部なので、版を上げるときは両方を一緒に上げます。

### 練習問題

**問1:** `tempfile` は `[dev-dependencies]` に書いてあります。もし `src/lib.rs` の中で `tempfile::tempdir()` を使う関数を書いたら、どうなるでしょうか。予想してから、練習用のコピーで確かめてください（確かめたら元に戻します）。また、なぜ `tempfile` を `[dependencies]` ではなく `[dev-dependencies]` に書くのかを答えてください。

**問2:** ARM64 版の Windows で RustNote をビルドするには、LLVM（clang）が必要でした（第9巻の巻頭）。これは、暗号のクレート `ring` を C のコンパイラでビルドするためです。では、RustNote の `Cargo.toml` には `ring` が無いのに、なぜ `ring` がビルドされるのでしょうか。`cargo tree` で、`ring` を使っているクレートをたどってください。

**問3:** 練習用のコピーで `git init` し、`.env.example` を `.env` にコピーし、`rustnote.db` という名前の空でないファイルを作ります。そのうえで、次の2つを確かめてください。

1. `git check-ignore -v` で、`.env`・`rustnote.db`・`rustnote.db-wal`・`target/debug/rustnote.exe`・`.env.example`・`Cargo.lock` のうち、どれが Git から外されるか。外されるものは、`.gitignore` の何行目の決まりによるか。
2. `git status --short` に、`.env` と `rustnote.db` が出てこないこと。

### 解答と解説

**問1の解答:**

予想: コンパイルエラーになる。`[dev-dependencies]` のクレートは、ライブラリの本体（`src/`）からは見えないからです。`src/lib.rs` の最後に、次の関数を足して確かめます。

```rust
/// 試し: dev-dependencies のクレートを src/ で使う
pub fn scratch_dir() -> tempfile::TempDir {
    tempfile::tempdir().expect("一時フォルダを作れません")
}
```

```powershell
cargo build --locked
```

```text

error[E0433]: cannot find module or crate `tempfile` in this scope
  --> src\lib.rs:30:5
   |
30 |     tempfile::tempdir().expect("一時フォルダを作れません")
   |     ^^^^^^^^ use of unresolved module or unlinked crate `tempfile`
   |
   = help: if you wanted to use a crate named `tempfile`, use `cargo add tempfile` to add it to your `Cargo.toml`

error[E0433]: cannot find module or crate `tempfile` in this scope
  --> src\lib.rs:29:25
   |

   |                         ^^^^^^^^ use of unresolved module or unlinked crate `tempfile`
   |
   = help: if you wanted to use a crate named `tempfile`, use `cargo add tempfile` to add it to your `Cargo.toml`

For more information about this error, try `rustc --explain E0433`.
error: could not compile `rustnote` (lib) due to 2 previous errors
```

- `cannot find module or crate tempfile in this scope`（この場所では `tempfile` というモジュールもクレートも見つかりません）と、使った2か所でエラーになりました。`help:` は「`cargo add tempfile` で `Cargo.toml` に足してください」と案内していますが、テストのための道具を本体の依存にするのは、正しい直し方ではありません。
- `[dev-dependencies]` に書くのは、本番の実行ファイルに**入れる必要が無い**からです。入れないぶん、本番のビルドが速くなり、できあがる実行ファイルも小さくなり、本番で動くコードが使うクレートの数（気をつけて見ておくべき範囲）も減ります。
- 確かめたら、足した関数を消して、`src/lib.rs` を元に戻します。

**問2の解答:**

```powershell

```

```text
ring v0.17.14
├── rustls v0.22.4
│   ├── hyper-rustls v0.25.0
│   │   └── libsql v0.10.0
│   │       └── rustnote v0.1.0 (...\rustnote)
│   └── tokio-rustls v0.25.0
│       └── hyper-rustls v0.25.0 (*)
└── rustls-webpki v0.102.8
    └── rustls v0.22.4 (*)
```

- 下から読むと、`rustnote → libsql → hyper-rustls → rustls → ring` とつながっています。libsql が Turso（ネットの向こうの DB）と暗号化して通信するために rustls（TLS という暗号化の仕組みを Rust で書いたクレート）を使い、rustls と、証明書を確かめる rustls-webpki が、暗号の計算に ring を使っているのです。
- `(*)` は、「この先は、上ですでに表示した」という印です。同じつながりを何度も書かないように省いています。
- RustNote の `Cargo.toml` に書いていないクレートでも、ビルドに必要な道具（ここでは clang）を求めることがあります。ビルドが止まったら、エラーに出てきたクレートの名前で `cargo tree -i` を調べると、「誰のために必要なのか」が分かります。

1. 外されるのは `.env`（11 行目の `.env`）、`rustnote.db`（5 行目の `*.db`）、`rustnote.db-wal`（7 行目の `*.db-wal`）、`target/debug/rustnote.exe`（2 行目の `/target/`）の4つです。`-v`（verbose）を付けると、「どのファイルの何行目の、どの決まりに当たったか」が、`.gitignore:11:.env` の形で表示されます。`.env.example` と `Cargo.lock` は表示されません。外されない（Git で共有する）からです。

### まとめ

- `Cargo.toml` は人が書く材料表、`Cargo.lock` は cargo が書くレシート（全クレートの版と指紋）。RustNote は直接使うクレートを `=` で固定し、`Cargo.lock` を Git で共有して、`--locked` で書き換えを止める。
- Rust の版は、`rust-version`（最低の版）と `rust-toolchain.toml`（このフォルダで使う版）で決め、`Dockerfile` と `ci.yml` にも同じ版を書く。features は依存のつながり全体で足し算されるので、自分が使う機能は自分の `Cargo.toml` に書く。
- 秘密の値と DB と成果物は `.gitignore` で共有から外し、環境変数は `.env.example` という見本だけを共有する。

## UNIT 02: 表を作る SQL と DB の入口

### この単元のゴール

- `migrations/` の3つの SQL ファイルが、どの表・索引・制約を作るかを説明できる
- `src/db.rs` の `migrate` が、まだ適用していない版だけを、1つずつトランザクションの中で適用し、`schema_migrations` に記録する流れを説明できる
- `Db::open_local` と `Db::connect` が入れている設定（WAL・外部キー・待ち時間）を、実際の値で確かめられる
- マイグレーションが途中で失敗したときに何が残るか、適用済みの SQL ファイルを書き換えたら何が起きるかを、実験で説明できる

### たとえ話でつかむ

ある建物に、何年もかけて部屋を増やしていく場面を考えます。

- 工事には**番号**が付いています。「1番: 1階を建てる」「2番: 2階を足す」「3番: 倉庫を足す」。工事は、必ず番号の順に、1回ずつ行います。
- 建物には**工事の記録簿**があり、終わった工事の番号が書いてあります。新しい担当者が来ても、記録簿を見れば「3番まで終わっている。次は4番から」と分かります。
- 工事の途中で問題が起きたら、その工事で作りかけた物は**全部取り壊して**、工事の前の状態に戻します。半分だけできた部屋を残すと、次の工事ができなくなるからです。
- 終わった工事の**図面を書き換えても、建物は変わりません**。2番の図面に「窓を1つ増やす」と書き足しても、すでに建った2階の窓は増えません。窓を増やしたいなら、新しく「4番: 2階に窓を足す」という工事を足します。

RustNote の DB も、同じやり方で作ります。

| 建物の工事 | RustNote |
|---|---|
| 番号の付いた工事 | **マイグレーション**（`migrations/0001_users.sql` など、番号順の SQL ファイル） |
| 工事の記録簿 | `schema_migrations` 表（適用済みの版の名前と時刻） |
| 番号の順に、まだの工事だけをする | `db::migrate` が、未適用の版だけを古い順に適用する |
| 途中で失敗したら、作りかけを取り壊す | 1つの版を**トランザクション**の中で適用し、失敗したら `rollback` |
| 終わった工事の図面を書き換えても変わらない | 適用済みの SQL ファイルを書き換えても、今ある DB には反映されない（エラー2） |

> **用語:** マイグレーション（migration：DB の表の作り（スキーマ）を変える手順を、番号順のファイルに分けて書いたもの。第7巻 UNIT 06）

<!-- -->

> **用語:** トランザクション（transaction：いくつかの変更を「全部やる」か「全部やめる」かの1まとまりにする仕組み。第7巻 UNIT 05）

- 大事なのは、④の中で、**SQL の実行と記録簿への書き込みを、同じトランザクションに入れている**ことです。もし SQL だけが成功して、記録が残らなかったら、次の起動で同じ SQL がもう一度流れ、「表がもうあります」のエラーになります。反対に、記録だけが残って SQL が失敗していたら、表が無いのに「適用済み」になります。同じトランザクションなら、両方が成功するか、両方とも無かったことになるかの、どちらかです。

#### 例2-1: マイグレーションの SQL とコードの全文

> **▼ このファイルがやること（先に日本語で）:** `0001_users.sql` はユーザーの表、`0002_notes.sql` はノートの表と一覧を速くする索引、`0003_sessions.sql` はログイン中のセッションの表と2つの索引を作ります。どれも、決まり（`UNIQUE`・`CHECK`・外部キー）を表に書き込んでいます（第9巻 UNIT 03）。

```sql
-- 0001: ユーザーのテーブル
-- email は UNIQUE（同じメールアドレスで二重に登録できない）。
-- password_hash には Argon2id の PHC 文字列（$argon2id$v=19$...）を入れる。生のパスワードは保存しない。
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

```sql
-- 0002: ノートのテーブル
-- title は 1〜80 文字（length() は文字数を数える。Rust 側の chars().count() と同じ）。
-- done は 0（未完了）か 1（完了）。
-- version は楽観的ロック用の番号。更新のたびに 1 増える。
-- 日時は UTC の 'YYYY-MM-DD HH:MM:SS' 形式の文字列（datetime('now') の形）。
CREATE TABLE notes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 80),
    body TEXT NOT NULL DEFAULT '',
    done INTEGER NOT NULL DEFAULT 0 CHECK (done IN (0, 1)),
    version INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 「自分のノートを新しい順に」を速くするための索引
CREATE INDEX idx_notes_user_updated ON notes (user_id, updated_at DESC, id DESC);
```

```sql
-- 0003: ログイン中のセッションのテーブル
-- token_hash は Topcoat が発行したトークンの SHA-256（32 バイト）。生のトークンは保存しない。
-- expires_at は有効期限。1970-01-01 からの秒数（UNIX 時刻）で持ち、比較しやすくする。
CREATE TABLE sessions (
    token_hash BLOB PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at INTEGER NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_sessions_user ON sessions (user_id);
CREATE INDEX idx_sessions_expires ON sessions (expires_at);
```

> **▼ このファイルがやること（先に日本語で）:** `src/db.rs` は、DB への入口の `Db` 型と、マイグレーションの `migrate` 関数を持ちます。`Db` は、設定に合わせてローカルのファイルか Turso を開き、接続のたびに必要な設定を入れます。`migrate` は、SQL ファイルを `include_str!` で実行ファイルに埋め込み、まだ適用していない版だけを適用します。

```rust
//! DB（Turso / libSQL）への接続と、マイグレーション（テーブルの作成・変更）。
//!
//! - 開発ではローカルファイル（例: rustnote.db）を使う
//! - 本番では Turso の URL（libsql://...）と認証トークンを環境変数で渡す
//!
//! 接続（Connection）は処理のたびに `Db::connect` で作る。
//! ローカルファイルなら開くだけ、リモートなら HTTP の準備だけなので軽い。

use std::path::Path;
use std::sync::Arc;

use libsql::{Builder, Connection, Database, Transaction};
use thiserror::Error;

use crate::config::Config;

/// DB への入口。中身は Arc なので、clone しても同じ DB を指す（安く複製できる）
#[derive(Clone)]
pub struct Db {
    database: Arc<Database>,
    is_local: bool,
}

impl Db {
    /// 設定に従って、ローカルファイルかリモート（Turso）の DB を開く
    pub async fn open(config: &Config) -> Result<Db, libsql::Error> {
        if config.is_remote() {
            // 秘密のトークンは、接続するこの場所でだけ取り出す
            let token = config
                .database_auth_token
                .as_ref()
                .map(|secret| secret.expose().to_string())
                .unwrap_or_default();
            let database = Builder::new_remote(config.database_url.clone(), token)
                .build()
                .await?;
            Ok(Db {
                database: Arc::new(database),
                is_local: false,
            })
        } else {
            Db::open_local(&config.database_url).await
        }
    }

    /// ローカルファイルの DB を開く（無ければ作られる）
    pub async fn open_local(path: impl AsRef<Path>) -> Result<Db, libsql::Error> {
        let database = Builder::new_local(path).build().await?;
        let db = Db {
            database: Arc::new(database),
            is_local: true,
        };
        // WAL モード: 読み込みと書き込みが同時に来ても待たされにくくなる（ファイルに記録される）
        let conn = db.connect().await?;
        conn.execute_batch("PRAGMA journal_mode = WAL;").await?;
        Ok(db)
    }

    /// 新しい接続を作る
    pub async fn connect(&self) -> Result<Connection, libsql::Error> {
        let conn = self.database.connect()?;
        if self.is_local {
            // SQLite は接続ごとに設定が必要:
            // foreign_keys … REFERENCES（外部キー）を守らせる
            // busy_timeout … ほかの接続が書き込み中なら最大 5 秒待つ
            conn.execute_batch("PRAGMA foreign_keys = ON; PRAGMA busy_timeout = 5000;")
                .await?;
        }
        Ok(conn)
    }

    /// DB に問い合わせができるか確かめる（GET /health で使う）
    pub async fn ping(&self) -> Result<(), libsql::Error> {
        let conn = self.connect().await?;
        let mut rows = conn.query("SELECT 1", ()).await?;
        rows.next().await?;
        Ok(())
    }
}

// ---------------------------------------------------------------------------
// マイグレーション
// ---------------------------------------------------------------------------

/// 1つのマイグレーション（版の名前と SQL）
pub struct Migration {
    pub version: &'static str,
    pub sql: &'static str,
}

/// アプリが持つマイグレーションの一覧（古い順）。
/// SQL ファイルは include_str! でコンパイル時に実行ファイルへ埋め込む。
pub const MIGRATIONS: &[Migration] = &[
    Migration {
        version: "0001_users",
        sql: include_str!("../migrations/0001_users.sql"),
    },
    Migration {
        version: "0002_notes",
        sql: include_str!("../migrations/0002_notes.sql"),
    },
    Migration {
        version: "0003_sessions",
        sql: include_str!("../migrations/0003_sessions.sql"),
    },
];

#[derive(Debug, Error)]
pub enum MigrateError {
    #[error("schema_migrations を準備できません")]
    Prepare(#[source] libsql::Error),
    #[error("マイグレーション {version} に失敗しました")]
    Apply {
        version: &'static str,
        #[source]
        source: libsql::Error,
    },
}

/// まだ適用していないマイグレーションだけを、1つずつトランザクションの中で適用する。
/// 戻り値は、今回新しく適用した版の名前の一覧。
pub async fn migrate(db: &Db) -> Result<Vec<&'static str>, MigrateError> {
    let conn = db.connect().await.map_err(MigrateError::Prepare)?;

    // 適用済みの版を記録する表（無ければ作る）
    conn.execute(
        "CREATE TABLE IF NOT EXISTS schema_migrations (
            version TEXT PRIMARY KEY,
            applied_at TEXT NOT NULL DEFAULT (datetime('now'))
        )",
        (),
    )
    .await
    .map_err(MigrateError::Prepare)?;

    let applied = applied_versions(&conn)
        .await
        .map_err(MigrateError::Prepare)?;

    let mut newly_applied = Vec::new();
    for migration in MIGRATIONS {
        if applied.iter().any(|v| v == migration.version) {
            continue;
        }
        let apply_error = |source| MigrateError::Apply {
            version: migration.version,
            source,
        };
        let tx = conn.transaction().await.map_err(apply_error)?;
        match apply(&tx, migration).await {
            // 全部成功したときだけ確定する
            Ok(()) => tx.commit().await.map_err(apply_error)?,
            // 途中で失敗したら、その版の変更をすべて取り消す
            Err(source) => {
                tx.rollback().await.map_err(apply_error)?;
                return Err(apply_error(source));
            }
        }
        newly_applied.push(migration.version);
    }
    Ok(newly_applied)
}

/// schema_migrations に記録された版の名前を読む
async fn applied_versions(conn: &Connection) -> Result<Vec<String>, libsql::Error> {
    let mut rows = conn
        .query("SELECT version FROM schema_migrations ORDER BY version", ())
        .await?;
    let mut versions = Vec::new();
    while let Some(row) = rows.next().await? {
        versions.push(row.get::<String>(0)?);
    }
    Ok(versions)
}

/// 1つのマイグレーションの SQL を実行し、適用済みとして記録する
async fn apply(tx: &Transaction, migration: &Migration) -> Result<(), libsql::Error> {
    tx.execute_batch(migration.sql).await?;
    tx.execute(
        "INSERT INTO schema_migrations (version) VALUES (?1)",
        [migration.version],
    )
    .await?;
    Ok(())
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: SQL のファイルは、実行ファイルの中に入る

- `MIGRATIONS` の `include_str!("../migrations/0001_users.sql")` は、コンパイルのときに、SQL ファイルの中身を文字列として実行ファイルに埋め込みます。公開した実行ファイルの隣に `migrations/` フォルダが無くても、マイグレーションを流せます（第9巻 UNIT 03 のエラー2）。
- `MIGRATIONS` の並び順が、適用の順番です。ファイル名の番号（0001・0002・0003）は、人が見て分かるように付けているもので、順番を決めているのはこの配列です。

##### 解説2: Db は、Arc で包んだ入口

- `Db` は、libsql の `Database` を `Arc` で包んでいます。`clone()` しても、中の DB は1つのままで、参照の数が増えるだけです（第3巻）。RustNote の `AppState` は、この `Db` を、3つのリポジトリに1つずつ `clone()` して渡しています。
- 接続（`Connection`）は、処理のたびに `connect()` で作ります。先頭のコメントのとおり、ローカルのファイルなら開くだけ、Turso なら HTTP の準備だけなので軽い、という判断です。

##### 解説3: 失敗の理由を2種類に分ける

- `MigrateError` は、「記録簿を準備できなかった」（`Prepare`）と、「この版の適用に失敗した」（`Apply`、失敗した版の名前つき）の2種類です。`#[source]` を付けたので、もとの libsql のエラーも、原因としてつながったまま残ります（第4巻 UNIT 05）。エラー1で、実際の表示を見ます。

#### 例2-2: 同じ DB に、migrate を2回かける

> **▼ このコードがやること（先に日本語で）:** 引数で渡した場所に DB ファイルを開き（無ければ作られる）、`db::migrate` を2回続けて呼んで、それぞれが返した「今回適用した版」を表示します。そのあと、記録簿の中身、できた表と索引、`notes` の列の名前を表示します。

```rust
//! RustNote の db::migrate を同じ DB に2回かけて、何が作られ、2回目に何が起きるかを確かめる。
//! DB ファイルの場所を引数で渡す（無ければ作られる）。
//! 実行: cargo run -q --example u02_migrate -- try.db

use libsql::Connection;
use rustnote::db::{self, Db};

/// 1列目の文字列を、行の数だけ集める
async fn strings(conn: &Connection, sql: &str) -> anyhow::Result<Vec<String>> {
    let mut rows = conn.query(sql, ()).await?;
    let mut values = Vec::new();
    while let Some(row) = rows.next().await? {
        values.push(row.get::<String>(0)?);
    }
    Ok(values)
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let path = std::env::args()
        .nth(1)
        .unwrap_or_else(|| "try.db".to_string());
    let db = Db::open_local(&path).await?;

    println!("1回目の migrate: {:?}", db::migrate(&db).await?);
    println!("2回目の migrate: {:?}", db::migrate(&db).await?);

    let conn = db.connect().await?;
    println!(
        "適用済みの版: {:?}",
        strings(
            &conn,
            "SELECT version FROM schema_migrations ORDER BY version"
        )
        .await?
    );
    println!(
        "表: {:?}",
        strings(
            &conn,
            "SELECT name FROM sqlite_master WHERE type = 'table' ORDER BY name"
        )
        .await?
    );
    println!(
        "索引: {:?}",
        strings(
            &conn,
            "SELECT name FROM sqlite_master WHERE type = 'index' AND name LIKE 'idx_%' ORDER BY name"
        )
        .await?
    );
    println!(
        "notes の列: {:?}",
        strings(&conn, "SELECT name FROM pragma_table_info('notes')").await?
    );
    Ok(())
}
```

- 1回目は3つの版がすべて適用され、2回目は `[]`（何も適用しない）でした。RustNote は起動のたびに `migrate` を呼びますが、2回目からは何もしません。何回呼んでも同じ結果になる（**冪等**な）作りです。
- 表には、マイグレーションの4つのほかに `sqlite_sequence` があります。`AUTOINCREMENT` を付けた列の「次に使う番号」を、SQLite が自動で記録する表です。自分で作る必要も、触る必要もありません。

> **用語:** 冪等（べきとう：同じ操作を何回くり返しても、1回したときと同じ結果になること）

### もう一歩: 実務に近い形

#### 例2-3: 接続ごとの設定を、libsql の素の接続と比べる

> **▼ このコードがやること（先に日本語で）:** 一時フォルダの DB を `Db::open_local` で開き、`Db::connect` の接続で、3つの設定（`journal_mode`・`foreign_keys`・`busy_timeout`）の値を表示します。同じファイルを、RustNote の `Db` を通さずに、libsql の素の接続でも開いて比べます。最後に、フォルダの中のファイルを表示します。

```rust
//! Db::connect が接続ごとに入れている設定（PRAGMA）を、libsql の素の接続と比べる。
//! 実行: cargo run -q --example u02_pragmas

use libsql::{Builder, Connection, Value};
use rustnote::db::Db;

/// PRAGMA の値を1つ読む（数のときも文字のときもあるので、両方を文字にする）
async fn pragma(conn: &Connection, name: &str) -> anyhow::Result<String> {
    let mut rows = conn.query(&format!("PRAGMA {name}"), ()).await?;
    let row = rows.next().await?.expect("PRAGMA は1行を返すはずです");
    Ok(match row.get_value(0)? {
        Value::Integer(number) => number.to_string(),
        Value::Text(text) => text,
        other => format!("{other:?}"),
    })
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let dir = tempfile::tempdir()?;
    let path = dir.path().join("u02.db");

    // RustNote の Db を通した接続
    let db = Db::open_local(&path).await?;
    let conn = db.connect().await?;
    println!("[Db::connect の接続]");
    for name in ["journal_mode", "foreign_keys", "busy_timeout"] {
        println!("    {name} = {}", pragma(&conn, name).await?);
    }

    // libsql の素の接続（RustNote の設定を通さない）
    let raw = Builder::new_local(&path).build().await?.connect()?;
    println!("[libsql の素の接続]");
    for name in ["journal_mode", "foreign_keys", "busy_timeout"] {
        println!("    {name} = {}", pragma(&raw, name).await?);
    }

    // WAL モードにすると、DB の横に作業用のファイルができる
    let mut files: Vec<String> = std::fs::read_dir(dir.path())?
        .filter_map(|entry| entry.ok())
        .map(|entry| entry.file_name().to_string_lossy().to_string())
        .collect();
    files.sort();
    println!("フォルダの中のファイル: {files:?}");
    Ok(())
}
```

- **WAL（journal_mode = wal）:** ファイルに記録される設定です。`Db::open_local` で1回入れたので、素の接続でも `wal` のままでした。WAL にすると、DB のファイル（`u02.db`）の横に、`u02.db-wal`（まだ本体に書き込んでいない変更）と `u02.db-shm`（その目次）ができます。RustNote の `.gitignore` が `*.db-wal`・`*.db-shm` を外しているのは、このためです（UNIT 01）。
- **busy_timeout:** 接続ごとの設定です。`Db::connect` の接続は 5000（ミリ秒）、素の接続は 0 でした。0 のままだと、ほかの接続が書き込み中のとき、待たずにすぐ「DB がふさがっている」エラーになります。RustNote は、最大 5 秒は待つようにしています。
- **foreign_keys:** SQLite では、外部キーの確かめは「接続ごとに ON にしないと働かない」決まりです。ところが、この libsql 0.10 では、素の接続でも最初から `1`（ON）でした。RustNote の `Db::connect` は、それでも毎回 `PRAGMA foreign_keys = ON` を入れています。libsql の既定が変わっても外部キーが働くように、そして、コードを読んだ人が「外部キーを守らせている」と分かるように書いてある、と読めます。

### RustNote ではここで使う

起動の入口の `src/main.rs` は、DB を開いて、マイグレーションをかけてから、待ち受けを始めます（抜き出しています）。

**問1の解答:**


`src/db.rs` の `MIGRATIONS` の最後に、1つ足します。

```rust
    }

    // フォルダを作ってから開くと、ファイルは自動で作られる
    std::fs::create_dir(dir.path().join("data")).expect("フォルダを作れません");
    match Db::open_local(&path).await {
        Ok(_) => println!(
            "フォルダを作ってから: 開けました（ファイルがある: {}）",
            path.exists()
        ),
        Err(error) => println!("フォルダを作ってから: 開けません: {error}"),
    }
}
```

- フォルダ（`data`）が無いと、`Unable to open connection to local database ...\rustnote.db: 14` で開けませんでした。14 は SQLite のエラーの番号で、「ファイルを開けない」（`SQLITE_CANTOPEN`）という意味です。SQLite は、ファイルは自動で作りますが、**フォルダは作りません**。
- フォルダを作ってから開くと、ファイルが自動で作られました。
- RustNote では、このエラーは `main.rs` の `with_context` で「DB（data/rustnote.db）を開けませんでした」と包まれて表示され、起動が止まります。公開するときの `Dockerfile` が、`mkdir -p /data` でフォルダを先に作っているのは、このためです（UNIT 10（準備中））。

### まとめ

- RustNote の表は、`migrations/` の番号順の SQL ファイルが作る。`db::migrate` は、未適用の版だけを古い順に、1つずつトランザクションの中で適用し、SQL の実行と記録簿への書き込みを同じトランザクションに入れる。失敗した版の作りかけは、`rollback` で残らない。
- `Db::open_local` は WAL（ファイルに記録される）を1回入れ、`Db::connect` は外部キーと待ち時間（接続ごと）を毎回入れる。libsql 0.10 は素の接続でも外部キーが ON だったが、RustNote は明示している。
- 適用済みの SQL ファイルは書き換えない。古い DB には反映されず、新しい DB とだけ形が変わってしまう。変更は、新しい版として足す。

#### 例3-1: src/config.rs の全文

> **▼ このファイルがやること（先に日本語で）:** 環境変数の `DATABASE_URL` と `DATABASE_AUTH_TOKEN` を読んで、`Config` を作ります。`DATABASE_URL` が無ければ `rustnote.db`、Turso の URL（`libsql://`・`https://`・`wss://`）なのにトークンが無ければ、エラーにします。トークンは、読んだらすぐ `Secret` 型に包み、`{:?}` で表示しても中身が出ないようにします。待ち受けのアドレスを、起動の知らせのために組み立てる関数 `listen_address` もあります。

```rust
//! 設定（Config）: 環境変数から読み込む。
//!
//! | 環境変数 | 意味 | 既定値 |
//! |---|---|---|
//! | `DATABASE_URL` | ローカルの DB ファイルのパス、または Turso の URL（`libsql://...`） | `rustnote.db` |
//! | `DATABASE_AUTH_TOKEN` | Turso の認証トークン（リモートのときだけ必要） | なし |
//! | `HOST` / `PORT` | 待ち受けるアドレス。`topcoat::start` が直接読む | `127.0.0.1` / `3000` |
//!
//! トークンのような秘密の値は `Secret` 型に包む。`{:?}` で設定全体をログに出しても、
//! 中身は `Secret(********)` としか表示されない。

use std::env;
use std::fmt;

use thiserror::Error;

/// DATABASE_URL が無いときに使うローカルの DB ファイル
pub const DEFAULT_DATABASE_URL: &str = "rustnote.db";

// ---------------------------------------------------------------------------
// 秘密の値を包む型
// ---------------------------------------------------------------------------

/// 秘密の値（Turso のトークンなど）。
/// Debug は derive せずに手で書き、中身の代わりに `********` を表示する。
/// Display は実装しないので、`{}` で表示しようとするとコンパイルエラーになる。
#[derive(Clone, PartialEq, Eq)]
pub struct Secret(String);

impl Secret {
    pub fn new(value: String) -> Secret {
        Secret(value)
    }

    /// 中身が本当に必要な場所（DB に接続するとき）だけで呼ぶ。
    /// わざと目立つ名前にして、秘密を使っている場所をすぐ見つけられるようにしている
    pub fn expose(&self) -> &str {
        &self.0
    }
}

// {:?} で表示されても中身を出さない
impl fmt::Debug for Secret {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str("Secret(********)")
    }
}

// ---------------------------------------------------------------------------
// 設定
// ---------------------------------------------------------------------------

/// アプリの設定
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Config {
    /// ローカルファイルのパス（例: `rustnote.db`）か、Turso の URL（例: `libsql://...`）
    pub database_url: String,
    /// Turso の認証トークン（秘密）。ローカルファイルのときは `None`
    pub database_auth_token: Option<Secret>,
}

/// 設定を読めなかった理由
#[derive(Debug, Error, PartialEq, Eq)]
pub enum ConfigError {
    #[error("環境変数 {0} の値が UTF-8 の文字列として読めません")]
    NotUnicode(&'static str),
    #[error("DATABASE_URL が Turso（{0}）なのに DATABASE_AUTH_TOKEN が設定されていません")]
    MissingAuthToken(String),
}

impl Config {
    /// 環境変数から設定を作る
    pub fn from_env() -> Result<Config, ConfigError> {
        let database_url =
            read_var("DATABASE_URL")?.unwrap_or_else(|| DEFAULT_DATABASE_URL.to_string());
        // 空文字の DATABASE_AUTH_TOKEN は「設定されていない」と同じに扱う。
        // 読んだらすぐ Secret に包み、String のまま持ち歩かない
        let database_auth_token = read_var("DATABASE_AUTH_TOKEN")?
            .filter(|t| !t.is_empty())
            .map(Secret::new);
        Config::new(database_url, database_auth_token)
    }

    /// 値を直接指定して設定を作る（テストでも使う）
    pub fn new(
        database_url: String,
        database_auth_token: Option<Secret>,
    ) -> Result<Config, ConfigError> {
        let config = Config {
            database_url,
            database_auth_token,
        };
        if config.requires_auth_token() && config.database_auth_token.is_none() {
            return Err(ConfigError::MissingAuthToken(config.database_url));
        }
        Ok(config)
    }

    /// ネットワークの向こうの DB（Turso / sqld）につなぐなら true
    pub fn is_remote(&self) -> bool {
        ["libsql://", "https://", "http://", "wss://", "ws://"]
            .iter()
            .any(|prefix| self.database_url.starts_with(prefix))
    }

    /// Turso（インターネット上の DB）ならトークンが必須
    fn requires_auth_token(&self) -> bool {
        ["libsql://", "https://", "wss://"]
            .iter()
            .any(|prefix| self.database_url.starts_with(prefix))
    }
}

/// 環境変数を1つ読む。無ければ `Ok(None)`
fn read_var(name: &'static str) -> Result<Option<String>, ConfigError> {
    match env::var(name) {
        Ok(value) => Ok(Some(value)),
        Err(env::VarError::NotPresent) => Ok(None),
        Err(env::VarError::NotUnicode(_)) => Err(ConfigError::NotUnicode(name)),
    }
}

/// 起動時のログに出す「待ち受けアドレス」。
/// `topcoat::start` と同じ規則（HOST / PORT、既定 127.0.0.1:3000）で組み立てる。
pub fn listen_address() -> String {
    let host = env::var("HOST").unwrap_or_else(|_| "127.0.0.1".to_string());
    let port = env::var("PORT").unwrap_or_else(|_| "3000".to_string());
    format!("{host}:{port}")
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: Secret は「隠す」と「出させない」の2つで守る

- `Debug` を `derive` せずに手で書き、`Secret(********)` とだけ表示します。だから、`Config` を `{:?}` でログに出しても（`Config` は `#[derive(Debug)]`）、トークンの中身は出ません。
- `Display` は**実装していません**。うっかり `{}` で表示しようとすると、コンパイルエラーになります（エラー2）。
- 中身が本当に要る所（`src/db.rs` の `Db::open` で Turso につなぐ所）だけで、`expose()` を呼びます。目立つ名前なので、`expose` で探せば、秘密を使っている場所がすぐ分かります。

##### 解説2: from_env と new を分ける

- `from_env` は「環境変数を読む」だけで、決まりの確かめは `new` に任せています。テストでは、環境変数を書き換えずに `Config::new(…)` で決まりを確かめられます（`#[cfg(test)]` の4つのテスト）。
- `is_remote`（ネットの向こうの DB か）と `requires_auth_token`（トークンが要るか）は、別の判定です。`http://` と `ws://` は「手元で動かす sqld（libSQL のサーバー）」のためのもので、リモートですが、トークンは要りません（例3-3の 6）。

##### 解説3: 環境変数が読めないときと、無いとき

- `read_var` は、無ければ `Ok(None)`、UTF-8 として読めなければ `ConfigError::NotUnicode` を返します。「無い」と「おかしい」を分けているので、既定値を使ってよい場合と、止めるべき場合を、取り違えません。
- 空の文字列のトークン（`DATABASE_AUTH_TOKEN=`）は、`filter(|t| !t.is_empty())` で「無い」と同じにしています。`.env.example` をコピーしたままの `DATABASE_AUTH_TOKEN=` の行が、「空のトークンで接続しようとする」事故にならないようにするためです。

#### 例3-2: src/main.rs と src/lib.rs の全文

> **▼ このファイルがやること（先に日本語で）:** `src/main.rs` は、起動の順番そのものです。`.env` を読み、設定を作り、CSS の束を読み、DB を開いてマイグレーションをかけ、ルーターを組み立てて待ち受けます。どこかで失敗したら、`anyhow` の `context` で「何をしようとして失敗したか」を付けて表示し、終わります。`src/lib.rs` は、アプリの中身を部品（モジュール）として公開するだけのファイルです。

```rust
//! RustNote の実行ファイルの入口。
//!
//! 起動の流れ:
//! 1. .env があれば環境変数として読み込む（開発用。本番では使わない）
//! 2. 設定（Config）を環境変数から作る
//! 3. アセット（CSS）の束を読み込む
//! 4. DB を開き、まだ適用していないマイグレーションを適用する
//! 5. ルーターを組み立て、HOST:PORT（既定 127.0.0.1:3000）で待ち受ける
//!
//! 起動時の失敗は anyhow で「何をしようとして失敗したか」を付けて表示し、終了する。

use anyhow::Context;
use rustnote::{
    config::{self, Config},
    db::{self, Db},
    routes,
    state::AppState,
};
use topcoat::asset::AssetBundle;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // .env が無くてもエラーにしない（本番では環境変数を直接設定する）
    dotenvy::dotenv().ok();

    let config = Config::from_env().context("設定を読み込めませんでした")?;

    // `topcoat asset bundle`（または `topcoat dev`）が実行ファイルの隣に作る assets/ を読む。
    // 無ければ DB に触る前に止める
    let assets = AssetBundle::load().context(
        "アセットの束（assets/）がありません。先に `topcoat asset bundle` を実行するか、`topcoat dev` で起動してください",
    )?;

    let db = Db::open(&config)
        .await
        .with_context(|| format!("DB（{}）を開けませんでした", config.database_url))?;
    let applied = db::migrate(&db)
        .await
        .context("マイグレーションに失敗しました")?;
    for version in &applied {
        eprintln!("マイグレーションを適用しました: {version}");
    }

    let router = routes::build_router(AppState::new(db), assets);

    eprintln!(
        "RustNote を起動しました: http://{}",
        config::listen_address()
    );
    topcoat::start(router)
        .await
        .context("サーバーを起動できませんでした（HOST / PORT を確認してください）")?;
    Ok(())
}
```

```rust
//! RustNote のライブラリ部分（アプリ本体）。
//!
//! 実行ファイル（src/main.rs）とテスト（tests/）の両方から使えるように、
```

##### 解説4: 手早く確かめられる物から

- 設定（②）と CSS の束（③）は、ファイルや環境変数を読むだけなので、一瞬で確かめられます。DB を開く（④）とマイグレーション（⑤）は、ファイルを作ったり、ネットの向こうに接続したりします。だから、先に②③を確かめ、だめなら、DB に触る前に止めます（例3-3）。
- `main` が返す `anyhow::Result<()>` は、`Err` で終わると、`Error:` と、`context` で付けた文、`Caused by:` の下に元のエラーを表示して、終了の番号を 1 にします。

##### 解説5: main.rs は薄く、中身は lib.rs に

- アプリの中身は、全部 `src/lib.rs` から公開する部品（`rustnote::config` など）に置き、`src/main.rs` は、それを順に呼ぶだけです。こうすると、`tests/` のテストや `examples/` の練習のプログラムも、同じ部品を `rustnote::…` で使えます（第9巻 UNIT 04）。
- `pub mod` の1行が、そのファイル（`src/flash.rs` など）を、このクレートの部品にする宣言です。1行消すと、そのファイルは無いのと同じになります（エラー1）。

#### 例3-3: 環境変数の組み合わせと、本物の起動

まず、`Config::from_env` が、6つの組み合わせをどう読むかを、練習用のプログラムで確かめます。

> **▼ このコードがやること（先に日本語で）:** `DATABASE_URL` と `DATABASE_AUTH_TOKEN` を、6通りに書き換えては、`Config::from_env()` を呼んで、結果（`Ok` の中身か、`Err` の文）を表示します。edition 2024 では、プログラムの中で環境変数を書き換える `set_var`・`remove_var` は `unsafe` なので、`unsafe { … }` の中で呼びます（エラー3）。

```rust
//! 第13巻 UNIT 03: 環境変数の組み合わせごとに、Config::from_env がどう読むかを確かめる。
//! 実行: cargo run -q --example u03_config

use std::env;

use rustnote::config::Config;

/// 環境変数をそろえてから、Config::from_env を呼んで結果を表示する
fn try_with(label: &str, url: Option<&str>, token: Option<&str>) {
    // SAFETY: このプログラムは1つのスレッドだけで動き、ほかに環境変数を読む人がいない
    unsafe {
        match url {
            Some(value) => env::set_var("DATABASE_URL", value),
            None => env::remove_var("DATABASE_URL"),
        }
        match token {
            Some(value) => env::set_var("DATABASE_AUTH_TOKEN", value),
            None => env::remove_var("DATABASE_AUTH_TOKEN"),
        }
    }
    match Config::from_env() {
        Ok(config) => println!(
            "{label}\n  → Ok: {config:?}（remote: {}）",
            config.is_remote()
        ),
        Err(error) => println!("{label}\n  → Err: {error}"),
    }
}

fn main() {
    try_with("1. 何も設定しない", None, None);
    try_with("2. ローカルのファイル", Some("data/rustnote.db"), None);
    try_with(
        "3. Turso の URL・トークン無し",
        Some("libsql://rustnote-demo.turso.io"),
        None,
    );
    try_with(
        "4. Turso の URL・トークンが空",
        Some("libsql://rustnote-demo.turso.io"),
        Some(""),
    );
    try_with(
        "5. Turso の URL・トークンあり",
        Some("libsql://rustnote-demo.turso.io"),
        Some("very-secret-token"),
    );
    try_with(
        "6. 手元の sqld（http）・トークン無し",
        Some("http://127.0.0.1:8080"),
        None,
    );
}
```

**問2の解答:**

- `Config` 全体を `{:?}` で文字にしたとき、①トークンの中身（`very-secret-token`）が含まれないこと、②`database_auth_token: Some(Secret(********))` と表示されること、③`expose()` で取り出すと、ちゃんと中身が返ること、の3つを確かめています（例3-1のテストの結果のとおり、通っています）。

- **直し方1（先に確かめる）:** `PORT` と `HOST` も、②の設定のところで読んで確かめます（`Config` に `port: u16` を足し、数でなければ `ConfigError` にする）。そうすれば、DB に触る前に止まります。
- **直し方2（先に待ち受けの場所を取る）:** `topcoat::start` は、中で「`HOST`・`PORT` を読む → `TcpListener::bind` → `serve`」をしています（topcoat 0.11.0 の `serve.rs`）。`main` の中で、DB を開く前に `TcpListener::bind` までしておき、マイグレーションのあとで `topcoat::serve(listener, router)` を呼べば、ポートが使えないこと（ほかのプログラムが使っている、など）も、DB に触る前に分かります。

### まとめ

- `src/config.rs` は、`DATABASE_URL`（無ければ `rustnote.db`）と `DATABASE_AUTH_TOKEN`（空は無いのと同じ）を読み、Turso の URL なのにトークンが無ければエラーにする。トークンは `Secret` に包み、`{:?}` では `Secret(********)`、`{}` ではコンパイルエラーにして守る。`.env` は、すでにある環境変数を上書きしない。

## UNIT 04: ドメインの型とエラーの分類

### この単元のゴール

- `src/domain.rs` の「検査済みの型」（`NoteTitle`・`Email`・`NoteId` など）が、中身を private にして、`parse` を通らずには作れないようにしている仕組みを説明できる
- タイトル・本文・メール・パスワード・ID の、それぞれの「数え方」と「そろえ方」（trim するか・小文字にするか・改行をそろえるか）を、いろいろな入力の実際の結果で言える
- `src/error.rs` の2つの層（DB の `RepoError` と、利用者への返事の `AppError`）と、`From` による変換、`status_code` と `public_message` の役目を説明できる
- 型が守れていない約束（`NoteQuery` の `pub` な項目、NUL の題）を、本物の実行で確かめられる

### たとえ話でつかむ

宅配便の受付の窓口を考えます。

- 窓口では、荷物の**大きさと重さを測り**、合格した荷物にだけ「**検査済み**」のシールを貼ります。シールは**窓口の係しか貼れません**。だから、奥で荷物を運ぶ人は、シールを見るだけで、測り直しません。
- 送り状の「届け先」と「依頼主」は、どちらも住所ですが、**欄が分かれている**ので、取り違えて書くことはありません。
- 断るときは、「重さも大きさも、両方オーバーです」と、**理由を全部まとめて**伝えます。1つ伝えて直してもらい、また次を伝えるのでは、お客さんが何度も並び直すことになります。
- 奥でトラックが故障しても、窓口では「時間をおいて、もう一度お越しください」とだけ伝え、**詳しい事情は業務日誌**に書きます。
- 「その荷物はありません」と「それは他人の荷物です」は、**同じ返事**にします。他人の荷物があること自体を、知らせないためです。

| 宅配の窓口 | RustNote（`src/domain.rs`・`src/error.rs`） |
|---|---|
| 大きさと重さを測る | `NoteTitle::parse` など（検査に通れば `Ok`、だめなら `Err`） |
| 検査済みのシール | `NoteTitle` などの型（中身は private） |
| シールは窓口の係しか貼れない | 中身が private なので、`domain` の外では `NoteTitle(…)` と書けない（エラー1） |
| 届け先と依頼主の欄 | `UserId` と `NoteId`（中身は同じ `i64` でも、別の型。エラー2） |
| 理由を全部まとめて伝える | `NewNote::parse`（タイトルと本文の問題を両方集める） |
| 窓口での説明と、業務日誌 | `public_message()`（500 では中身を隠す）と、ログ |
| 「ありません」と「他人のです」を同じに | 他人のノートも `AppError::NotFound`（404） |

```rust
//! ドメイン（アプリが扱う「もの」）の型。
//!
//! 外から来た文字列（フォーム・URL・DB の値）は、ここの `parse` / `new` を通して
//! 検査済みの型に変える。中身は private なので、検査を通らずに作る方法はない。
//! 「`NoteTitle` 型の値がある」＝「1〜80 文字の検査に合格した」が必ず成り立つ。

use std::fmt;
use std::str::FromStr;

use thiserror::Error;

// ---------------------------------------------------------------------------
// アプリ全体の定数
// ---------------------------------------------------------------------------

/// タイトルの最大文字数（chars().count() で数える。SQLite の length() と同じ）
pub const MAX_TITLE_CHARS: usize = 80;
/// 本文の最大文字数
pub const MAX_BODY_CHARS: usize = 10_000;
/// パスワードの最小文字数
pub const MIN_PASSWORD_CHARS: usize = 8;
/// パスワードの最大文字数
pub const MAX_PASSWORD_CHARS: usize = 128;
/// 一覧の1ページに表示するノートの数
pub const PER_PAGE: u32 = 20;
/// 検索キーワードの最大文字数（長すぎる入力で DB に負担をかけないため）
pub const MAX_KEYWORD_CHARS: usize = 100;

/// ID が不正だった理由
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum IdError {
    #[error("ID は数字で指定してください")]
    NotANumber,
    #[error("ID は 1 以上の数です")]
    NotPositive,
}

/// ユーザーの ID（users.id）
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct UserId(i64);

impl UserId {
    /// 1 以上の数だけを受け付ける
    pub fn new(value: i64) -> Result<UserId, IdError> {
        if value <= 0 {
            return Err(IdError::NotPositive);
        }
        Ok(UserId(value))
    }

    /// 中身の数を取り出す（DB に渡すときに使う）
    pub fn get(self) -> i64 {
        self.0
    }
}

impl fmt::Display for UserId {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}", self.0)
    }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct NoteId(i64);

impl NoteId {
    /// 1 以上の数だけを受け付ける
    pub fn new(value: i64) -> Result<NoteId, IdError> {
        if value <= 0 {
            return Err(IdError::NotPositive);
        }
        Ok(NoteId(value))
    }

    /// 中身の数を取り出す（DB に渡すときに使う）
    pub fn get(self) -> i64 {
        self.0
    }
}

// Topcoat の module_param! もこの FromStr を使って URL の {id} を NoteId に変える。
impl FromStr for NoteId {
    type Err = IdError;

    fn from_str(s: &str) -> Result<Self, Self::Err> {
        let value: i64 = s.parse().map_err(|_| IdError::NotANumber)?;
        NoteId::new(value)
    }
}

// href! で URL を組み立てるときに使う（/notes/42 の 42 の部分）

    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {

    }
}

/// メールアドレスが不正だった理由
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum EmailError {
    #[error("メールアドレスに @ がありません")]
    MissingAt,
    #[error("メールアドレスの形式が正しくありません")]
    Malformed,
    #[error("メールアドレスが長すぎます")]
    TooLong,
}

/// 検査済みのメールアドレス（前後の空白を除き、小文字にそろえてある）
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct Email(String);

impl Email {
    /// メールアドレスの最大の長さ（バイト数）
    pub const MAX_LEN: usize = 254;

    pub fn parse(input: &str) -> Result<Email, EmailError> {
        // 同じ人を同じ値にするため、前後の空白を除いて小文字にそろえる
        let normalized = input.trim().to_lowercase();
        if normalized.len() > Self::MAX_LEN {
            return Err(EmailError::TooLong);
        }
        let Some((local, domain)) = normalized.split_once('@') else {
            return Err(EmailError::MissingAt);
        };
        let bad = local.is_empty()
            || domain.is_empty()
            || domain.contains('@')
            || !domain.contains('.')
            || domain.starts_with('.')
            || domain.ends_with('.')
            || normalized.contains(char::is_whitespace);
        if bad {
            return Err(EmailError::Malformed);
        }
        Ok(Email(normalized))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Display for Email {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(&self.0)
    }
}

/// パスワードが不正だった理由
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum PasswordError {
    #[error("パスワードは{min}文字以上にしてください")]
    TooShort { min: usize },
    #[error("パスワードは{max}文字以内にしてください")]
    TooLong { max: usize },
}

/// 検査済みのパスワード。
/// Debug で中身が表示されないよう、Debug は手で実装している（ログへの漏れを防ぐ）。
#[derive(Clone, PartialEq, Eq)]
pub struct Password(String);

impl Password {
    pub fn parse(input: &str) -> Result<Password, PasswordError> {
        // パスワードは空白も含めて利用者が決めたものなので、trim しない
        let len = input.chars().count();
        if len < MIN_PASSWORD_CHARS {
            return Err(PasswordError::TooShort {
                min: MIN_PASSWORD_CHARS,
            });
        }
        if len > MAX_PASSWORD_CHARS {
            return Err(PasswordError::TooLong {
                max: MAX_PASSWORD_CHARS,
            });
        }
        Ok(Password(input.to_string()))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Debug for Password {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str("Password(***)")
    }
}

/// タイトルが不正だった理由
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum TitleError {
    #[error("タイトルを入力してください")]
    Empty,
    #[error("タイトルは{max}文字以内にしてください（現在{len}文字）")]
    TooLong { len: usize, max: usize },
}

/// 検査済みのタイトル（前後の空白を除いて 1〜80 文字）
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NoteTitle(String);

impl NoteTitle {
    pub const MAX_CHARS: usize = MAX_TITLE_CHARS;

    /// 文字列を検査し、合格したときだけ NoteTitle を返す
    pub fn parse(input: &str) -> Result<NoteTitle, TitleError> {
        let trimmed = input.trim();
        // 文字数は chars().count() で数える（len() はバイト数なので日本語で狂う）
        let len = trimmed.chars().count();
        if len == 0 {
            return Err(TitleError::Empty);
        }
        if len > Self::MAX_CHARS {
            return Err(TitleError::TooLong {
                len,
                max: Self::MAX_CHARS,
            });
        }
        Ok(NoteTitle(trimmed.to_string()))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl fmt::Display for NoteTitle {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(&self.0)
    }
}

/// 本文が不正だった理由
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum BodyError {
    #[error("本文は{max}文字以内にしてください（現在{len}文字）")]
    TooLong { len: usize, max: usize },
}

/// 検査済みの本文（空でもよい。最大 10,000 文字）
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NoteBody(String);

impl NoteBody {
    pub const MAX_CHARS: usize = MAX_BODY_CHARS;

    pub fn parse(input: &str) -> Result<NoteBody, BodyError> {
        // ブラウザのフォームは改行を \r\n で送ってくるので \n にそろえる
        let normalized = input.replace("\r\n", "\n");
        let len = normalized.chars().count();
        if len > Self::MAX_CHARS {
            return Err(BodyError::TooLong {
                len,
                max: Self::MAX_CHARS,
            });
        }
        Ok(NoteBody(normalized))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

/// 作成・編集フォームの検査で見つかった問題（項目ごと）
#[derive(Debug, Clone, Default, PartialEq, Eq)]
pub struct NoteInputErrors {
    pub title: Option<TitleError>,
    pub body: Option<BodyError>,
}

impl NewNote {
    /// タイトルと本文をまとめて検査する。
    /// 両方の問題を一度に画面へ出せるよう、最初の失敗で止めずに全部集める。
    pub fn parse(title: &str, body: &str) -> Result<NewNote, NoteInputErrors> {
        match (NoteTitle::parse(title), NoteBody::parse(body)) {
            (Ok(title), Ok(body)) => Ok(NewNote { title, body }),
            (title, body) => Err(NoteInputErrors {
                title: title.err(),
                body: body.err(),
            }),
        }
    }
}

/// 一覧の検索条件（キーワードとページ番号）
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NoteQuery {
    /// 検索キーワード。空なら None（すべて表示）
    pub keyword: Option<String>,
    /// 1 から始まるページ番号
    pub page: u32,
}

impl NoteQuery {
    /// URL の ?q= と ?page= から作る。空白だけのキーワードは無いのと同じに扱う
    pub fn new(keyword: Option<&str>, page: Option<u32>) -> NoteQuery {
        let keyword = keyword
            .map(str::trim)
            .filter(|k| !k.is_empty())
            .map(|k| k.chars().take(MAX_KEYWORD_CHARS).collect());
        NoteQuery {
            keyword,
            page: page.unwrap_or(1).max(1),
        }
    }

    /// SQL の OFFSET（何件読み飛ばすか）
    pub fn offset(&self) -> u64 {
        u64::from(self.page - 1) * u64::from(PER_PAGE)
    }
}

/// 一覧の1ページ分の結果
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NotePage {
    pub notes: Vec<Note>,
    /// 今のページ番号（1 から）
    pub page: u32,
    /// 条件に合うノートの総数
    pub total_count: u64,
}

impl NotePage {
    /// 全部で何ページあるか（0 件でも 1 ページと数える）
    pub fn total_pages(&self) -> u32 {
        let pages = self.total_count.div_ceil(u64::from(PER_PAGE)).max(1);
        u32::try_from(pages).unwrap_or(u32::MAX)
    }

    pub fn has_prev(&self) -> bool {
        self.page > 1
    }

    pub fn has_next(&self) -> bool {
        self.page < self.total_pages()
    }
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: 中身が private な「検査済みの型」

- `pub struct NoteTitle(String);` の `String` には `pub` が付いていません。型の名前は公開されていますが、**中身は `domain` の中からしか触れません**。だから、ほかのファイルでは `NoteTitle(…)` と書いて作ることも、`.0` で中身を書き換えることもできず、`NoteTitle::parse` で作り、`as_str()` で読むしかありません（エラー1）。
- こうすると、「`NoteTitle` 型の値がある」なら「1〜80 文字の検査に合格した」が、必ず成り立ちます。ルートやリポジトリは、`NoteTitle` を受け取るだけで、測り直しません（第9巻 UNIT 03 の「不変条件を型の検査で守る」）。
- `UserId` と `NoteId` は、中身はどちらも `i64` ですが、別の型です。ユーザーの ID を、ノートの ID の代わりに渡すと、コンパイルエラーになります（エラー2）。
- `NoteId` は `FromStr` を実装しているので、`"42".parse::<NoteId>()` と書けます。Topcoat の `module_param!` も、この `FromStr` で、URL の `/notes/{id}` の `{id}` を `NoteId` に変えます（UNIT 08）。

##### 解説2: 数え方と、そろえ方

| 型 | そろえ方 | 数え方と上限 | Debug と Display |
|---|---|---|---|
| `NoteTitle` | 前後の空白を除く（`trim`） | 文字数（`chars().count()`）で 1〜80 | どちらもあり |
| `NoteBody` | `\r\n` を `\n` にそろえる。trim しない | 文字数で 0〜10,000（空でよい） | Debug だけ |
| `Email` | trim して、小文字にそろえる | バイト数（`len()`）で 254 まで。`@` が1つ・ドメインに `.` など | どちらもあり |
| `Password` | そろえない（空白も、利用者が決めたパスワードの一部） | 文字数で 8〜128 | Debug は `Password(***)`。Display は無い |
| `NoteId`・`UserId` | なし | 1 以上の `i64` | どちらもあり |

- タイトルを `len()`（バイト数）で数えると、日本語は1文字が3バイトなので、27 文字で 80 を超えてしまいます。だから `chars().count()` で数えます（テスト `note_title_counts_characters_not_bytes`）。
- ブラウザのフォームは、改行を `\r\n` で送ってきます。本文は `\n` にそろえてから数えるので、改行を1文字と数えます。
- メールは、同じ人を同じ値にするために、小文字にそろえます。`Alice@Example.COM` と `alice@example.com` は、同じユーザーです。
- `Password` の `Debug` は、手で書いて `Password(***)` とだけ表示します。`#[derive(Debug)]` のままだと、`{:?}` でログに出したときに、パスワードがそのまま書かれてしまうからです（UNIT 03 の `Secret` と同じ考え方）。

##### 解説3: NewNote::parse は、問題を全部集める

- `match (NoteTitle::parse(title), NoteBody::parse(body))` で、2つを**両方**検査してから、結果の組み合わせを見ます。両方 `Ok` なら `NewNote`、どちらかが `Err` なら、`NoteInputErrors` に、それぞれの問題（無ければ `None`）を入れて返します。
- こうすると、「タイトルが空」と「本文が長すぎる」を、一度に画面に出せます（問1で、`?` で書いた版と比べます）。

##### 解説4: 一覧の検索の条件とページ送り

- `NoteQuery::new` は、URL の `?q=` と `?page=` から作ります。キーワードは trim して、空なら `None`（全部表示）、長ければ先頭の 100 文字だけにします。ページは、無ければ 1、0 なら 1 にそろえます（`max(1)`）。
- `offset` は、SQL の `OFFSET`（何件読み飛ばすか）で、`(page - 1) × 20` です。掛け算は `u64` でするので、大きなページの番号でも、あふれません。
- `NotePage::total_pages` は、`div_ceil`（割って切り上げ）で、全部で何ページあるかを数えます。0 件でも 1 ページです。`has_prev` と `has_next` は、「前へ」「次へ」のリンクを出すかどうかに使います（UNIT 07 の `pagination`）。
- **注意:** `NoteQuery` の項目（`keyword`・`page`）は `pub` です。ファイルの先頭のコメントには「検査を通らずに作る方法はない」とありますが、`NoteQuery` だけは、`new` を通らずに作れます（問2・第11巻 UNIT 04）。

#### 例4-2: src/error.rs の全文

> **▼ このファイルがやること（先に日本語で）:** 失敗を2つの層に分けます。`RepoError` は DB の層の失敗（一意制約の違反・version の食い違い・見つからない・値を読めない・DB の故障）です。`AppError` は、利用者への返事を決めるための分類で、それぞれが HTTP の状態コードに対応します。`RepoError` を `AppError` に変える決まり（`From`）と、状態コード（`status_code`）、画面に出してよい文（`public_message`）も、ここにあります。

```rust
//! エラーの分類。
//!
//! - `RepoError` … DB の層で起きる失敗（一意制約違反・version の食い違い・接続の失敗など）
//! - `AppError`  … 利用者への返事を決めるための分類。HTTP のステータスコードに対応する
//!
//! | AppError | ステータス | 起きる場面 |
//! |---|---|---|
//! | `InvalidTitle` など入力の検証エラー | 400 | 空のタイトル、形式の違うメール |
//! | `Unauthorized` | 401 | ログインしていない（通常はログイン画面へのリダイレクトで扱う） |
//! | `NotFound` | 404 | 存在しないノート、**他人のノート**（あること自体を隠す） |
//! | `EmailTaken` / `Conflict` | 409 | 登録済みのメール、ほかの画面で先に更新された |
//! | `Internal` | 500 | DB の故障など。画面には詳細を出さず、ログに原因を書く |

use thiserror::Error;
use topcoat::router::StatusCode;

use crate::domain::{BodyError, EmailError, PasswordError, TitleError};

/// いろいろな種類のエラーをまとめて入れる箱（Internal の中身に使う）
pub type BoxError = Box<dyn std::error::Error + Send + Sync>;

// ---------------------------------------------------------------------------
// DB の層のエラー
// ---------------------------------------------------------------------------

#[derive(Debug, Error)]
pub enum RepoError {
    #[error("一意制約に違反しました: {0}")]
    UniqueViolation(String),
    #[error("version が一致しません（ほかの更新が先に保存されました）")]
    VersionMismatch,
    #[error("対象のデータが見つかりません")]
    NotFound,
    #[error("DB の値を読み取れません: {0}")]
    InvalidData(String),
    #[error("DB の操作に失敗しました")]
    Database(#[source] libsql::Error),
}

// libsql のエラーを RepoError に変換する。
// 「UNIQUE constraint failed」はローカル（SQLite）でも Turso でも同じ文言なので、文言で見分ける。
impl From<libsql::Error> for RepoError {
    fn from(error: libsql::Error) -> Self {
        let message = error.to_string();
        if message.contains("UNIQUE constraint failed") {
            RepoError::UniqueViolation(message)
        } else {
            RepoError::Database(error)
        }
    }
}

// ---------------------------------------------------------------------------
// アプリの層のエラー
// ---------------------------------------------------------------------------

#[derive(Debug, Error)]
pub enum AppError {
    #[error(transparent)]
    InvalidTitle(#[from] TitleError),
    #[error(transparent)]
    InvalidBody(#[from] BodyError),
    #[error(transparent)]
    InvalidEmail(#[from] EmailError),
    #[error(transparent)]
    InvalidPassword(#[from] PasswordError),
    #[error("ログインしてください")]
    Unauthorized,
    #[error("ページが見つかりません")]
    NotFound,
    #[error("そのメールアドレスは既に登録されています")]
    EmailTaken,
    #[error("ほかの画面で先に更新されました。読み込み直してください")]
    Conflict,
    #[error("サーバーの中でエラーが起きました")]
    Internal(#[source] BoxError),
}

// DB の失敗を、利用者への返事の分類に変換する
impl From<RepoError> for AppError {
    fn from(error: RepoError) -> Self {
        match error {
            RepoError::VersionMismatch => AppError::Conflict,
            RepoError::NotFound => AppError::NotFound,
            other => AppError::Internal(Box::new(other)),
        }
    }
}

impl AppError {
    /// 想定外の失敗を Internal に包む
    pub fn internal(error: impl Into<BoxError>) -> AppError {
        AppError::Internal(error.into())
    }

    /// HTTP のステータスコード
    pub fn status_code(&self) -> StatusCode {
        match self {
            AppError::InvalidTitle(_)
            | AppError::InvalidBody(_)
            | AppError::InvalidEmail(_)
            | AppError::InvalidPassword(_) => StatusCode::BAD_REQUEST,
            AppError::Unauthorized => StatusCode::UNAUTHORIZED,
            AppError::NotFound => StatusCode::NOT_FOUND,
            AppError::EmailTaken | AppError::Conflict => StatusCode::CONFLICT,
            AppError::Internal(_) => StatusCode::INTERNAL_SERVER_ERROR,
        }
    }

    /// 画面に出してよい文章（500 のときは中身を隠す）
    pub fn public_message(&self) -> String {
        match self {
            AppError::Internal(_) => "時間をおいてもう一度お試しください".to_string(),
            other => other.to_string(),
        }
    }
}

#[cfg(test)]
mod tests {

        assert!(matches!(

        assert!(matches!(

            AppError::NotFound

        assert_eq!(internal.status_code(), StatusCode::INTERNAL_SERVER_ERROR);

    }
}
```

##### 解説5: 2つの層と、From による変換

- **`RepoError`（DB の層）:** libsql のエラーは、`From<libsql::Error>` で `RepoError` に変わります。文に `UNIQUE constraint failed` があれば `UniqueViolation`、それ以外は `Database` です。この文は、手元の SQLite でも Turso でも同じなので、文で見分けています。`Database(#[source] libsql::Error)` の `#[source]` は、元のエラーを「原因」として持っておく印で、ログに原因まで書けます。
- **`AppError`（返事の分類）:** `InvalidTitle(#[from] TitleError)` の `#[from]` は、`From<TitleError> for AppError` を作ります。だから、`AppError` を返す関数の中では、`NoteTitle::parse(…)?` と `?` を付けるだけで、`TitleError` が `AppError::InvalidTitle` に変わります（`#[from]` が無い型に `?` を付けると、エラー3）。`#[error(transparent)]` は、「文は、中の `TitleError` の文をそのまま使う」という意味です。
- **`From<RepoError> for AppError`:** `VersionMismatch` は `Conflict`（409）、`NotFound` は `NotFound`（404）、それ以外は全部 `Internal`（500）です。`UniqueViolation` も、ここでは `Internal` になります。登録済みのメールを 409 にするのは、`src/routes/signup.rs` が、変換する**前**に `UniqueViolation` を見分けているからです（UNIT 07）。

##### 解説6: status_code と public_message

- `status_code` の `match` には、`_`（そのほか全部）が**ありません**。`AppError` に種類を足すと、ここがコンパイルエラーになり、「新しい種類は、何番の状態コードか」を決めるまで、先へ進めません（問3）。
- `public_message` は、`Internal` だけ「時間をおいてもう一度お試しください」にして、ほかは `#[error("…")]` の文をそのまま返します。500 の原因（DB の故障の文など）は、画面には出さず、ログにだけ書きます（第11巻 UNIT 07）。
- `AppError::internal(…)` は、`Into<BoxError>` にできる物なら何でも `Internal` に包みます。`&str`（`"disk full"`）も、`std::error::Error` を実装した型も渡せます。

### 解答と解説

**問1の解答:**

```rust
//! 第13巻 UNIT 04 問1: NewNote::parse を ? で書いたら、どう変わるか。
//! 実行: cargo run -q --example u04_q1

use rustnote::domain::{NewNote, NoteBody, NoteTitle};

/// ? で書いた版（最初の失敗で止まる）
fn parse_with_question(title: &str, body: &str) -> Result<NewNote, String> {
    let title = NoteTitle::parse(title).map_err(|error| error.to_string())?;
    let body = NoteBody::parse(body).map_err(|error| error.to_string())?;
    Ok(NewNote { title, body })
}

fn main() {
    let long_body = "x".repeat(10_001);
    println!(
        "? で書いた版: {:?}",
        parse_with_question("", &long_body).map(|_| ())
    );

    let errors = NewNote::parse("", &long_body).unwrap_err();
    println!(
        "教材の版（タイトル）: {:?}",
        errors.title.map(|error| error.to_string())
    );
    println!(
        "教材の版（本文）: {:?}",
        errors.body.map(|error| error.to_string())
    );
}
```


- `?` で書いた版は、タイトルの問題で止まるので、本文の問題（10,001 文字）は伝わりませんでした。利用者は、タイトルを直して送り直してから、初めて本文の問題を知ります。
- 教材の版は、両方の問題を集めて返しました。作成のフォームは、この2つを、それぞれの入力欄の下に、一度に表示します（UNIT 08）。

### まとめ

- `src/domain.rs` の検査済みの型（`NoteTitle`・`NoteBody`・`Email`・`Password`・`NoteId`・`UserId`）は、中身が private なので、`parse`・`new` を通らずには作れない（E0423）。`UserId` と `NoteId` は取り違えられない（E0308）。

| マイグレーション | 表の作り（スキーマ）を変える手順を、番号順のファイルに分けて書いたもの |
| `schema_migrations` | 適用済みのマイグレーションの版の名前と時刻を記録する表 |
| トランザクション | いくつかの変更を、全部やるか全部やめるかの1まとまりにする仕組み。`commit` で確定、`rollback` で取り消す |
| 冪等 | 同じ操作を何回くり返しても、1回したときと同じ結果になること |
| `include_str!` | ファイルの中身を、コンパイルのときに文字列として実行ファイルに埋め込むマクロ |
| WAL（`journal_mode = wal`） | 変更をまず別のファイル（`-wal`）に書く方式。読み込みと書き込みが重なっても待ちにくい。ファイルに記録される |
| `busy_timeout` | ほかの接続が書き込み中のとき、何ミリ秒まで待つか。接続ごとの設定 |
| `PRAGMA foreign_keys` | 外部キーの確かめを ON にする SQLite の設定。SQLite では接続ごとに入れる |
| `sqlite_sequence` | `AUTOINCREMENT` の次の番号を、SQLite が自動で記録する表 |
| `EXPLAIN QUERY PLAN` | SQL を、DB がどう実行するつもりか（索引を使うか、全部読むか）を表示する |
| `SQLITE_CANTOPEN`（14） | DB のファイルを開けなかったときのエラーの番号。フォルダが無いときなど |

### UNIT 03 の用語

| 用語 | 意味 |
|---|---|
| 環境変数 | プログラムの外から渡す名前と値の組。RustNote は DATABASE_URL などを読む |
| `.env` | 開発のとき、環境変数をまとめて書いておくファイル。すでにある環境変数は上書きしない |
| `Config` | RustNote の設定（DB の URL と、Turso のトークン） |
| `Secret` | 秘密の値を包む型。`{:?}` では `Secret(********)`、`{}` は使えない |
| `expose()` | `Secret` の中身を取り出す、わざと目立つ名前のメソッド |
| `anyhow::Context` | エラーに「何をしようとして失敗したか」を付ける。main の `Error:`・`Caused by:` の表示になる |
| `pub mod` | ファイルを、クレートの部品（モジュール）にする宣言 |

### UNIT 04 の用語

| 用語 | 意味 |
|---|---|
| 検査済みの型 | 決まりの検査に合格した値だけが入る型。中身を private にして、parse を通らないと作れないようにする |
| `thiserror` | `#[derive(Error)]` と `#[error("…")]` で、エラーの型とその文を短く書けるようにするクレート |
| `#[from]` | thiserror の印。`From` を作るので、`?` でそのエラーを自動で変換できる |
| `#[source]` | thiserror の印。元のエラーを「原因」として持っておき、ログに原因まで書けるようにする |
| `RepoError` | RustNote の DB の層の失敗（一意制約の違反・version の食い違い・見つからない など） |
| `AppError` | RustNote の、利用者への返事を決める分類。HTTP の状態コードに対応する |
| `public_message` | 画面に出してよい文。500 のときは原因を隠す |
| `FromStr` | `"42".parse::<NoteId>()` のように、文字列から型を作れるようにする trait |
