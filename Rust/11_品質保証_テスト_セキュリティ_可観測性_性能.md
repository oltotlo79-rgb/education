# 第11巻: 品質保証 — テスト・セキュリティ・可観測性・性能

## この巻で身に付けること

第10巻までで、RustNote の画面と機能は、ひととおりそろいました。けれども、「今日、動いた」ことと、「明日も、誰かが直したあとも、ちゃんと動く」ことは別の話です。次のような事故は、動くアプリでも起きます。

- 小さな修正のつもりが、別の画面を壊していたのに、公開するまで誰も気づかなかった
- 英語のデータでは問題が無かったのに、日本語のタイトルを入れたら弾かれた
- 他人のノートが見えてしまう不具合を一度直したのに、半年後に同じ不具合がまた入った
- 公開したら遅くなったが、どこが遅いのか、測る方法が無かった
- 夜中に止まっていたのに、朝、利用者から言われるまで分からなかった

この巻では、こうした事故を、**テスト・見張り（可観測性）・測定**で、早く・自動で見つける方法を学びます。大事なのは、「とにかくテストをたくさん書く」ことではなく、**何を、どの段のテストで確かめるか**を決めることです。

### 到達目標

この巻を終えると、次のことができるようになります。

- 境界の値（空・1・最大・最大 + 1・日本語・空白）を表に並べた、ユニットテストを書ける。テストが本当に間違いを見つけられるかを、わざと壊した版で確かめられる
- 本物の DB を使った結合テスト、HTTP の返事（状態コード・ヘッダー・本文・クッキー）のテスト、ブラウザで操作する E2E テストを、役割を分けて書ける
- 脅威モデル（第8巻）を、「攻撃が止まること」を確かめる守りのテストに変えられる
- ログ・数の記録（メトリクス）・ヘルスチェックの違いを説明し、速さを release ビルドで測り、負荷をかけて限界を調べられる
- CI で、整形・Clippy・テスト・依存の監査を、毎回自動で回せる

### 前提知識（先に読んでおく巻）

- **第2巻（Rust 基礎）:** 日本語の文字数を `chars().count()` で数えること（第2巻 UNIT 05）。UNIT 01 の表に、日本語と絵文字の行が出てきます。
- **第4巻（設計）:** 検査済みの型（第4巻 UNIT 01）と、テストの書き方の基本（`#[test]`・`assert!`・`assert_eq!`。第4巻 UNIT 10）。
- **第9巻（RustNote 設計）:** RustNote のドメインの型（`NoteTitle`・`Email`・`Password`・`NoteId`）と、その決まり（第9巻 UNIT 03）。この巻のテストも、第9巻と同じ形（`tests/` に足して `cargo test --test 名前`）で書きます。

### この巻の進め方

テストは、「通った」だけでは、本当に役に立っているかが分かりません。各単元では、次の順番で進めてください。

1. **決まりを書き出す:** テストを書く前に、確かめる決まり（「タイトルは 1〜80 文字」など）を、日本語で書き出します。
2. **端の値を並べる:** 決まりの両側（80 と 81、0 と 1）と、間違えやすい入力（空白・日本語・絵文字）を表にします。
3. **テストを動かす:** 全部の行が通ることを確かめます。
4. **わざと壊して確かめる:** 関数をわざと間違えた版に変えても、テストがちゃんと失敗するかを確かめます。失敗しないテストは、何も守っていません。

## UNIT 01: ユニットテスト・境界値・表の形のテスト

### この単元のゴール

- テストの「段」（ユニット・結合・HTTP・E2E）の違いを、速さと確かめる範囲で説明できる
- 決まりの両側の値（境界値: 0 と 1、80 と 81）と、間違えやすい入力（空白・全角の空白・日本語・絵文字）を表に並べて、1つのテストで確かめられる
- わざと間違えた版の関数に同じ表を当てて、テストが本当に間違いを見つけられるかを確かめられる
- 文字列の長さの3つの数え方（文字・バイト・UTF-16）の違いを、実際の値で説明できる

### たとえ話でつかむ

お菓子の工場で、袋詰めの機械を検査する場面を考えます。決まりは「1袋に 1〜80 個」です。

- 検査の人は、40 個のような**ちょうど真ん中**の袋だけを試すことはしません。真ん中が正しくても、端で間違える機械はよくあるからです。**0 個・1 個・80 個・81 個**の4つを必ず試します。決まりの**境目の両側**です。
- 形が崩れたお菓子・小さなお菓子・2つがくっついたお菓子のように、**数え方を間違えやすいもの**も試します。
- 検査の結果は、**表**に書きます。「何を入れたか・どうなるはずか・どうなったか」を1行ずつ並べれば、どこで間違えたかが一目で分かります。
- そして、検査の表そのものが正しいかも確かめます。わざと**壊した機械**に同じ検査をして、ちゃんと「不合格」が出るかを見るのです。壊れた機械まで合格にしてしまう検査は、意味がありません。

| お菓子の工場 | RustNote のテスト |
|---|---|
| 「1袋に 1〜80 個」の決まり | `NoteTitle::parse` の「前後の空白を除いて 1〜80 文字」 |
| 0・1・80・81 個の袋 | **境界値**（決まりの端と、その外側） |
| 数え方を間違えやすいお菓子 | 全角の空白・日本語・絵文字・濁点を分けて書いた「が」 |
| 検査の表 | **表の形のテスト**（入力と期待する結果を、1行ずつ並べたテスト） |
| 壊した機械で検査を試す | **わざと間違えた版**で、テストが失敗するかを見る |

> **用語:** ユニットテスト（unit test：関数や型のような小さな部品1つを、ほかから切り離して確かめるテスト。DB もネットワークも使わないので速い）

### まず動かす最小コード

#### 例1-1: NoteTitle::parse を、表の形で確かめる

> **▼ このコードがやること（先に日本語で）:** タイトルの決まりを確かめる行（名前・入力・期待する結果）を、表（`Vec<Case>`）に並べます。表のすべての行を `NoteTitle::parse` に渡し、期待どおりなら `ok`、違えば `NG` と、実際の結果を表示します。合わなかった行が1つでもあれば、テストを失敗させます。同じ表を、わざと間違えた版の関数（文字数を `len()` で数える）にも当てて、表が間違いを見つけられるかも確かめます。

```rust
//! 第11巻 UNIT 01: NoteTitle::parse を、境界の値を並べた表で確かめる（表の形のテスト）。
//! 実行: cargo test --test u01_title_table -- --nocapture

use rustnote::domain::NoteTitle;

/// 期待する結果: 合格して入る値か、不合格のときのエラーの文
enum Expect {
    Ok(String),
    Err(&'static str),
}

/// 表の1行: 名前・入力・期待する結果
struct Case {
    label: &'static str,
    input: String,
    expect: Expect,
}

fn ok(label: &'static str, input: impl Into<String>, value: impl Into<String>) -> Case {
    Case {
        label,
        input: input.into(),
        expect: Expect::Ok(value.into()),
    }
}

fn err(label: &'static str, input: impl Into<String>, message: &'static str) -> Case {
    Case {
        label,
        input: input.into(),
        expect: Expect::Err(message),
    }
}

/// タイトルの決まり（前後の空白を除いて 1〜80 文字）を、境界の値で並べた表
fn title_cases() -> Vec<Case> {
    let a80 = "あ".repeat(80);
    vec![
        ok("ふつうの日本語", "牛乳を買う", "牛乳を買う"),
        ok("前後の空白は取る", "  買い物  ", "買い物"),
        err("空", "", "タイトルを入力してください"),
        err("半角の空白だけ", "   ", "タイトルを入力してください"),
        err("全角の空白だけ", "\u{3000}", "タイトルを入力してください"),
        ok("1文字（下の端）", "あ", "あ"),
        ok("80文字（上の端）", a80.clone(), a80.clone()),
        err(
            "81文字（上の端 + 1）",
            "あ".repeat(81),
            "タイトルは80文字以内にしてください（現在81文字）",
        ),
        ok("空白を除けば80文字", format!(" {a80} "), a80),
        ok(
            "絵文字の家族（見た目は1つ）",
            "👨\u{200D}👩\u{200D}👧",
            "👨\u{200D}👩\u{200D}👧",
        ),
    ]
}

/// 表のすべての行を `parse` で試し、合わなかった行の説明を返す
fn check(parse: impl Fn(&str) -> Result<String, String>) -> Vec<String> {
    let mut failures = Vec::new();
    for case in title_cases() {
        let actual = parse(&case.input);
        let matched = match (&case.expect, &actual) {
            (Expect::Ok(value), Ok(got)) => value == got,
            (Expect::Err(message), Err(got)) => message == got,
            _ => false,
        };
        let mark = if matched { "ok  " } else { "NG  " };
        let shown = match &actual {
            Ok(got) if got.chars().count() > 10 => {
                format!("Ok（{} 文字）", got.chars().count())
            }
            Ok(got) => format!("Ok({got:?})"),
            Err(message) => format!("Err({message})"),
        };
        println!("{mark}{} → {shown}", case.label);
        if !matched {
            failures.push(case.label.to_string());
        }
    }
    failures
}

/// RustNote の NoteTitle::parse を、表の形にそろえて呼ぶ
fn rustnote_parse(input: &str) -> Result<String, String> {
    NoteTitle::parse(input)
        .map(|title| title.as_str().to_string())
        .map_err(|error| error.to_string())
}

#[test]
fn note_title_follows_the_table() {
    let failures = check(rustnote_parse);
    assert!(failures.is_empty(), "表と合わなかった行: {failures:?}");
}

/// わざと間違えた版: 文字数を len()（バイト数）で数えている
fn broken_parse(input: &str) -> Result<String, String> {
    let trimmed = input.trim();
    let len = trimmed.len();
    if len == 0 {
        return Err("タイトルを入力してください".to_string());
    }
    if len > 80 {
        return Err(format!(
            "タイトルは80文字以内にしてください（現在{len}文字）"
        ));
    }
    Ok(trimmed.to_string())
}

#[test]
fn the_table_catches_a_broken_version() {
    let failures = check(broken_parse);
    println!("わざと間違えた版で合わなかった行: {failures:?}");
    // 表が、間違いを見つけられること（合わない行が1つ以上あること）を確かめる
    assert!(!failures.is_empty(), "表が間違いを見つけられませんでした");
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: 表の1行に、名前を付ける

- `Case` は、表の1行です。`label`（行の名前）・`input`（入力）・`expect`（期待する結果）の3つを持ちます。`ok(...)` と `err(...)` は、行を短く書くための小さな関数です。
- 行の名前に「80文字（上の端）」「81文字（上の端 + 1）」のように、**なぜその行があるのか**を書いておきます。失敗したときに、どの決まりの、どの端で間違えたのかが、名前だけで分かります（エラー1）。
- `"\u{3000}"` は全角の空白、`"\u{200D}"` は、絵文字どうしをつなぐ「見えない文字」（ゼロ幅接合子）です。見えない文字は、ソースに直接書くと区別できないので、`\u{...}` の形で書きます。

##### 解説2: 1つの確かめ方を、全部の行に当てる

- `check` は、表のすべての行に、同じ確かめ方を当てる関数です。比べたい関数を引数（`parse`）で受け取るので、RustNote の `NoteTitle::parse` にも、わざと間違えた版にも、同じ表を使えます。
- 1行ずつ `assert!` で止めずに、合わなかった行の名前を `failures` に集めてから、最後にまとめて `assert!` しています。こうすると、1回の実行で、**合わない行を全部**見つけられます。

##### 解説3: RustNote の版は、全部の行が ok

- 1つ目のテスト（`note_title_follows_the_table`）では、10 行すべてが `ok` でした。半角の空白だけ・全角の空白だけは「タイトルを入力してください」、81 文字は「タイトルは80文字以内にしてください（現在81文字）」です。前後に空白を付けた 82 文字の入力は、空白を除くと 80 文字なので合格でした。
- 家族の絵文字の行は、`Ok("👨\u{200d}👩\u{200d}👧")` と表示されました。`{:?}` で表示すると、見えない文字（ゼロ幅接合子）が `\u{200d}` と書き出されます。

##### 解説4: 間違えた版は、80 と 81 の行で見つかった

- 2つ目のテスト（`the_table_catches_a_broken_version`）では、文字数を `len()`（バイト数）で数える版に、同じ表を当てました。`NG` になったのは、80 文字・81 文字・空白を除けば 80 文字の3行です。日本語の「あ」は1文字3バイトなので、80 文字は 240 バイトと数えられ、「長すぎる」と断られました。
- 一方、「牛乳を買う」（15 バイト）や、家族の絵文字（18 バイト）の行は、間違えた版でも `ok` でした。**短い日本語だけの表では、この間違いを見つけられない**のです。境界値の行を入れておいたから、見つけられました。
- このテストは、「間違えた版で、合わない行が1つ以上あること」を `assert!` で確かめています。表を直していて、うっかり境界値の行を消してしまったら、このテストが失敗して教えてくれます。

#### 例1-2: 「長さ」の3つの数え方を比べる

タイトルの文字数は、`chars().count()` で数えています。でも、人が見て「1文字」と思うものと、プログラムの数え方は、いつも同じではありません。

> **▼ このコードがやること（先に日本語で）:** いくつかの文字列について、`chars().count()`（Unicode の文字の数）・`len()`（UTF-8 のバイト数）・`encode_utf16().count()`（UTF-16 の単位の数）の3つを表示し、`NoteTitle::parse` が合格にするかも表示します。

```rust
//! 1つの文字列の「長さ」を、3通りの数え方で比べる。
//! NoteTitle::parse は chars().count()（Unicode の文字の数）で数えている。
//! 実行: cargo run -q --example u01_counts

use rustnote::domain::NoteTitle;

fn main() {
    let samples = [
        ("A", "A"),
        ("あ", "あ"),
        ("が（1文字で表した形）", "\u{304C}"),
        ("が（か + 濁点の2つで表した形）", "\u{304B}\u{3099}"),
        ("👍", "👍"),
        ("家族の絵文字", "👨\u{200D}👩\u{200D}👧"),
        ("ゼロ幅スペースだけ", "\u{200B}"),
    ];
    for (label, text) in samples {
        let parsed = match NoteTitle::parse(text) {
            Ok(_) => "合格".to_string(),
            Err(error) => format!("不合格（{error}）"),
        };
        println!("[{label}]");
        println!(
            "    文字 {} ／ バイト {} ／ UTF-16 {} ／ NoteTitle::parse は {parsed}",
            text.chars().count(),
            text.len(),
            text.encode_utf16().count()
        );
    }
}
```

- **家族の絵文字は、5 文字:** 見た目は1つですが、👨・つなぐ文字・👩・つなぐ文字・👧の5文字でできています。RustNote では、この絵文字を 16 個入れると、見た目は 16 個でも 80 文字になり、17 個目で断られます。

- **UTF-16 の数との食い違い:** ブラウザの入力欄の `maxlength`（入力できる長さの上限）は、HTML の決まりでは UTF-16 の単位で数えます。RustNote の作成のフォームは `maxlength=(MAX_TITLE_CHARS)`（80）を付けているので、決まりどおりに数えるブラウザでは、👍 のように UTF-16 で 2 単位の絵文字だけのタイトルは、40 個までしか入りません。サーバーは 80 文字（80 個）まで受け付けるので、ブラウザのほうが先に止めることになります。実際のブラウザでの数え方は、ブラウザを使ったテストで確かめます（UNIT 05）。どの数え方で「長さ」を決めるかは、仕様として決めて、表のテストに書いておきます。

> **注意:** 人が見て「1文字」と思う単位（書記素クラスタ）で数えるには、標準ライブラリではなく、`unicode-segmentation` のような外のクレートが必要です。RustNote は、SQLite の `length()` と同じ数え方（Unicode の文字の数）にそろえることを優先して、`chars().count()` を使っています（第2巻 UNIT 05・第9巻 UNIT 03）。

### まとめ

- テストには段がある。ユニットテストは、関数1つを速く確かめる段で、決まりの細かい端はここで確かめる。上の段（DB・HTTP・E2E）は、つながりを確かめる段で、大事な流れに絞る。
- 境界値（端と、その1つ外側）と、間違えやすい入力（空白・全角の空白・日本語・絵文字）を、名前付きの行で表に並べる。1つの確かめ方を全部の行に当て、合わない行をまとめて報告する。
- わざと間違えた版に同じ表を当てて、テストが失敗することを確かめる。結果を確かめないテストは、何も守っていない。

## UNIT 02: リポジトリの結合テスト

### この単元のゴール

- リポジトリ（`NoteRepository` など）を、偽物ではなく**本物の DB**（一時フォルダの libSQL ファイル）で確かめる理由を、SQL の細かい決まりの例で説明できる
- 準備（Arrange）・操作（Act）・確かめ（Assert）の形で、成功・見つからない・他人・版の食い違いを、1つずつ確かめるテストを書ける
- わざと SQL を壊したとき、ユニットテストは通ったまま、結合テストだけが気づく様子を確かめられる
- テストどうしが DB ファイルを使い回したときに起きる、実行のたびに変わる失敗を読み、テストごとに新しい DB を作る形に直せる

### たとえ話でつかむ

レストランの厨房で、新しいスープの味を確かめる場面を考えます。

- UNIT 01 のユニットテストは、**材料1つずつの味見**です。「塩はこの量」「だしはこの濃さ」と、1つずつ確かめます。速くて、どこが悪いかもすぐ分かります。
- ところが、材料が全部正しくても、**実際の鍋で煮る**と、火加減や、入れる順番のせいで、思った味にならないことがあります。そこで、本物の鍋で煮て味見をします。これが、この単元の**結合テスト**です。
- 味見のたびに、**洗った新しい鍋**を使います。前の人が使った鍋のままだと、前のスープの味が残っていて、どちらの味なのか分からなくなります。2人が同時に1つの鍋を使えば、もっと混乱します。

| 厨房 | RustNote のテスト |
|---|---|
| 材料1つずつの味見 | ユニットテスト（`escape_like` や `NoteTitle::parse` を、DB なしで確かめる。UNIT 01） |
| 本物の鍋で煮て味見 | リポジトリの結合テスト（本物の libSQL に、本物の SQL を流す） |
| 火加減・入れる順番 | SQL の細かい決まり（`LIKE` の `ESCAPE`・`WHERE` の条件・`UNIQUE`・`ON DELETE CASCADE`） |
| 洗った新しい鍋 | テストごとに作る一時フォルダの DB（`common::test_db()`） |
| 前のスープの味が残る | 前のテストのデータが残った DB。結果が実行のたびに変わる |

> **用語:** 結合テスト（けつごうテスト：いくつかの部品を、本物どうしでつないで確かめるテスト。ここでは、リポジトリと本物の DB をつなぐ）

#### 例2-1: NoteRepository の約束を、1つずつ確かめる

`NoteRepository` の6つのメソッドには、それぞれ約束があります（`src/repository/notes.rs` のコメント）。たとえば「他人のノート・存在しないノートは None」「`expected_version` が今の version と違えば `VersionMismatch`」です。これを、本物の DB で1つずつ確かめます。

> **▼ このコードがやること（先に日本語で）:** 空の DB に alice と bob を登録します（準備）。alice のノートを作り、探す・更新する・完了にする・消す、を、alice と bob の両方から試します（操作）。それぞれの結果を、1行ずつ表示します（確かめ）。ここでは結果を見るために表示していますが、本物のテストでは `assert!` で確かめます。

```rust
//! 第11巻 UNIT 02: NoteRepository の約束を、本物の DB（一時フォルダの libSQL ファイル）で1つずつ確かめる。
//! 実行: cargo test --test u02_contract -- --nocapture

mod common;

use rustnote::{
    domain::{Email, NewNote, Note, NoteId},
    error::RepoError,
    repository::{LibsqlNoteRepository, LibsqlUserRepository, NoteRepository, UserRepository},
};

/// ノートの大事な所だけを、1行の文字列にする
fn brief(result: Result<Note, RepoError>) -> String {
    match result {
        Ok(note) => format!(
            "Ok（id={} version={} done={} title={:?}）",
            note.id, note.version, note.done, note.title
        ),
        Err(error) => format!("Err({error:?})"),
    }
}

fn new_note(title: &str) -> NewNote {
    NewNote::parse(title, "").expect("テスト用のノート")
}

#[tokio::test]
async fn note_repository_contract() {
    // Arrange: 空の DB と、2人のユーザー
    let test = common::test_db().await;
    let users = LibsqlUserRepository::new(test.db.clone());
    let notes = LibsqlNoteRepository::new(test.db.clone());
    let alice = users
        .create(
            &Email::parse("alice@example.com").unwrap(),
            "$argon2id$dummy",
        )
        .await
        .unwrap();
    let bob = users
        .create(&Email::parse("bob@example.com").unwrap(), "$argon2id$dummy")
        .await
        .unwrap();

    // Act と Assert: 約束を1つずつ
    let created = notes.insert(alice.id, &new_note("初版")).await.unwrap();
    let id = created.id;
    println!(
        "insert（alice）             → {}",
        brief(Ok(created.clone()))
    );
    println!(
        "   作成と更新の日時が同じ   → {}",
        created.created_at == created.updated_at
    );

    let found = notes.find(alice.id, id).await.unwrap();
    println!(
        "find（alice）               → 見つかる: {}",
        found.is_some()
    );
    let found = notes.find(bob.id, id).await.unwrap();
    println!(
        "find（bob）                 → 見つかる: {}",
        found.is_some()
    );

    let result = notes.update(alice.id, id, &new_note("第2版"), 1).await;
    println!("update（alice, version 1）  → {}", brief(result));
    let result = notes.update(alice.id, id, &new_note("古い画面"), 1).await;
    println!("update（alice, version 1）  → {}", brief(result));
    let missing = NoteId::new(99).unwrap();
    let result = notes.update(alice.id, missing, &new_note("無い"), 1).await;
    println!("update（alice, id 99）      → {}", brief(result));
    let result = notes.update(bob.id, id, &new_note("乗っ取り"), 2).await;
    println!("update（bob, version 2）    → {}", brief(result));

    let result = notes.toggle_done(alice.id, id).await;
    println!("toggle_done（alice）        → {}", brief(result));

    println!(
        "delete（bob）               → {:?}",
        notes.delete(bob.id, id).await
    );
    println!(
        "delete（alice）             → {:?}",
        notes.delete(alice.id, id).await
    );
    println!(
        "delete（alice, もう一度）   → {:?}",
        notes.delete(alice.id, id).await
    );
}
```

### RustNote ではここで使う

テストごとの DB は、`tests/common/mod.rs` の `test_db` が作ります（抜き出しています）。

```rust
/// 一時フォルダの DB。TempDir が消えるとフォルダごと削除される
pub struct TestDb {
    pub db: Db,
    _dir: TempDir,
}

/// マイグレーション済みの空の DB を作る
pub async fn test_db() -> TestDb {
    let dir = tempfile::tempdir().expect("一時フォルダを作れません");
    let db = Db::open_local(dir.path().join("test.db"))
        .await
        .expect("DB を開けません");
    db::migrate(&db).await.expect("マイグレーションに失敗");
    TestDb { db, _dir: dir }
}
```

- `tempfile::tempdir()` は、ほかと重ならない名前の一時フォルダを作ります。テストが同時にいくつ動いても、それぞれ別のフォルダです。
- `TestDb` は、`db` と一緒に `TempDir` を持っています。テストが終わって `TestDb` が片付けられる（drop される）と、`TempDir` もフォルダごと消えます（第3巻 UNIT 01）。項目の名前が `_dir` と `_` で始まるのは、「使わないが、持っておくこと自体に意味がある」という印です。`TempDir` を持っておくのは、テストの間はフォルダを残し、終わったら消すためです。
- 本番と同じ `db::migrate` を当てるので、テストの DB の表は、いつも本番と同じ形です。マイグレーションを足せば、テストの DB にも自動で入ります。

`tests/repository.rs` は、この `test_db` を使って、リポジトリの約束を8つのテストで確かめています。ユーザーを登録する手順は、何度も出てくるので、小さな関数にまとめています（抜き出しています）。

**問2の解答:**

`tests/u02_q2.rs` です。

```rust
//! 問2の解答: セッションの期限ちょうどの時刻で、探す・掃除するとどうなるかを確かめる。
//! 実行: cargo test --test u02_q2 -- --nocapture

mod common;

use std::time::{Duration, SystemTime, UNIX_EPOCH};

use rustnote::{
    domain::Email,
    repository::{
        LibsqlSessionRepository, LibsqlUserRepository, SessionRepository, UserRepository,
    },
};
use topcoat::session::TokenHash;

#[tokio::test]
async fn session_expiry_boundary() {
    let test = common::test_db().await;
    let users = LibsqlUserRepository::new(test.db.clone());
    let sessions = LibsqlSessionRepository::new(test.db.clone());
    let alice = users
        .create(
            &Email::parse("alice@example.com").unwrap(),
            "$argon2id$dummy",
        )
        .await
        .unwrap();

    // 期限（T）を、決まった時刻にしておく（今の時刻に頼らない）
    let t = UNIX_EPOCH + Duration::from_secs(2_000_000_000);
    let second = Duration::from_secs(1);
    let hash = TokenHash::new([7; 32]);
    sessions.create(&hash, alice.id, t).await.unwrap();

    for (label, now) in [
        ("T - 1秒", t - second),
        ("T ちょうど", t),
        ("T + 1秒", t + second),
    ] {
        let found = sessions.find_user(&hash, now).await.unwrap();
        println!("find_user（{label}）→ 見つかる: {}", found.is_some());
    }
    let before: SystemTime = t - second;
    println!(
        "delete_expired（T - 1秒）→ {} 件消した",
        sessions.delete_expired(before).await.unwrap()
    );
    println!(
        "delete_expired（T ちょうど）→ {} 件消した",
        sessions.delete_expired(t).await.unwrap()
    );
}
```

- 期限ちょうどの T では、もう見つかりませんでした。`find_user` の SQL は `s.expires_at > ?2`（期限が今より**あと**なら有効）で、`delete_expired` は `expires_at <= ?1`（期限が今か、今より**前**なら消す）です。T ちょうどは「使えない」側と「消す」側の両方に入るので、すき間も重なりもありません。
- 境界の「ちょうど」は、UNIT 01 の境界値と同じで、いちばん間違えやすい所です。`>` と `>=` を取り違えると、「期限ちょうどの1秒だけ、使えないのに消されない」セッションができます。
- 時刻を `SystemTime::now()` ではなく、決まった時刻（`UNIX_EPOCH` から 20 億秒）にしたのは、テストの結果を、動かした時刻によって変えないためです（エラー2の「共有しているもの」の1つが、今の時刻です）。

```rust
//! 問3の解答: ユーザーを消すと、その人のノートとセッションはどうなるかを確かめる。
//! 実行: cargo test --test u02_q3 -- --nocapture

mod common;

use std::time::{Duration, SystemTime};

use rustnote::{
    db::Db,
    domain::{Email, NewNote},
    repository::{
        LibsqlNoteRepository, LibsqlSessionRepository, LibsqlUserRepository, NoteRepository,
        SessionRepository, UserRepository,
    },
};
use topcoat::session::TokenHash;

/// 表ごとの行の数を、1行の文字列にする
async fn counts(db: &Db) -> String {
    let conn = db.connect().await.expect("DB に接続できません");
    let mut parts = Vec::new();
    for table in ["users", "notes", "sessions"] {
        let mut rows = conn
            .query(&format!("SELECT COUNT(*) FROM {table}"), ())
            .await
            .expect("数えられません");
        let row = rows
            .next()
            .await
            .expect("行を読めません")
            .expect("行がない");
        let count: i64 = row.get(0).expect("COUNT(*)");
        parts.push(format!("{table}={count}"));
    }
    parts.join(" ")
}

#[tokio::test]
async fn deleting_a_user_cascades() {
    let test = common::test_db().await;
    let users = LibsqlUserRepository::new(test.db.clone());
    let notes = LibsqlNoteRepository::new(test.db.clone());
    let sessions = LibsqlSessionRepository::new(test.db.clone());
    let expires = SystemTime::now() + Duration::from_secs(60);
    for (n, email) in ["alice@example.com", "bob@example.com"]
        .into_iter()
        .enumerate()
    {
        let user = users
            .create(&Email::parse(email).unwrap(), "$argon2id$dummy")
            .await
            .unwrap();
        for title in ["1件目", "2件目"] {
            notes
                .insert(user.id, &NewNote::parse(title, "").unwrap())
                .await
                .unwrap();
        }
        let hash = TokenHash::new([n as u8; 32]);
        sessions.create(&hash, user.id, expires).await.unwrap();
    }
    println!("消す前: {}", counts(&test.db).await);

    // RustNote には「退会」の機能がまだ無いので、SQL で直接 alice を消す
    let conn = test.db.connect().await.unwrap();
    let deleted = conn
        .execute("DELETE FROM users WHERE email = 'alice@example.com'", ())
        .await
        .unwrap();
    println!("users から {deleted} 行消した");
    println!("消した後: {}", counts(&test.db).await);
}
```

- `migrations` の表の定義で、`notes.user_id` と `sessions.user_id` に `REFERENCES users(id) ON DELETE CASCADE`（参照先が消えたら、一緒に消す）と書いてあり、libSQL の接続では外部キーの検査が有効（`foreign_keys=1`。第13巻 UNIT 02）だからです。
- もし外部キーの検査が無効だったら、持ち主のいないノートが残ります。こうした**表の約束**も、SQL と同じで、本物の DB でしか確かめられません。RustNote に「退会」の機能を作るときは、このテストを、その機能のテストに育てます。

### まとめ

- リポジトリは、本物の DB（一時フォルダの libSQL ファイル）で確かめる。Rust の関数が正しくても、SQL の `ESCAPE` や `WHERE` の持ち主の条件が壊れていれば、ユニットテストは通ったままになる。
- 準備・操作・確かめの形で、成功だけでなく、見つからない・他人・版の食い違いを1つずつ確かめる。`assert!` には、失敗したときの文と実際の値を書いておく。
- テストごとに新しい DB を作り、テストどうしで何も共有しない。共有すると、結果が実行のたびに変わり、前の実行のデータにも引きずられる。

## UNIT 03: HTTP のテスト

### この単元のゴール

- レスポンスの4つの部分（状態コード・ヘッダー・クッキー・本文）を、RustNote の本物のレスポンスで読み、それぞれ何を確かめればよいかを言える
- 確かめの道具（`assert_redirect`・`cookie_attributes`）を作り、`#[track_caller]` を付けて、失敗したときに**テストのどの行か**が出るようにできる
- 本文を「その文字があるか」（`contains`）ではなく、CSS セレクター（`scraper`）で「どの要素の中か」まで決めて確かめる理由を、通ってしまう間違いで説明できる
- 同じ名前のヘッダー（`Set-Cookie`）が2つあるときの読み方と、順番に頼ったテストが、ときどきだけ失敗する理由を言える

### たとえ話でつかむ

通販の荷物を受け取って、中身を確かめる（検品する）場面を考えます。

- **伝票の印:** 「お届け済み」「転送しました」のような印が、まず目に入ります。これが**状態コード**です。「転送しました」なら、**転送先の住所**（`Location`）も確かめます。
- **同封の会員証:** 箱に、会員証が入っていることがあります。会員証には「有効期限」「本人だけが使えます」のような**注意書き**（属性）が付いています。会員証が2枚入っているとき、どちらが上に入っているかは、**決まっていません**。だから、上から1枚目ではなく、**名前で**探します。
- **箱の中身:** 「箱のどこかに『リンゴ』という字がある」では、検品になりません。中に入っていたチラシに「リンゴ」と書いてあるだけかもしれないからです。「**果物の仕切りの中に**、リンゴが1個」と、**場所まで決めて**確かめます。

| 荷物の検品 | HTTP のテスト |
|---|---|
| 伝票の印 | 状態コード（`200 OK`・`303 See Other`・`404 Not Found` など） |
| 転送先の住所 | `Location` ヘッダー |
| 会員証と注意書き | `Set-Cookie` ヘッダーと、その属性（`HttpOnly`・`Max-Age` など） |
| 会員証が2枚 | 同じ名前のヘッダーが2つ（`get_all` で全部読み、名前で探す） |
| 箱の中身 | 本文（HTML） |
| 仕切りの中で確かめる | CSS セレクターで、要素を決めて確かめる（例3-3） |

> **用語:** ヘッダー（レスポンスの本文の前に付く「名前: 値」の行。移動先の `Location`、クッキーを渡す `Set-Cookie`、本文の形を表す `Content-Type` など。同じ名前の行が、いくつあってもよい）

> **用語:** CSS セレクター（HTML の中の要素を、`ul.note-list li a`（`note-list` という class の `ul` の中の、`li` の中の `a`）のように、場所で指定する書き方。CSS で見た目を当てるときと同じ書き方）

### まず動かす最小コード

#### 例3-1: 1つのレスポンスの、4つの部分を見る

テストを書く前に、RustNote が**本当に何を返しているか**を、全部表示して見ます。

> **▼ このコードがやること（先に日本語で）:** 登録のフォームを送り（`POST /signup`）、返ってきた状態コードと、ヘッダーを全部表示します。セッションのトークンは、先頭の6文字と長さだけにします。次に、そのクッキーでノートの一覧（`GET /notes`）を開き、状態コード・ヘッダーと、本文の長さ・`<title>`・`<h1>` を表示します。

```rust
//! 第11巻 UNIT 03: 1つのレスポンスの4つの部分（状態コード・ヘッダー・クッキー・本文）を見る。
//! 実行: cargo test --test u03_parts -- --nocapture

mod common;

use common::{body_text, encode, session_cookie, test_app};
use topcoat::router::response::Response;

const PASSWORD: &str = "correct horse battery";

/// 状態コードと、ヘッダーを全部表示する（セッションのトークンは、先頭の6文字だけ）
fn show(label: &str, response: &Response) {
    println!("--- {label}");
    println!("状態コード: {}", response.status());
    for (name, value) in response.headers() {
        let value = value.to_str().unwrap_or("（文字にできない）");
        let shown = match value.strip_prefix("__Host-session=") {
            Some(rest) => {
                let (token, attributes) = rest.split_once(';').unwrap_or((rest, ""));
                format!(
                    "__Host-session={}…（{} 文字）;{attributes}",
                    &token[..6],
                    token.len()
                )
            }
            None => value.to_string(),
        };
        println!("{name}: {shown}");
    }
}

#[tokio::test]
async fn four_parts_of_a_response() {
    let app = test_app().await;

    // 1. 登録のフォームを送る（成功すると、303 でノートの一覧へ）
    let form = format!(
        "email={}&password={}&password_confirm={}",
        encode("alice@example.com"),
        encode(PASSWORD),
        encode(PASSWORD)
    );
    let response = app.post_form("/signup", &form, None).await;
    show("POST /signup", &response);
    let cookie = session_cookie(&response).unwrap();

    // 2. ログインしたクッキーで、ノートの一覧を開く
    let response = app.get("/notes", Some(&cookie)).await;
    show("GET /notes", &response);
    let html = body_text(response).await;
    println!("本文: {} バイト", html.len());
    for tag in ["<title>", "<h1>"] {
        let start = html.find(tag).unwrap();
        let end = start + html[start..].find("</").unwrap();
        println!("本文の {tag}: {}", &html[start + tag.len()..end]);
    }
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: 状態コードと Location

- 登録に成功すると、`303 See Other` と `location: /notes` が返りました。ブラウザは、この2つを見て、`/notes` を開き直します（PRG。第10巻 UNIT 02）。本文は空です。

##### 解説2: Set-Cookie は2つ。属性まで読む

- `set-cookie:` の行が2つありました。お知らせの `flash=signed_up` と、ログインの `__Host-session` です。同じ名前のヘッダーが、2回出てきます。
- `__Host-session` の属性は、`HttpOnly`（JavaScript から読めない）・`SameSite=Lax`（ほかのサイトからの POST では送られない）・`Secure`（HTTPS だけ）・`Path=/`・`Max-Age=2592000`（2,592,000 秒＝30 日）です。`flash` は `Max-Age=300`（5 分）で、`Secure` がありません。どれも第8巻で確かめた守りなので、テストで、属性まで確かめます。
- この出力では `flash` が先ですが、**先とは限りません**（エラー2）。

##### 解説3: GET /notes のヘッダーと本文

- `content-type: text/html; charset=utf-8` は、「本文は HTML で、文字は UTF-8」という意味です。RustNote は、HTML の中にも `<meta charset="utf-8">` を書いていますが、ブラウザは、ヘッダーのほうを先に見ます。
- `vary:` は、Topcoat が付けた、「`Accept`・`accept-encoding` のヘッダーによって、返す中身が変わることがある」というキャッシュ向けの知らせです。
- 本文は 1,318 バイトで、`<title>` は `RustNote`、`<h1>` は `ノート` でした。
- 逆に、**無いヘッダー**もあります。`X-Frame-Options` のような、守りのためのヘッダーは1つもありませんでした（問2）。全部表示してみると、こうした「無いもの」にも気づけます。

### もう一歩: 実務に近い形

#### 例3-2: 確かめの道具を作り、`#[track_caller]` を付ける

例3-1で見た値を、`assert` で確かめます。「303 で、この URL へ」「このクッキーの属性は、これ」は何度も出てくるので、**道具**（小さな関数）にします。

> **▼ このコードがやること（先に日本語で）:** `assert_redirect` は、「303 で、`to` へ移動するか」を確かめます。`cookie_attributes` は、`Set-Cookie` を**全部**読んで、名前が合うものを探し、属性を並んだ順に返します。この2つの道具で、登録のレスポンス・ログインしていない人の移動先・Content-Type を確かめる、3つのテストを書きます。

```rust
//! 第11巻 UNIT 03: レスポンスを確かめる道具（ヘルパー）を作り、HTTP のテストを短く書く。
//! 道具に #[track_caller] を付けて、失敗したときに「テストのどの行か」が出るようにする。
//!
//! 実行: cargo test --test u03_helpers

mod common;

use common::{encode, location, test_app};
use topcoat::router::{StatusCode, header, response::Response};

const PASSWORD: &str = "correct horse battery";

/// 303 で `to` へ移動するレスポンスか
#[track_caller]
fn assert_redirect(response: &Response, to: &str) {
    assert_eq!(response.status(), StatusCode::SEE_OTHER, "303 のはず");
    assert_eq!(location(response), to, "移動先");
}

/// `name` のクッキーの属性（`HttpOnly`・`Path=/` など）を、並んだ順に返す。無ければ止まる
#[track_caller]
fn cookie_attributes(response: &Response, name: &str) -> Vec<String> {
    let prefix = format!("{name}=");
    let value = response
        .headers()
        .get_all(header::SET_COOKIE)
        .iter()
        .filter_map(|value| value.to_str().ok())
        .find(|value| value.starts_with(&prefix))
        .unwrap_or_else(|| panic!("{name} のクッキーがありません"));
    value
        .split(';')
        .skip(1)
        .map(|attribute| attribute.trim().to_string())
        .collect()
}

#[tokio::test]
async fn signup_sets_two_cookies_and_redirects() {
    let app = test_app().await;
    let form = format!(
        "email={}&password={}&password_confirm={}",
        encode("alice@example.com"),
        encode(PASSWORD),
        encode(PASSWORD)
    );
    let response = app.post_form("/signup", &form, None).await;

    assert_redirect(&response, "/notes");
    // セッション: JavaScript から読めず・HTTPS だけ・ほかのサイトからの POST では送られず・30 日
    assert_eq!(
        cookie_attributes(&response, "__Host-session"),
        [
            "HttpOnly",
            "SameSite=Lax",
            "Secure",
            "Path=/",
            "Max-Age=2592000"
        ]
    );
    // お知らせ: 5 分だけ
    assert_eq!(
        cookie_attributes(&response, "flash"),
        ["HttpOnly", "SameSite=Lax", "Path=/", "Max-Age=300"]
    );
}

#[tokio::test]
async fn pages_for_members_send_guests_to_login() {
    let app = test_app().await;
    for path in ["/notes", "/notes/1", "/notes/1/edit"] {
        let response = app.get(path, None).await;
        assert_redirect(&response, "/login");
    }
}

#[tokio::test]
async fn html_pages_say_utf8() {
    let app = test_app().await;
    let response = app.get("/login", None).await;
    assert_eq!(response.status(), StatusCode::OK);
    assert_eq!(
        response.headers()[header::CONTENT_TYPE],
        "text/html; charset=utf-8"
    );
}
```

```rust
const NAMES: [&str; 6] = [
```

```text
x-frame-options            無い
content-security-policy    無い
referrer-policy            無い
strict-transport-security  無い
cache-control              無い
--- GET /notes（200 OK）
x-content-type-options     無い
x-frame-options            無い
content-security-policy    無い
referrer-policy            無い
```

- 6つとも、どちらのページにもありませんでした。それぞれ、次のことを防ぐためのヘッダーです。

| ヘッダー | 無いと、起こりうること |
|---|---|
| `x-content-type-options: nosniff` | ブラウザが、`Content-Type` と違う種類のファイルだと推し量って、扱ってしまう |
| `x-frame-options`（または CSP の `frame-ancestors`） | ほかのサイトが、RustNote の画面を `iframe` の中に見えないように重ね、利用者に、知らずにボタンを押させる（クリックジャッキング） |
| `content-security-policy` | もし HTML に、ほかの人のスクリプトが紛れ込んでも（XSS）、ブラウザが止めない |
| `referrer-policy` | ほかのサイトへのリンクを押したとき、元の URL をどこまで相手に伝えるかが、ブラウザの既定まかせになる（今の多くのブラウザは、ほかのサイトにはドメインまでしか伝えないが、古いブラウザでは `/notes?q=…` の検索の言葉まで伝わる） |
| `strict-transport-security` | 利用者が `http://` で開くたびに、HTTPS へ移る前の最初のリクエストが、暗号化されないまま送られる（途中で書き換えられるおそれ） |
| `cache-control: no-store` | ログインした人だけの画面が、ブラウザのキャッシュや履歴（戻るボタン）に残ることがある |

- RustNote は、第8巻で、クッキーの `SameSite=Lax`（ほかのサイトの `iframe` の中では、ログインのクッキーが送られない）と、Topcoat のエスケープ（問3）で、いちばん大きな危険を防いでいます。それでも、何重にも守るために、これらのヘッダーを足す余地があります（改善点）。どの値にするかは、UNIT 06（準備中）の守りの回帰テストで、もう一度考えます。

```rust
    let html = body_text(app.get("/notes", Some(&alice)).await).await;
    let document = Html::parse_document(&html);
    let links: Vec<String> = document
        .select(&Selector::parse("ul.note-list li a").unwrap())
        .map(|link| link.text().collect())
        .collect();
    let bold = document
        .select(&Selector::parse("ul.note-list b").unwrap())
        .count();
    let raw_start = html.find("<li class=\"note-item\">").unwrap();
    let raw = &html[raw_start..raw_start + html[raw_start..].find("</a>").unwrap() + 4];

    println!("本文の中の形: {raw}");
    println!("リンクの文字: {links:?}");
    println!("一覧の中の b 要素: {bold} 個");
    assert_eq!(links, [title]);
    assert_eq!(bold, 0);
}
```

```text

リンクの文字: ["<b>太字</b> & \"引用\""]
```

- 本文の中では、`<` が `&lt;`、`>` が `&gt;`、`&` が `&amp;` に書き換えられていました（Topcoat のエスケープ。第6巻）。`"` は、要素の中の文字なので、そのままです。
- `scraper` で読むと、リンクの文字は、入力した題と**まったく同じ**に戻り、`b` 要素は 0 個でした。「HTML としてではなく、ただの文字として表示された」ことを、文字の並びの細かい形に頼らずに確かめられます。

### まとめ

- HTTP のテストでは、状態コード・ヘッダー（Location）・Set-Cookie（属性まで）・本文の4つを確かめる。まず全部を表示して、本当に返っているもの（と、返っていないもの）を見る。RustNote は、守りのヘッダーを返していない。
- 確かめの道具には `#[track_caller]` を付ける。付けると、失敗の場所が、道具の中ではなく、テストの呼んだ行になる。本文を読む `body_text` はレスポンスを受け取るので、状態コードは先に取っておく（E0382）。
- 同じ名前のヘッダーは `get_all` で全部読み、名前で探す。`Set-Cookie` の順番は決まっていない（cookie 0.18.2 の `HashSet`）ので、1つ目を読むテストは、ときどきだけ失敗する。本文は CSS セレクターで要素を決めて確かめる。`contains` は、検索の欄に戻した入力にも当たって、空の一覧でも通ってしまう。

## UNIT 04: property test・fuzz・入力の読み取り

### この単元のゴール

- 「どんな入力でも成り立つ決まり」（property）を関数で書き、proptest に、でたらめな入力を何百個も作らせて確かめられる
- 失敗した入力を、proptest が小さく縮める（shrink）様子と、失敗の種が `.proptest-regressions` に保存される仕組みを説明できる
- でたらめな入力を HTTP の入口に送り、RustNote の本物のバグ（NUL で始まる題で 500）を見つけ、原因（SQLite の `length()`）まで追える
- cargo-fuzz（WSL の nightly）で、コードの中を見ながら入力を変えていく fuzz を動かし、proptest が見逃した入力を見つける様子を確かめられる
- でたらめな試しは「見つけないこともある」ことを、実際の回数で説明できる

### たとえ話でつかむ

新しい自動販売機の、出荷前の試験を考えます。

- **チェック表の試験（UNIT 01）:** 人が「10 円玉だけ」「お札とおつりの境目」など、間違えやすい所を考えて、表のとおりに試します。考えた所は確実に試せますが、考えなかった所は試しません。
- **でたらめに押すロボット（property test）:** 「どう押しても、入れたお金より多いおつりは出ない」という**決まり**を1つ決め、ロボットに、でたらめなボタンとお金で何百回も試させます。壊れたら、ロボットは「何をしたら壊れたか」を記録し、余分な操作を1つずつ取り除いて、**いちばん短い手順**にしてくれます（shrink）。
- **機械の中を見ながら押すロボット（fuzz）:** 機械の中のどの部品が動いたかを見ながら、「今まで動かなかった部品が動いた押し方」を少しずつ変えて、何百万回も試します。
- どちらのロボットも、**運しだい**の所があります。今日の試験で見つからなかった不具合が、明日見つかることもあります。

| 自動販売機の試験 | RustNote のテスト |
|---|---|
| チェック表の試験 | UNIT 01 の表の形のテスト（人が選んだ端の値） |
| 決まり | property（「合格・不合格が、決まりと同じ」など） |
| でたらめに押すロボット | proptest（入力の作り方 = strategy を決めて、でたらめに作る） |
| 手順を短くする | shrink（失敗した入力を、小さく縮める） |
| 機械の中を見ながら押すロボット | cargo-fuzz（libFuzzer。通ったコードの道筋を見て、入力を変える） |
| 運しだい | 見つかる回と、見つからない回がある（例4-3） |

> **用語:** property test（プロパティテスト：「どんな入力でも、この決まりが成り立つ」を、道具が作るたくさんの入力で確かめるテスト）

> **▼ このコードがやること（先に日本語で）:** 決まり「前後の空白を除いた文字数が 1〜80 なら合格」を、`rule` という関数で書きます。1つ目のテストは、proptest がどんな文字列を作るのかを、5つだけ表示します（種を決めた `TestRunner::deterministic()` なので、毎回同じものが出ます）。2つ目は「`NoteTitle::parse` の合格・不合格が、`rule` と同じ」、3つ目は「合格した題を、もう一度 `parse` しても同じ題になる」を、それぞれ 256 個のでたらめな文字列で確かめます。

```rust
//! 第11巻 UNIT 04: NoteTitle::parse の決まりを、でたらめな文字列で、たくさん確かめる（property test）。
//!
//! 実行: cargo test --test u04_title_prop -- --nocapture

use proptest::prelude::*;
use proptest::strategy::ValueTree;
use proptest::test_runner::TestRunner;
use rustnote::domain::NoteTitle;

/// 決まり: 前後の空白を除いた文字数が 1〜80 なら合格
fn rule(input: &str) -> bool {
    (1..=80).contains(&input.trim().chars().count())
}

// 1. proptest が作る入力を、少しだけのぞいてみる（種を決めた TestRunner なので、毎回同じ）
#[test]
fn look_at_inputs() {
    let mut runner = TestRunner::deterministic();
    let strategy = "\\PC{0,100}";
    for _ in 0..5 {
        let input = strategy.new_tree(&mut runner).unwrap().current();
        println!(
            "{} 文字: {:?}…",
            input.chars().count(),
            input.chars().take(12).collect::<String>()
        );
    }
}

proptest! {
    // 2. どんな文字列でも、合格・不合格が、決まりと同じになる
    #[test]
    fn parse_follows_the_rule(input in "\\PC{0,100}") {
        prop_assert_eq!(NoteTitle::parse(&input).is_ok(), rule(&input));
    }

    // 3. 合格した題を、もう一度 parse しても、同じ題になる
    #[test]
    fn parse_twice_is_the_same(input in any::<String>()) {
        if let Ok(title) = NoteTitle::parse(&input) {
            prop_assert_eq!(NoteTitle::parse(title.as_str()), Ok(title));
        }
    }
}
```

#### ▼ コードを1つずつ分解して解説

##### 解説1: 「答え」ではなく「決まり」を書く

- UNIT 01 の表は、「`"あ".repeat(80)` → 合格」のように、入力ごとに**答え**を書きました。property test では、入力が何かは分からないので、「合格・不合格は `rule` と同じ」のように、**どんな入力でも成り立つ決まり**を書きます。
- 決まりの書き方には、よく使う形があります。「別の方法で求めた答えと同じ」（`rule` と比べる）・「2回やっても同じ」（3つ目のテスト）・「元に戻せる」・「やってはいけないことが起きない」（パニックしない・500 にならない。例4-3）です。

##### 解説2: 入力の作り方（strategy）

- `"\\PC{0,100}"` は、「制御文字などの目に見えない文字（Unicode の分類 `C`）以外の文字を、0〜100 個」という正規表現です。Rust の文字列の中で `\` を書くので、`\\` と2つ重ねます（エラー1）。
- 表示した5つのように、proptest は、いろいろな国の文字・絵文字・記号を混ぜた文字列を作ります。人がチェック表に書かない文字です。
- `proptest!` の中の `#[test]` は、何も指定しなければ、1つのテストにつき **256 個**の入力を試します。

##### 解説3: 失敗の種を保存する場所

- 出力から省いた `FileFailurePersistence … failed to find lib.rs or main.rs` は、「失敗したときに、その入力の種（seed）を保存するファイルの場所を、`src/lib.rs` の隣で探したが、見つからなかった」という知らせです。`tests/` の中のテストでは、テストのファイルの隣（`tests/u04_title_prop.proptest-regressions`）に保存されます（例4-2）。失敗しなければ、ファイルは作られません。

#### 例4-2: 失敗した入力を、小さく縮める（shrink）

UNIT 01 の「わざと間違えた版」を、property test で確かめます。

> **▼ このコードがやること（先に日本語で）:** 間違えた版を2つ用意します。`forgot_trim` は前後の空白を除き忘れた版、`counted_bytes` は文字数ではなくバイト数（`len()`）で数えた版です。それぞれが `rule` と同じになるかを、例4-1と同じ作り方の文字列で確かめます。

```rust
//! 第11巻 UNIT 04: わざと間違えた parse を、property test で確かめる。
//! 失敗した入力を、proptest が「もっと小さい入力」に縮めていく（shrink）様子を見る。
//!
//! 実行: cargo test --test u04_shrink -- --test-threads=1

use proptest::prelude::*;

/// 決まり: 前後の空白を除いた文字数が 1〜80 なら合格
fn rule(input: &str) -> bool {
    (1..=80).contains(&input.trim().chars().count())
}

/// わざと間違えた版1: 前後の空白を除き忘れた
fn forgot_trim(input: &str) -> bool {
    (1..=80).contains(&input.chars().count())
}

/// わざと間違えた版2: 文字数ではなく、バイト数で数えた
fn counted_bytes(input: &str) -> bool {
    (1..=80).contains(&input.trim().len())
}

proptest! {
    #[test]
    fn a_forgot_trim(input in "\\PC{0,100}") {
        prop_assert_eq!(forgot_trim(&input), rule(&input));
    }

    #[test]
    fn b_counted_bytes(input in "\\PC{0,100}") {
        prop_assert_eq!(counted_bytes(&input), rule(&input));
    }
}
```

#### 例4-3: でたらめな入力を、HTTP の入口に送る

今度は、関数1つではなく、RustNote の**入口**（検索・ページ番号・作成のフォーム）に、でたらめな入力を送ります。決まりは「どんな入力でも、500 にならない」です。500 は「サーバーの故障」で、利用者の入力のまちがいなら、400 で返すのが約束です。

> **▼ このコードがやること（先に日本語で）:** alice を1人だけ登録し、300 回、次の2つを送ります。①`GET /notes?q=…&page=…`（検索の言葉は、でたらめなバイトを `%XX` の形にしたもの。ページ番号は、大きな数・負の数・数字でない文字）。②`POST /notes`（題と本文も、でたらめなバイト）。①は 200 か 400、②は 303 か 400 だけが返ることを確かめ、返った状態コードの回数を数えて表示します。proptest の `TestRunner` を自分で動かし、`tokio` の `Runtime` の `block_on` で、非同期の処理を待ちます。

```rust
//! 第11巻 UNIT 04: でたらめな入力を、HTTP の入口（検索・ページ番号・作成のフォーム）に送り、
//! どんな入力でも 500 にならず、決めた状態コードだけが返ることを確かめる。
//!
//! 実行: cargo test --test u04_http_prop -- --nocapture

mod common;

use std::cell::RefCell;
use std::collections::BTreeMap;

use common::test_app;
use proptest::prelude::*;
use proptest::test_runner::{Config, TestRunner};

/// バイトの並びを、全部 %XX の形にする（UTF-8 として正しくないバイトも送れる）
fn percent_all(bytes: &[u8]) -> String {
    bytes.iter().map(|byte| format!("%{byte:02X}")).collect()
}

/// ページ番号として送る文字列: 大きな数・負の数・数字でないもの
fn page_text() -> impl Strategy<Value = String> {
    prop_oneof![
        any::<u64>().prop_map(|n| n.to_string()),
        any::<i32>().prop_map(|n| n.to_string()),
        "[-+0-9a-z.]{0,8}",
    ]
}

#[test]
fn random_inputs_never_give_500() {
    let runtime = tokio::runtime::Runtime::new().unwrap();
    let app = runtime.block_on(test_app());
    let alice = runtime.block_on(app.sign_up("alice@example.com", "correct horse battery"));
    let mut runner = TestRunner::new(Config::with_cases(300));
    // run に渡す関数は Fn（外の変数を書き換えられない）なので、RefCell に入れて数える
    let seen = RefCell::new(BTreeMap::new());

    let strategy = (
        proptest::collection::vec(any::<u8>(), 0..40),
        page_text(),
        proptest::collection::vec(any::<u8>(), 0..40),
        proptest::collection::vec(any::<u8>(), 0..40),
    );
    let result = runner.run(&strategy, |(q, page, title, body)| {
        runtime.block_on(async {
            // 一覧の検索とページ送り
            let uri = format!("/notes?q={}&page={page}", percent_all(&q));
            let status = app.get(&uri, Some(&alice)).await.status();
            *seen
                .borrow_mut()
                .entry(format!("GET /notes → {status}"))
                .or_insert(0) += 1;
            prop_assert!(
                status.as_u16() == 200 || status.as_u16() == 400,
                "{uri} → {status}"
            );

            // 作成のフォーム
            let form = format!("title={}&body={}", percent_all(&title), percent_all(&body));
            let status = app.post_form("/notes", &form, Some(&alice)).await.status();
            *seen
                .borrow_mut()
                .entry(format!("POST /notes → {status}"))
                .or_insert(0) += 1;
            prop_assert!(
                status.as_u16() == 303 || status.as_u16() == 400,
                "{form} → {status}"
            );
            Ok(())
        })
    });
    for (what, count) in seen.borrow().iter() {
        println!("{what}: {count} 回");
    }
    result.unwrap();
}
```

#### エラー3（通ってしまう）: 前後の空白を除き忘れた版を、見つけられなかった

例4-2の `forgot_trim` は、間違えた版なのに、256 回の試しを**通りました**。

- **なぜか:** `forgot_trim` が `rule` と違う答えを出すのは、「空白だけの文字列」か、「前後に空白があって、ちょうど 80 文字の境目をまたぐ文字列」のときだけです。`"\\PC{0,100}"` は、いろいろな国の文字を、まんべんなく作るので、空白だけの文字列は、ほとんど作られません。
- **直し方:** 間違いが出やすい形に、作り方を**寄せます**。空白（半角・全角・タブ）と `a` だけで、0〜85 文字の文字列を作ります（`tests/u04_spaces.rs`）。

```rust
//! 第11巻 UNIT 04: 入力の作り方を、間違いが出やすい形に寄せる。
//! 空白（半角・全角・タブ）と「a」だけで、0〜85 文字の文字列を作る。
//!
//! 実行: cargo test --test u04_spaces

use proptest::prelude::*;

/// 決まり: 前後の空白を除いた文字数が 1〜80 なら合格
fn rule(input: &str) -> bool {
    (1..=80).contains(&input.trim().chars().count())
}

/// わざと間違えた版: 前後の空白を除き忘れた
fn forgot_trim(input: &str) -> bool {
    (1..=80).contains(&input.chars().count())
}

proptest! {
    #[test]
    fn forgot_trim_with_spaces(input in "[ \t\u{3000}a]{0,85}") {
        prop_assert_eq!(forgot_trim(&input), rule(&input));
    }
}
```

### RustNote ではここで使う

- **見つかったバグ:** 題が NUL で始まるノートを作ると 500 になります（例4-3）。利用者は、ふつうのブラウザの入力欄からは NUL を入れにくいですが、フォームを自分で作れば、だれでも送れます。教材の `Rust/rustnote` のコードは変えていません。直すなら、例4-3の差分のように、`NoteTitle::parse` で制御文字を断ります（本文の `NoteBody` には CHECK が無いので、NUL が入っても 500 にはなりません）。
- **型が守っていない約束:** `NoteQuery` の項目は `pub` なので、`page = 0` で作るとパニックします（例4-4）。項目を `pub` でなくし、`NoteQuery::new` だけで作れるようにすると、型が約束を守れます（改善点）。
- **読めないバイト:** UTF-8 として読めないバイトは、断られずに `�` に置き換えて受け取られます。断りたいときは、`parse` で `\u{FFFD}` を断る方法があります（今は受け付けています）。
- RustNote の `tests/` には、property test も fuzz もありません。この単元のテストは、練習用のコピーにだけ足しました（`Cargo.toml` の `proptest` も同じ）。

### 練習問題

**問1:** `Email::parse` について、「合格したアドレスを、もう一度 `parse` しても同じ」と「合格したアドレスには、空白も大文字も無く、`@` はちょうど1つ」を、property test で確かめてください。でたらめな文字列では、ほとんど合格しないので、「メールアドレスらしい形」の作り方を考えてください。

**問2:** 例4-3の、直した版の結果では、`GET /notes → 400` が 227 回、`200` が 73 回でした。検索の言葉は、どんなバイトでも 200 になります。では、400 は、どの入力から来たのでしょうか。`page_text()` の作り方から考えてください。

**問3:** 例4-4の `query_offset` を、URL から作るときと同じ `NoteQuery::new(None, page)`（`page` は `Option<u32>`）で作る版にして、30 秒動かすと、どうなるでしょうか。

### 解答と解説

**問1の解答:**

```rust
//! 第11巻 UNIT 04 問1: Email::parse の決まりを、property test で確かめる。
//! 実行: cargo test --test u04_q1 -- --nocapture

use proptest::prelude::*;
use rustnote::domain::Email;

/// メールアドレスらしい形（大文字・空白・全角も混ぜる）
fn email_like() -> impl Strategy<Value = String> {
    "[ ]{0,2}[a-zA-Z0-9.Ａ_]{0,10}@[a-zA-Z0-9.Ｂ-]{0,10}[ ]{0,2}"
}

proptest! {
    // 合格したアドレスを、もう一度 parse しても同じ
    #[test]
    fn parse_twice_is_the_same(input in email_like()) {
        if let Ok(email) = Email::parse(&input) {
            prop_assert_eq!(Email::parse(email.as_str()), Ok(email));
        }
    }

    // 合格したアドレスには、空白も大文字も無く、@ はちょうど1つ
    #[test]
    fn accepted_addresses_are_tidy(input in email_like()) {
        if let Ok(email) = Email::parse(&input) {
            let text = email.as_str();
            prop_assert!(!text.contains(char::is_whitespace));
            prop_assert_eq!(text, text.to_lowercase());
            prop_assert_eq!(text.matches('@').count(), 1);
        }
    }
}

// どのくらいの割合が合格するかも見ておく（合格が少なすぎると、上の確かめが空回りする）
#[test]
fn how_many_are_accepted() {
    use proptest::strategy::ValueTree;
    use proptest::test_runner::TestRunner;
    let mut runner = TestRunner::deterministic();
    let strategy = email_like();
    let mut accepted = 0;
    for _ in 0..1000 {
        let input = strategy.new_tree(&mut runner).unwrap().current();
        if Email::parse(&input).is_ok() {
            accepted += 1;
        }
    }
    println!("1000 個のうち、合格は {accepted} 個");
}
```


- 2つの property は、どちらも 256 回で通りました。`how_many_are_accepted` のとおり、この作り方では 1000 個のうち 179 個が合格します。合格する入力が少なすぎると、`if let Ok(…)` の中の確かめが、ほとんど動かずに「通って」しまうので、割合も見ておきます。
- 作り方には、前後の空白・大文字・全角の文字（`Ａ`・`Ｂ`）・`.` や `-` を混ぜました。`parse` が、空白を除いて小文字にそろえることを、確かめるためです。

**問2の解答:**

- `page_text()` は、3つの作り方から1つを、同じくらいの割合で選びます。①`any::<u64>()` の数: ほとんどが `u32` の上限（約 42 億）より大きいので、`?page=` を `u32` として読めず 400。②`any::<i32>()` の数: 半分くらいが負の数なので 400。③`"[-+0-9a-z.]{0,8}"`: 数字だけになることは少なく、多くは 400。
- 全部を合わせると、だいたい 4 分の 3 くらいが 400 になり、300 回中 227 回と合います。ページ番号のまちがいは、500 ではなく 400 になる、ということも、同時に確かめられました。

### まとめ

- property test は、「どんな入力でも成り立つ決まり」を書き、proptest に、でたらめな入力を何百個も作らせて確かめる。失敗すると、入力を小さく縮め、`proptest!` なら種を `.proptest-regressions` に保存する。決まりは「別の方法と同じ」「2回やっても同じ」「500 にならない・パニックしない」などの形で書く。
- でたらめな入力を HTTP の入口に送ると、題が NUL で始まると 500 になる、本物のバグが見つかった。Rust は NUL も1文字と数え、SQLite の `length()` は NUL より前だけを数えるので、DB の CHECK で断られる。ただし、見つかったのは 10 回中 3 回。見つかった入力は、ふつうのテストとして残す。
- cargo-fuzz（WSL の nightly）は、コードの中を見ながら、1 分で 100 万回以上試す。`NoteQuery { page: 0 }` のパニックを、proptest の 256 回が見逃したのに、すぐに見つけた。property test は作り方の外を試さないので、間違いが出やすい形に作り方を寄せ、UNIT 01 の表も残す。

## UNIT 05: E2E・ブラウザ・アクセシビリティ

### この単元のゴール

- Playwright で、本物の Chrome を動かし、RustNote の**いちばん大事な流れ**（登録 → ノートを作る → 一覧 → ログアウト）を、1本のテストで確かめられる
- テストの前に、RustNote のサーバーを**新しい DB**で起動する設定（`webServer`）を書ける
- 入力欄を、画面に書かれた名前（ラベル・ボタンの文字）で探す理由を、アクセシビリティと結び付けて説明できる
- UNIT 01 で「HTML の決まり」として書いた `maxlength` の数え方（UTF-16）を、本物のブラウザで確かめられる
- axe で画面を自動で調べ、見つかった指摘（`landmark-unique`）を読んで直せる

### たとえ話でつかむ

新しいお店の、開店前の日を考えます。

- これまでの単元は、**部品ごとの点検**でした。レジ（ユニットテスト）・倉庫（リポジトリ）・注文の窓口（HTTP のテスト）を、1つずつ確かめました。
- 開店前の日には、店員が**お客さんの役**をして、入口から入り、品物を選び、会計をして、出口から出るまでを、**通しで**歩いてみます。部品が全部正しくても、「入口のドアが重くて開かない」ことは、通して歩かないと分かりません。これが **E2E**（端から端まで）のテストです。
- 全部の品物で通し歩きをすると、日が暮れます。だから、**いちばん大事な道すじ**だけを歩きます。
- 歩きながら、**目の不自由な人・車いすの人**にも使えるかを見ます。棚の名札は読み上げられるか、段差は無いか。これが**アクセシビリティ**の点検です。点検表（axe）を使うと、見落としにくくなります。

#### ▼ コードを1つずつ分解して解説

##### 解説1: サーバーごと、毎回まっさらに

- `[WebServer]` の行は、Playwright が起動した RustNote が書いた行です。3つのマイグレーションを当てているので、DB が**新しいファイル**だと分かります。前の実行で登録した alice は残っていません（UNIT 02 のエラー2と同じ考え方）。
- 出力からは省きましたが、`[WebServer]` には、アクセスログも出ていました。その中に、次の2行がありました。

```text
[WebServer] GET /_topcoat/assets/style-e9b983efabcfc6c3.css -> 200 OK (814.9µs)
[WebServer] GET /favicon.ico -> 404 Not Found (311.7µs)
```

- ブラウザは、CSS（`/_topcoat/assets/…`）のほかに、頼まれなくても `/favicon.ico`（タブに出す小さな絵）を取りに来ます。RustNote には無いので 404 です。HTTP のテスト（UNIT 03）では見えない、ブラウザならではの動きです。

##### 解説2: 画面に書かれた名前で探す

- `getByLabel("メールアドレス")` は、`<label for="email">メールアドレス</label>` が付いた入力欄を探します。`getByRole("button", { name: "登録する" })` は、「登録する」という名前のボタンを探します。
- この探し方は、**画面の読み上げ**が使うのと同じ名前で探します。ラベルが付いていない入力欄は、テストでも探しにくく、読み上げでも、何を入れる欄なのかが読まれません。テストが書きやすい画面は、アクセシビリティも良い画面です。
- `class` や `id` で探す（`page.locator("#email")`）こともできますが、見た目の都合で `class` を変えると、テストが壊れます。利用者に見えている名前で探すほうが、壊れにくくなります。

##### 解説3: `expect` は、待ってくれる

- `await expect(page).toHaveURL("/notes")` は、URL が `/notes` に**なるまで**、少し待ってくれます（既定で 5 秒まで）。ボタンを押してから、次の画面が出るまでの時間を、自分で `sleep` で待つ必要はありません。
- `toHaveText`・`toBeVisible` も同じです。待たずに1回だけ確かめる書き方だと、速いパソコンでは通り、遅い CI では落ちる、「ときどき失敗するテスト」になります。

#### 例5-2: 題の入力欄に、ブラウザでは何文字まで入るか

UNIT 01 では、「HTML の決まりでは、入力欄の `maxlength` は UTF-16 の単位で数える」と書き、本物のブラウザで確かめるのは、この単元に回しました。RustNote の題の入力欄は `maxlength="80"` です。

> **▼ このコードがやること（先に日本語で）:** 登録して「新しいノートを書く」を開いたあと、題の入力欄に、半角の `a`・ひらがなの `あ`・絵文字の `😀` を、それぞれ 100 個、キーボードで1文字ずつ打ちます（`pressSequentially`）。入った文字数と、UTF-16 の数（JavaScript の `length`）を表示し、そのまま作成して、詳細の画面の題が同じかを確かめます。最後に、`fill`（まとめて入れる）でも試します。

```ts
// 第11巻 UNIT 05 例5-2: 題の入力欄（maxlength="80"）に、ブラウザでは何文字まで入るか。
// UNIT 01 で「HTML の決まりでは、maxlength は UTF-16 の単位で数える」と書いたことを、本物の Chrome で確かめる。
import { expect, test } from "@playwright/test";

test.beforeEach(async ({ page }) => {
  // 登録して、一覧の「新しいノートを書く」を開く
  await page.goto("/signup");
  await page.getByLabel("メールアドレス").fill(`user${Date.now()}@example.com`);
  await page.getByLabel("パスワード（8文字以上）").fill("correct horse battery");
  await page.getByLabel("パスワード（確認）").fill("correct horse battery");
  await page.getByRole("button", { name: "登録する" }).click();
  await page.getByText("新しいノートを書く").click();
});

for (const [name, one] of [
  ["半角の a", "a"],
  ["ひらがなの あ", "あ"],
  ["絵文字の 😀", "😀"],
]) {
  test(`${name} を 100 個打つ`, async ({ page }) => {
    const title = page.getByLabel("タイトル（80文字まで）");
    // キーボードで1文字ずつ打つ（人が打つのと同じ）
    await title.pressSequentially(one.repeat(100));
    const value = await title.inputValue();
    console.log(
      `${name}: 入った文字数 ${[...value].length}・UTF-16 の数 ${value.length}`,
    );

    // そのまま作成すると、サーバーはどう受け取るか
    await page.getByRole("button", { name: "作成する" }).click();
    await expect(page.getByRole("heading", { level: 1 })).toHaveText(value);
    console.log(`${name}: 作成した → ${page.url().replace(/^.*(\/notes\/\d+)$/, "$1")}`);
  });
}

test("fill で入れると、maxlength はどうなるか", async ({ page }) => {
  const title = page.getByLabel("タイトル（80文字まで）");
  await title.fill("a".repeat(100));
  const value = await title.inputValue();
  console.log(`fill: 入った文字数 ${value.length}`);
});
```

#### 例5-3: axe で、アクセシビリティを自動で調べる

axe（アックス）は、画面を調べて、「ラベルの無い入力欄」「色の差が小さすぎる文字」「名前の無いボタン」など、決まった点検の項目を、自動で確かめる道具です。`@axe-core/playwright` で、Playwright のテストの中から動かせます。

> **▼ このコードがやること（先に日本語で）:** 登録してノートを1つ作り、一覧・詳細・編集の画面と、ログアウトしたあとのログインの画面を、axe で調べます。違反（守れていない点検の項目）と合格の数を表示し、違反があれば、どの要素か（`target`）と、直し方の要約を表示します。

```ts
// 第11巻 UNIT 05 例5-3: axe（アクセシビリティの自動の検査）で、RustNote の画面を調べる。
import AxeBuilder from "@axe-core/playwright";
import { test } from "@playwright/test";

test("4つの画面を axe で調べる", async ({ page }) => {
  // 登録して、ノートを1つ作る（一覧と詳細に、中身がある状態にする）
  await page.goto("/signup");
  await page.getByLabel("メールアドレス").fill(`a11y${Date.now()}@example.com`);
  await page.getByLabel("パスワード（8文字以上）").fill("correct horse battery");
  await page.getByLabel("パスワード（確認）").fill("correct horse battery");
  await page.getByRole("button", { name: "登録する" }).click();
  await page.getByText("新しいノートを書く").click();
  await page.getByLabel("タイトル（80文字まで）").fill("牛乳を買う");
  await page.getByRole("button", { name: "作成する" }).click();
  const detail = new URL(page.url()).pathname;

  for (const path of ["/notes", detail, `${detail}/edit`]) {
    await page.goto(path);
    await report(page, path);
  }
  // ログアウトして、ログインの画面も調べる
  await page.getByRole("button", { name: "ログアウト" }).click();
  await report(page, "/login");
});

async function report(page: import("@playwright/test").Page, path: string) {
  const results = await new AxeBuilder({ page }).analyze();
  console.log(`--- ${path}: 違反 ${results.violations.length} 種類・合格 ${results.passes.length} 種類`);
  for (const violation of results.violations) {
    console.log(`${violation.id}（${violation.impact}）: ${violation.nodes.length} か所`);
    for (const node of violation.nodes) {
      console.log(`  ${node.target.join(" ")}: ${node.failureSummary?.split("\n")[1]?.trim()}`);
    }
  }
}
```

### よくあるエラーと読み方

#### エラー1: ラベルの一部だけで探して、2つ見つかった（strict mode violation）

```ts
// 第11巻 UNIT 05 エラー1: ラベルの一部だけで、入力欄を探した。
import { test } from "@playwright/test";

test("パスワードを入れる", async ({ page }) => {
  await page.goto("/signup");
  await page.getByLabel("パスワード").fill("correct horse battery");
});
```

```text
  ✘  1 tests\e05_strict.spec.ts:4:5 › パスワードを入れる (294ms)
    Error: locator.fill: Error: strict mode violation: getByLabel('パスワード') resolved to 2 elements:
        1) <input required="" id="password" name="password" type="password" autocomplete="new-password"/> aka getByRole('textbox', { name: 'パスワード（8文字以上）' })
        2) <input required="" type="password" id="password_confirm" name="password_confirm" autocomplete="new-password"/> aka getByRole('textbox', { name: 'パスワード（確認）' })
    Call log:
      - waiting for getByLabel('パスワード')
    Error Context: test-results\e05_strict-パスワードを入れる\error-context.md
```

- **何が起きたか:** `getByLabel("パスワード")` は、ラベルに「パスワード」を**含む**入力欄を探すので、登録の画面の「パスワード（8文字以上）」と「パスワード（確認）」の**2つ**が見つかりました。Playwright は、どちらに入れるか決められないので、止まります（strict mode：1つに決まらないときは止まる）。
- **読み方:** `1)`・`2)` の行に、見つかった要素と、それぞれを1つに決める書き方（`aka getByRole('textbox', { name: 'パスワード（8文字以上）' })`）が出ています。
- **直し方:** ラベルを全部書きます（例5-1のように `getByLabel("パスワード（8文字以上）")`）。「ちょうど同じ」にしたいときは、`getByLabel("パスワード", { exact: true })` と書きます。

- **何が起きたか:** ログインの画面のラベルは「メールアドレス」なので、「Eメール」の入力欄は、いつまでも見つかりません。Playwright は、要素が出てくるのを**待ち続け**、テストの時間の上限（ここでは `test.setTimeout(5_000)` の 5 秒。既定は 30 秒）で止まりました。
- **読み方:** `Call log` の `waiting for getByLabel('Eメール')` が、「何を待っていたか」です。時間切れのエラーは、たいてい「探し方が画面と合っていない」か、「前の操作で、思った画面に来ていない」かのどちらかです。`Error Context` のファイル（`test-results/…/error-context.md`）には、止まったときの画面の中身が書かれているので、それを見ます。

#### エラー3: CSS の束が無い実行ファイルで、サーバーを起動した

`topcoat asset bundle` をせずに、実行ファイルだけを別のフォルダに置いた場合です（`RUSTNOTE_EXE` を、そのフォルダの実行ファイルにしました）。

### RustNote ではここで使う

- RustNote には、まだ E2E のテストがありません。この単元の `e2e` フォルダは、練習用に作りました。足すなら、例5-1の1本（大事な流れ）から始め、HTTP のテストで確かめられることは、HTTP のテストに残します。
- **改善点（この単元で見つかったこと）:** 一覧の画面の2つの `nav` に名前が無い（例5-3・問1）。題の入力欄の `maxlength="80"` は、絵文字だと 40 個で止まり、サーバーの決まり（80 文字）と合っていない（例5-2）。`/favicon.ico` が無く、ブラウザが毎回 404 をもらう（解説1。害は無い）。
- RustNote の画面は、入力欄に `<label for>` が付いているので、`getByLabel` で探せました。検索の欄だけは、ラベルが無く、`placeholder`（「キーワードで検索」）だけです。axe はこれを違反にしませんでしたが、`placeholder` は入力を始めると消えるので、ラベルを付けるほうが親切です。

```ts
// 第11巻 UNIT 05 問2: 入力欄を通らずに、絵文字 80 個の題を、フォームの形で直接送る。
import { expect, test } from "@playwright/test";

test("絵文字 80 個の題を、直接送る", async ({ page }) => {
  await page.goto("/signup");
  await page.getByLabel("メールアドレス").fill(`q2${Date.now()}@example.com`);
  await page.getByLabel("パスワード（8文字以上）").fill("correct horse battery");
  await page.getByLabel("パスワード（確認）").fill("correct horse battery");
  await page.getByRole("button", { name: "登録する" }).click();

  // page.request は、このページと同じクッキーで、HTTP のリクエストを直接送る
  const title = "😀".repeat(80);
  const response = await page.request.post("/notes", {
    form: { title, body: "" },
    maxRedirects: 0,
  });
  console.log(`状態コード: ${response.status()}・移動先: ${response.headers()["location"]}`);
  await page.goto(response.headers()["location"]);
  const shown = await page.getByRole("heading", { level: 1 }).textContent();
  console.log(`詳細の題: ${[...(shown ?? "")].length} 文字（UTF-16 で ${shown?.length}）`);
  expect([...(shown ?? "")].length).toBe(80);

```

```text
状態コード: 303・移動先: /notes/1
詳細の題: 80 文字（UTF-16 で 160）
  ✓  1 tests\q2_direct.spec.ts:4:5 › 絵文字 80 個の題を、直接送る (928ms)
```

- サーバーは `303`（作成）で受け付け、詳細の画面の題は 80 文字（UTF-16 では 160）でした。サーバーの決まりは「80 **文字**」で、ブラウザの `maxlength` は「80 **UTF-16 の単位**」なので、食い違っています。
- `maxlength` は、利用者の打ちまちがいを防ぐための**手助け**で、守りではありません。入力欄を通らない送り方は、いつでもできます。だから、決まりは、必ずサーバーの `parse` で確かめます（第9巻 UNIT 03）。そのうえで、ブラウザの手助けは、サーバーの決まりと**同じ数え方**にそろえるのが理想です（たとえば、`maxlength` をやめて、JavaScript で `[...value].length` を数えて知らせる、など）。

**問3の解答:**

```ts
// 第11巻 UNIT 05 問3: 一覧の画面で Tab を押していき、フォーカスが移る順番を記録する。
import { test } from "@playwright/test";

test("Tab の順番", async ({ page }) => {
  await page.goto("/signup");
  await page.getByLabel("メールアドレス").fill(`q3${Date.now()}@example.com`);
  await page.getByLabel("パスワード（8文字以上）").fill("correct horse battery");
  await page.getByLabel("パスワード（確認）").fill("correct horse battery");
  await page.getByRole("button", { name: "登録する" }).click();
  await page.getByText("新しいノートを書く").click();
  await page.getByLabel("タイトル（80文字まで）").fill("牛乳を買う");
  await page.getByRole("button", { name: "作成する" }).click();
  await page.goto("/notes");

  for (let i = 1; i <= 8; i++) {
    await page.keyboard.press("Tab");
    // 今フォーカスがある要素を、タグの名前と、見えている文字（無ければ name か placeholder）で表す
    const focused = await page.evaluate(() => {
      const el = document.activeElement as HTMLElement | null;
      if (!el || el === document.body) return "（ページ全体）";
      const text = (el.innerText || el.getAttribute("placeholder") || el.getAttribute("name") || "").trim();
      return `${el.tagName.toLowerCase()}「${text.split("\n")[0]}」`;
    });
    console.log(`Tab ${i} 回目: ${focused}`);
  }
});
```

```text
Tab 1 回目: a「RustNote」
Tab 2 回目: a「ノート一覧」
Tab 3 回目: button「ログアウト」
Tab 4 回目: input「キーワードで検索」
Tab 5 回目: button「検索」
Tab 6 回目: summary「新しいノートを書く」
Tab 7 回目: a「牛乳を買う」
Tab 8 回目: （ページ全体）
```

- 上の帯（アプリ名 → ノート一覧 → ログアウト）→ 検索の欄 → 検索のボタン → 「新しいノートを書く」→ ノートのリンク、と、画面の上から下へ、HTML に書いた順に移りました。8 回目は、押せる物が終わって、ページ全体（ブラウザのアドレス欄の側）へ戻りました。
- 「新しいノートを書く」（`summary`）にも、Tab で止まれます。閉じた `details` の中の入力欄には、止まりません（開くまで、見えないため）。第10巻 UNIT 10 で、人の手で確かめた順番と同じです。この順番をテストに残しておくと、HTML の並びを変えたときに、気づけます。

### まとめ

- E2E は、Playwright で本物の Chrome を動かし、いちばん大事な流れだけを1本で確かめる。`webServer` で、テストのたびに RustNote を新しい DB で起動し、`/health` が答えてから始める。入力欄は、ラベルやボタンの名前（`getByLabel`・`getByRole`）で探し、`expect` に待たせる。
- 本物の Chrome の `maxlength="80"` は UTF-16 で数え、絵文字は 40 個で止まった。サーバーは 80 文字まで受け付けるので、ブラウザのほうが厳しい。`maxlength` は手助けで、守りはサーバーの `parse` がする。
- axe は、一覧の画面の2つの `nav` に名前が無い（`landmark-unique`）ことを見つけ、`aria-label` で 0 になった。ラベルの一部だけで探すと strict mode で止まり、画面に無いラベルで探すと時間切れになる。CSS の束が無いと、サーバーが起動できない。

| E2E | 利用者と同じ入口（ブラウザ）から、サーバー・DB まで本物でつないで確かめるテスト |

| `webServer` | Playwright の設定。テストの前にサーバーを起動し、URL が答えるまで待つ |
| `getByLabel`・`getByRole` | ラベルや、ボタン・リンクの名前で要素を探す、Playwright の探し方 |
| strict mode | 探した要素が1つに決まらないときに止まる、Playwright の決まり |
| アクセシビリティ（a11y） | 障害のある人や、キーボード・読み上げを使う人も、同じように使えること |
| ランドマーク | `header`・`nav`・`main` など、画面の大きな区切り。同じ種類が2つあるときは名前を付ける |
| axe | 画面のアクセシビリティを、決まった点検の項目で自動に調べる道具 |
