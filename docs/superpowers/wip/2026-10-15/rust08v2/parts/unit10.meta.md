title: 守りのテスト・監査・事故の対応
---checklist
- ☐ この巻の守りを1本のテストにまとめ、守りを1つ外すと、その守りの名前で止まることを確かめられる
- ☐ 今の RustNote のアクセスログに残ることと、残らないこと（誰が・どこから・Origin の検査の 403）を言える
- ☐ 監査の記録に書くこと（いつ・どこから・誰が・何をして・どうなったか）と、書かないこと（パスワード・トークン）を説明できる
- ☐ 漏れた token_hash と password_hash では入れないことと、DELETE FROM sessions で全員のセッションを終わらせられることを、テストで確かめられる
- ☐ 事故の対応の順番（気づく・止める・調べる・知らせる・直す・振り返る）と、止めるのを先にする理由を言える
---glossary
| 回帰テスト | 一度作った守りや直した間違いが、あとの変更で元に戻っていないかを、毎回確かめるテスト |
| 監査の記録（監査ログ） | ログインの成功・失敗・ログアウトなど、守りに関わる出来事を、あとから調べられるように残す記録 |
| 事故の対応（インシデント対応） | 気づく・止める・調べる・知らせる・直す・振り返るまでの、事故のときの動き |
| `client_ip` | リクエストを送ってきた相手のアドレスを返す Topcoat の関数。プロキシの後ろでは `TrustedProxies` の設定が要る |
| `RemoteAddr` | 接続してきた相手のアドレス。Topcoat のサーバーがリクエストに付ける（テストでは自分で付ける） |
| 伏せる（マスク） | 記録に残す値の一部を隠すこと（`alice@example.com` → `a…@example.com`） |
| `DELETE FROM sessions` | sessions 表の行を全部消し、全員のセッションをサーバーの側で一度に終わらせる SQL |
