## この巻のまとめ

この巻の UNIT 01〜10 で、次のことができるようになったかを確かめましょう。できたものに印を付けてください。

**UNIT 01: 認証・セッション・認可と脅威モデル**

- ☐ 認証（誰か）・セッション（同じ人か）・認可（してよいか）の違いを、コンサート会場のたとえで説明できる
- ☐ RustNote で、ログインしていないと 303 でログイン画面へ、他人のノートは 404 になることを、テストで確かめられる
- ☐ クッキーに入るトークン（46 文字）と、DB に保存されるハッシュ（32 バイト）の違いと、ハッシュだけを保存する理由を説明できる
- ☐ `__Host-` の名前と、`HttpOnly`・`Secure`・`SameSite=Lax`・`Max-Age` の意味を言える
- ☐ ほかのサイトからの POST が、Topcoat の Origin の検査で 403 になり、何も保存されないことを確かめられる。ヘッダーが無いリクエストが通る理由も言える
- ☐ 持ち主を渡さずにノートを探すと、`E0308`・`E0061` でコンパイルが止まる理由と、SQL に持ち主の条件を書き忘れると IDOR になることを説明できる
- ☐ 守るもの・攻める人・入口・信頼の境目を書き出した脅威モデルの表を作り、守りが無い所（ログインの回数の制限）も書ける

**UNIT 02: パスワード・Argon2id・salt**

- ☐ パスワードを暗号化ではなくハッシュにして保存する理由と、salt の役目を、ミキサーと隠し味のたとえで説明できる
- ☐ PHC 文字列 `$argon2id$v=19$m=19456,t=2,p=1$…` の5つの部分（方式・版・重さの設定・salt・ハッシュ）を読める
- ☐ 同じパスワードでもハッシュが毎回違うのに、照合は成功する理由を言える
- ☐ 速いハッシュと Argon2id の速さ（1秒に約 1110 万回と 49 回）の違いから、わざと重いハッシュを使う理由を説明できる
- ☐ argon2 0.5 の書き方を写したときの `E0432`・`E0061` を読み、版を確かめてから写すことを言える
- ☐ 保存したハッシュが壊れているとログインが 500 になる理由と、ダミーのハッシュで失敗の時間をそろえる仕組み（と、最初の1回だけ遅い抜け）を説明できる

**UNIT 03: 登録・メールのそろえ方・重複**

- ☐ 新規登録が、入力を全部検査（400）→ ハッシュ → INSERT（UNIQUE なら 409）→ そのままログイン（303）の順で動くことを確かめられる
- ☐ メールアドレスを前後の空白を取って小文字にそろえる理由と、保存と検索の両方でそろえる必要を説明できる
- ☐ 同時に2つの登録が届いても UNIQUE が1行にすることと、「先に探してから入れる」形では2行できる理由を言える
- ☐ `Email` 型で、検査していない文字列を `create` に渡せないこと（E0308）を説明できる
- ☐ 登録の 409 が「登録済みかどうか」を伝えてしまうことと、その代わりの作り方を言える
- ☐ 全角の英字のメールが別の人になる（改善点）ことと、パスワードを trim しない理由を説明できる

**UNIT 04: ログイン・同じ文で断る・回数の制限**

- ☐ ログインが、そろえる → 探す → 照合 → 前のセッションを消して新しいトークン → 303、の順で動くことを確かめられる
- ☐ 3つの失敗（形が違う・登録が無い・パスワードが違う）が、文・画面・状態コード・時間まで同じであることを、テストで確かめられる
- ☐ 文を言い分けたり、ダミーのハッシュを外したりすると、アカウントの列挙ができる理由を説明できる
- ☐ ログインのたびにトークンを新しくすると、セッションの固定を防げる理由を言える
- ☐ 回数の制限を、メールごと・送り元ごとの鍵で設計し、パスワードスプレーと本人の締め出しへの得意・不得意を言える
- ☐ `async fn` を呼んで `.await` を忘れたときの `E0277` を読める

**UNIT 05: Topcoat のセッションの一生**

- ☐ セッションの一生（start → 毎回の照合 → stop）を、クッキーと sessions 表の両方で追いかけられる
- ☐ Topcoat の受け持ち（トークンを作って運び、ハッシュを渡す）と、RustNote の受け持ち（記録・照合・期限・取り消し・掃除）を分けて言える
- ☐ ログアウトで DB の記録を消さないと、写し取られたクッキーが使い続けられることを説明できる
- ☐ 照合で期限を見る理由と、期限切れの行がログインのときの `delete_expired` で消えることを言える
- ☐ サーバーの側で行を消して、全部の端末のセッションを終わらせられることを確かめられる
- ☐ 期限を延ばすときの `session::refresh` と、DB の `expires_at` の更新を組にする作り方を説明できる

**UNIT 06: クッキー・CSRF・Origin・SameSite**

- ☐ OriginPolicy の判断の順番（見るだけのメソッド → 信じる送り元 → Sec-Fetch-Site → Origin と Host → どちらも無い）を、表で確かめて説明できる
- ☐ 本物のブラウザで、HttpOnly のクッキーが document.cookie に出ないことと、SameSite=Lax のクッキーが、ほかのサイトからの fetch と POST には付かず、リンクの GET には付くことを確かめられる
- ☐ CSRF の守りが SameSite と OriginPolicy の2つの層で、OriginPolicy を外すと同じサイトの別の名前からの POST が通る理由を言える
- ☐ ほかのサービスからの POST を `trust_origins` で信じるときの、値の書き方（最後に / を付けない）を説明できる
- ☐ 状態を変える操作を、ログアウトも含めて全部 POST にする理由を言える

**UNIT 07: 認可・IDOR・持ち主の境目**

- ☐ ノートの5つの入口の全部で、他人には 404、ログインしていない人には 303 で、データが変わらないことを、表のテストで確かめられる
- ☐ 認可の守りの3か所（ログイン・ID の形・持ち主の条件付きの SQL）と、リポジトリの関数が owner を受け取る理由を説明できる
- ☐ 1つの SQL だけ持ち主の条件を外したとき、表のテストのマス1つとして見えることを言える
- ☐ `AND` と `OR` のかっこを忘れると、他人の本文にだけある言葉で漏れる理由を説明できる
- ☐ 連番の ID から他人のノートの数が分かることと、ランダムな ID が持ち主の条件の代わりにならない理由を言える

**UNIT 08: Better Auth との比較と、おすすめの構成**

- ☐ Better Auth を本物の Node.js で動かし、RustNote と同じ順番（登録・重複・失敗・回数の制限・Origin・DB・ログアウト）で確かめられる
- ☐ 同じ所（失敗の文と時間・SameSite=Lax・Origin・ログアウトで行を消す）と、違う所（DB のトークン・署名付きのクッキー・scrypt・期限・回数の制限）を説明できる
- ☐ DB が漏れたときの守りが、トークンのハッシュを入れる RustNote と、トークンを入れて署名する Better Auth で、どう違うかを言える
- ☐ secret の設定忘れ・開発のときの回数の制限・送り元の IP が分からないとき、の3つの設定の間違いを説明できる
- ☐ Rust のアプリで、自分で作る・Better Auth・外の認証サービスのどれを選ぶかを、理由とともに言える

**UNIT 09: OIDC・外の認証サービス・MFA・回復**

- ☐ OIDC の Authorization Code フローと PKCE の流れを説明でき、code_challenge を作って RFC 7636 の例と一致することを確かめられる
- ☐ state と nonce の役目と、state を確かめないとログインの CSRF が起きる理由を言える
- ☐ TOTP を自分で計算して RFC 6238 の例と一致することを確かめ、時計のずれと同じ数字の使い回しの扱いを説明できる
- ☐ パスワードの再設定のトークンを、ハッシュで保存・1 時間・1 回だけで作れる
- ☐ 外の認証サービスの利用者を、メールではなく iss と sub で結び付ける理由を言える

**UNIT 10: 守りのテスト・監査・事故の対応**

- ☐ この巻の守りを1本のテストにまとめ、守りを1つ外すと、その守りの名前で止まることを確かめられる
- ☐ 今の RustNote のアクセスログに残ることと、残らないこと（誰が・どこから・Origin の検査の 403）を言える
- ☐ 監査の記録に書くこと（いつ・どこから・誰が・何をして・どうなったか）と、書かないこと（パスワード・トークン）を説明できる
- ☐ 漏れた token_hash と password_hash では入れないことと、DELETE FROM sessions で全員のセッションを終わらせられることを、テストで確かめられる
- ☐ 事故の対応の順番（気づく・止める・調べる・知らせる・直す・振り返る）と、止めるのを先にする理由を言える
