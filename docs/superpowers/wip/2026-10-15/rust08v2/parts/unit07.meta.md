title: 認可・IDOR・持ち主の境目
---checklist
- ☐ ノートの5つの入口の全部で、他人には 404、ログインしていない人には 303 で、データが変わらないことを、表のテストで確かめられる
- ☐ 認可の守りの3か所（ログイン・ID の形・持ち主の条件付きの SQL）と、リポジトリの関数が owner を受け取る理由を説明できる
- ☐ 1つの SQL だけ持ち主の条件を外したとき、表のテストのマス1つとして見えることを言える
- ☐ `AND` と `OR` のかっこを忘れると、他人の本文にだけある言葉で漏れる理由を説明できる
- ☐ 連番の ID から他人のノートの数が分かることと、ランダムな ID が持ち主の条件の代わりにならない理由を言える
---glossary
| 認可 | ログインした人が、その操作をしてよいかを決めること |
| IDOR | URL などの ID を書き換えるだけで、他人のデータに届いてしまう弱さ |
| 横の権限・縦の権限 | 他人のデータに届く問題（横）と、管理者の操作に届く問題（縦） |
| 表のテスト | 入口と利用者の組み合わせを表にして、全部を1回で確かめるテスト |
| `owner: UserId` | リポジトリの全部の関数が受け取る持ち主。渡し忘れは E0061 |
| `AND` と `OR` の結び付き | SQL では AND が先に結び付く。OR を含む条件はかっこで囲む |
| E0061 | 関数の引数の数が合わないエラー |
