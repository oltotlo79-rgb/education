1. このアプリは何をするものか（工数管理とは）

1.1 「工数（こうすう）」とは何か

用語: 工数（こうすう）とは？ 「ある作業に、どれだけの 人の時間 を使ったか」を表す数のこと。たとえば「1人が1時間かけた作業」を基準に、「この作業には3人時（にんじ）かかった」のように数えます。工場や保全（ほぜん：設備の点検・修理）の現場では、「どの作業にどれだけ人手をかけたか」を記録して、ムダを見つけたり、人員計画を立てたりするのに使います。

このアプリは、ひとことで言えば 「従業員が、その日どの作業に何時間使ったかを記録し、集計するシステム」 です。プロジェクトの説明書（CLAUDE.md）にもこう書かれています。

2.2 やり取りの流れ（4ステップ）

  1. リクエスト（request：要求） … ブラウザがサーバーに「ログインしたい。従業員番号は12345だ」とお願いします。
  2. サーバーの処理 … サーバーが「その番号は登録されているか？」とデータベースに問い合わせます。
  3. データベースの応答 … データベースが「ある／ない」を返します。
  4. レスポンス（response：応答） … サーバーが「成功」または「エラー」をブラウザに返し、ブラウザが画面を切り替えます。

用語: リクエストとレスポンスとは？ - リクエスト … ブラウザ → サーバー へ送る「お願い」。「この情報をくれ」「このデータを保存してくれ」など。 - レスポンス … サーバー → ブラウザ へ返す「返事」。お願いの結果（成功・失敗・データ本体）が入っています。 この「お願い→返事」が、Webアプリの すべての通信の基本単位 です。本アプリでも、画面を開くたび・ボタンを押すたびに、このやり取りが何度も発生しています。

用語: HTTP（エイチティーティーピー）とは？ ブラウザとサーバーが会話するときの「言葉のルール（プロトコル：約束事）」。HyperText Transfer Protocol の略。http://localhost:8000 の http がこれです。リクエストには「メソッド」という種類があり、本アプリでは主に次の4つを使います。

用語: HTTPメソッド（GET / POST / PUT / DELETE）とは？ リクエストの「目的」を表すラベルです。レストランの注文票の種類だと思ってください。 - GET（ゲット） … 「データをください」（一覧を見る、画面を開く）。例：メニュー画面を表示。 - POST（ポスト） … 「新しいデータを送ります」（登録、ログイン）。例：ログイン情報を送る。 - PUT（プット） … 「既存のデータを書き換えます」（更新）。例：工数の修正。 - DELETE（デリート） … 「このデータを消してください」（削除）。例：工数の削除。 §7で見る main_views.py には、def post(self, request):（POSTのとき）、def get(self, request):（GETのとき）のように、メソッドごとに処理が分かれて 書かれています。

開発中、あなたのPCの中でブラウザもサーバーも動かします。そのとき出てくる住所が localhost（ローカルホスト：このPC自身）です。

  • フロントエンド（React開発サーバー）… http://localhost:3000
  • バックエンド（Django）… http://localhost:8000

用語: ポート番号とは？ :3000 や :8000 の数字。1台のPCの中で、複数のプログラムが同時に通信できるように付ける「部屋番号」のようなもの。同じPC（localhost）でも、3000番の部屋にはReact、8000番の部屋にはDjangoが住んでいる、というイメージです。なぜ番号で分けるかは、後で settings.py の CORS（コルス）設定（§12）で関係してきます。

3. フロントエンドとバックエンドの分離

3.1 なぜ画面と処理を別々に作るのか

昔ながらのWebアプリは、サーバーが「完成したHTMLページ」を毎回まるごと作ってブラウザに送っていました。本アプリは違い、フロントエンド（React）とバックエンド（Django）をきっぱり分けて います。

【昔の方式】
ブラウザ ──「ページちょうだい」──> サーバー ──> HTMLを丸ごと組み立てて返す
（ボタンを押すたびに、画面が真っ白になって、全部読み込み直し）

【本アプリの方式（フロント・バック分離）】
ブラウザ(React) ──「データだけちょうだい（JSON）」──> サーバー(Django)
              <──「はい、データです（JSON）」────────
（Reactが受け取ったデータで、画面の必要な部分だけを書き換える。画面は真っ白にならない）

用語: JSON（ジェイソン）とは？ JavaScript Object Notation の略。データを「名前: 値」のペアの集まりで表す、文字列の書き方。人間にも読みやすく、機械も解釈しやすいので、フロントとバックの間でデータをやり取りする「共通語」として使われます。たとえばログイン成功時、サーバーは次のようなJSONを返します（§7で実物を見ます）。 json {"status": "success"} 「status（状態）という名前の値が success（成功）だ」という意味です。

3.2 分離のメリット（後任者にとっての利点）

メリット 説明
担当を分けやすい 「画面の見た目」は frontend/ だけ、「処理・データ」は kosu/ だけ、と探す場所がはっきりする
画面がサクサク データだけ受け取り、必要な部分だけ書き換えるので、画面全体の再読み込みがない
役割が明快 「これは見た目の問題（フロント）か、データの問題（バック）か」で原因を切り分けやすい
再利用しやすい 同じバックエンドAPIを、別の画面やアプリからも呼べる

保守のヒント: バグが出たとき、まず「これは画面（フロント）の問題か、処理（バック）の問題か」を切り分けると、調査がぐっと速くなります。画面の見た目・文言・配置 → frontend/src/、データの中身・計算・保存 → kosu/ が出発点です。

3.3 「API」という言葉

用語: API（エーピーアイ）とは？ Application Programming Interface の略。難しそうですが、ここでは 「フロントとバックがデータをやり取りするための窓口（URL）」 くらいに考えてください。本アプリでは、/api/login/ /api/main_menu/ のように、/api/ で始まるURLが「バックエンドへの注文窓口」です。フロントは、この窓口にリクエストを送り、JSONで返事を受け取ります。

つまり本アプリの構図は、こうです。

React（frontend/） ──/api/○○/へリクエスト──> Django（kosu/） ──> PostgreSQL
（見た目・操作）         （JSONでやり取り）        （処理・判断）      （保存）

この「/api/ が窓口」という事実は、後で hozen_another/urls.py（§9）に実コードで書かれているのを確認します。

  • ② useNavigate（ユーズナビゲート）は「別の画面へ移動する」道具。ログイン成功後にメインメニューへ飛ばすのに使います。

  • await が付いているので、サーバーの返事が来るまでここで待ち、返事を response に入れます。

  • ⑪ catch (err) … 通信そのものが失敗したとき（サーバーがエラーを返した、ネットが切れた等）にここへ来ます。
  • ⑫ axios.isAxiosError(err) … そのエラーが「通信由来のものか」を判定。

class AsyncTask(models.Model):
  # 保持する最大件数
  MAX_RECORDS = 1000

  # タスクの一意なID
  task_id = models.CharField(max_length=255, unique=True)
  # 状態(pending/success/error)
  status = models.CharField(max_length=50, choices=[

    ('success', 'Success'),
    ('error', 'Error')
  ])
  # 結果
  result = models.TextField(null=True, blank=True)
  # 作成日時(自動)
  created_at = models.DateTimeField(auto_now_add=True)
  # 更新日時(自動)
  updated_at = models.DateTimeField(auto_now=True)

  # 保存時に上限を超えたら古い順に削除
  def save(self, *args, **kwargs):
    super().save(*args, **kwargs)
    current_count = self.__class__.objects.count()
    if current_count > self.MAX_RECORDS:
      excess_count = current_count - self.MAX_RECORDS
      oldest_records = self.__class__.objects.order_by('created_at')[:excess_count]
      for record in oldest_records:
        record.delete()

16. この章のまとめ

  • このアプリの目的 は工数（作業にかけた人の時間）の記録・集計。ログイン／工数／人員／班員／定義／問い合わせ／管理者の各機能があり、フォルダがそれに対応する（§1・§13）。
  • Webアプリには3者 がいる ―― ブラウザ（画面）・サーバー（処理）・データベース（保存）。リクエストとレスポンスでやり取りし、HTTPメソッド（GET/POST/PUT/DELETE）で目的を区別する（§2）。
  • 本アプリは フロント（React）とバック（Django）を分離 し、JSON でデータをやり取りする。窓口は /api/ で始まるURL（§3・§9）。
  • ログイン1本を6ファイルで端から端まで追った：Login.tsx（入力・送信）→ hozen_another/urls.py（/api/→kosu）→ kosu/urls.py（login/→Login）→ main_views.py（member 表に問い合わせ・成功/失敗判定・セッション保存）→ JSON返却 → Login.tsx（navigate("/")）→ index.tsx（/→MainMenu表示）。他の全機能も同じ骨格（§4〜§10）。
  • models.py はデータの設計図。1モデル＝1テーブル、1フィールド＝1カラム。member（人員。authority/administrator で3段階権限）・Business_Time_graph（工数）・kosu_division（定義。1レコードに最大50区分）が中核。id（pk）は自動付与（§8）。
  • 技術スタック は React / TypeScript / Django / DRF / PostgreSQL を中心とした 定番で保守しやすい組み合わせ。7基準で見ると「情報が豊富・保守しやすい・将来性が高い」のが強み（§11）。
  • settings.py はアプリの設定ダイヤル盤。秘密情報は .env から読み（漏洩防止）、INSTALLED_APPS で kosu を有効化、CORS で別ポート通信を許可、DATABASES でPostgreSQL接続、STATICFILES/TEMPLATES でReactのビルド成果物を配信（§12）。
  • フォルダ構成の地図 を持っておけば、「どこを直せばよいか」で迷わない。見た目・処理は frontend/src/、データ・計算・権限は kosu/、設定は hozen_another/（§13）。
