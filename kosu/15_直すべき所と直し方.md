>

>
> - **どこ:** ファイルと行番号（`c7ea392` の行番号）
> - **何が困るか**と、手元で確かめた結果
> - **直し方:** 直す場所ごとに、「**今**」のコードと「**直した後**」のコードを、全部。直した後のコードは、手元の写しに全部入れて、アプリのテスト（353 個）と画面のテスト（534 個）が全部通ることを確かめた物です（§10）
> - **直ったことの確かめ方**

> ⚠️ **いちばん急ぐこと:** 今の `master` は、**アプリのテストが 353 個のうち 9 個落ちる** 状態です（[T-5](#85-t-5-アプリのテストが-9-個落ちるテストだけ先に入った)）。前の版で書いたテストは全部入ったのに、そのテストが確かめる直しのうち、ダウンロード（[S-4](#54-s-4-ダウンロードの-api-が渡された場所のファイルをそのまま返して消そうとする)）・ヘルプ（[S-7](#57-s-7-ヘルプ画面の初期化-api総当たり途中の失敗パスワード未設定)）・ロード（[B-8](#68-b-8-データのロードが途中で失敗するとデータが半分だけ消える)）・401 の整理（[B-10](#610-b-10-ログイン以外の理由でも-401-を返し画面がログイン画面へ飛ぶ)）のコードが入っていないためです。**この 4 つの直しを入れれば、9 個とも通ります**（手元で確かめた）。GitHub Actions（`master` に入れると本番に出す仕組み）は、今も GitHub の画面で手動で止めてあります（2026 年 11 月 11 日に確かめた）。**[T-5](#85-t-5-アプリのテストが-9-個落ちるテストだけ先に入った) と [D-1](#71-d-1-github-actions-がテストを流さずに本番へ出す作りのまま)（Actions でテストを流す）を直すまでは、Actions を動かさないでください。**

## 1. この巻の読み方

### 1.1 印の意味

**急ぐ度**

| 印 | 意味 |
|---|---|
| 🔴 すぐ | 本番のデータが守られていない、または使えなくなる。ほかの作業より先に直す |
| 🟠 早めに | 動かない、または壊れやすい。使う人が困る |
| 🟡 余裕のある時に | 整理・改善。直さなくても、すぐには困らない |

**今の状態**（前の版＝`ec2cedc` の時の一覧と比べて）

| 書き方 | 意味 |
|---|---|
| 新しく見つかった | 前の版には無かった（今回のコードの変更で起きた物も含む） |
| 前から残っている | 前の版から、まだ直っていない |
| 一部だけ直った | 前の版の直し方の一部が入った。残りを書いている |
| 直った | もう直っている。§3 に、どう直ったかと、確かめた結果を書いた |

**どうやって分かったか**

| 印 | 意味 |
|---|---|
| ✅ 手元で再現 | `master` を手元の別のフォルダに書き出し、メモリの中だけのデータベースで動かして、本当にそうなることを確かめた（本番には一切触っていない。§10） |
| 📖 コードから | コードを読んで分かった。動かしては確かめていない |

**番号の頭の文字:** S ＝ 安全（Security）、B ＝ 不具合（Bug）、D ＝ 開発・運用の整理（Development）、T ＝ テスト（Test）。番号は前の版と同じ物を使っています（直った番号も、欠番にしないで残しています）。新しい番号は [T-5](#85-t-5-アプリのテストが-9-個落ちるテストだけ先に入った) の 1 つです。

### 1.2 「今」と「直した後」の読み方

直し方は、次の形で書いています。

- **場所:** ファイルと、`c7ea392` での行番号。たとえば「`kosu/views/asynchronous_views.py` の 592〜648 行目」。
- **今:** その行の、今のコード（コメントも含めて、ファイルのとおり）。
- **直した後:** 「今」の行を、全部これに置き換えます。
- 「この行の前に入れる」と書いてある物は、何も消さずに、その行の前に足します。
- 「新しいファイル」と書いてある物は、そのファイルを新しく作り、中身を全部入れます。

> ⚠️ **行番号は、上から直していくと、ずれます。** 1 つのファイルの中で何か所も直す時は、**下の方の場所から** 直すか、行番号ではなく「今」のコードを、エディターの検索（`Ctrl` ＋ `F`）で探して置き換えてください。

> ⚠️ **本番のホスト名（住所）は、この資料には書いていません。** コードの中で `<本番のホスト名>` と書いた所は、今のファイルに書いてある名前を、そのまま使ってください。

### 1.3 この巻で使う言葉

| 言葉 | 意味 |
|---|---|
| API（エーピーアイ） | 画面（React）がサーバー（Django）に「データをちょうだい」「これを保存して」と頼む窓口。`/api/member_new/` のような URL の 1 つ 1 つ（07 巻） |
| ログインの確かめ（認証） | 「今、だれがログインしているか」を確かめること。このアプリでは、ログインすると **セッション**（サーバーが覚えておく、その人用のメモ）に従業員番号（`login_No`）が入り、`kosu/permissions.py` の `LoginNoAuthentication` がそれを読む |
| 権限の確かめ（認可） | 「その人に、その操作をしてよいか」を確かめること。人員の表の「権限（`authority`）」と「管理者（`administrator`）」の 2 つのスイッチを、`permissions.py` の `HasAuthority`・`IsAdministrator` が確かめる |
| CSRF（シーサーフ） | ログインしたままの人が、別の（悪い）サイトを開いた時に、そのサイトが裏でこのアプリへ「消して」などを送らせる攻撃。防ぐには、このアプリの画面だけが知っている合言葉（**CSRF トークン**）を、書き込みの時に一緒に送らせて確かめる |
| CORS（コルス） | 別のサイトの JavaScript が、このアプリの API の返事を読んでよいかを、サーバーが答える仕組み |
| Cookie（クッキー） | ブラウザがサイトごとに覚えておく小さなデータ。ログインのセッションの番号（`sessionid`）も、CSRF トークン（`csrftoken`）もここに入る |
| ステータスコード | API の返事に付く 3 けたの番号。200 ＝ 成功、400 ＝ 送った物がおかしい、401 ＝ ログインしていない、403 ＝ してはいけない、404 ＝ 見つからない、409 ＝ ほかのデータとぶつかる、429 ＝ 呼びすぎ、500 ＝ サーバーの中でエラー（09 巻） |
| トランザクション | 何件もの書き込みを「全部する」か「全部しない」かにまとめる仕組み。途中で失敗したら、それまでの書き込みも取り消す（08 巻） |
| マイグレーション | データベースの表の形の変更を書いたファイル（`kosu/migrations/`）。`migrate` で本物のデータベースに当てる（08 巻） |

```python
@api_view(['GET'])  # GET のみ受け付ける DRF のAPIにする
@permission_classes([IsAdministrator])  # 管理者のみ利用可能
def download_file(request):  
    # ダウンロード対象のファイルパスをクエリパラメータから取得する
    file_path = request.GET.get('file_path')  
    # ファイルをバイナリの読み込み専用モード（'rb'）で開く（パスの妥当性チェックは行わずにそのまま開く）
    file_handle = open(file_path, 'rb')  
    # ファイルをダウンロードさせるレスポンスを作成する
    #   as_attachment=True: ブラウザで表示せず、ファイルとして保存させる
    #   filename          : 保存時のファイル名（パスからファイル名の部分だけを取り出す）
    response = FileResponse(  
        file_handle,  
        as_attachment=True,  
        filename=os.path.basename(file_path),  
    )  
    # ダウンロード後にサーバー上のファイルを削除する（下の cleanup_on_close から別スレッドで呼ばれる）。
    #
    # 引数:
    #   なし（外側の file_path を使う）
    # 戻り値:
    #   なし
    def delayed_file_cleanup():  
        # ファイルがまだ送信中・使用中の可能性があるため、3秒待ってから削除する
        time.sleep(3)  
        # ファイルが存在する場合だけ削除する
        if os.path.exists(file_path):  
            try:  
                os.remove(file_path)  
            # 削除に失敗してもダウンロード自体には影響しないため、標準出力にログを出すだけにする
            except Exception as e:  
                print(  
                    f'Cleanup failed after delay for '  
                    f'{file_path}: {e}'  
                )  
    # レスポンスの送信が終わったとき（close() 呼び出し時）に実行する処理。
    #
    # 3秒の待機中にサーバーの処理を止めないよう、削除処理を別スレッドで開始する。
    #
    # 引数:
    #   なし
    # 戻り値:
    #   なし
    def cleanup_on_close():  
        # ファイル削除処理を別スレッドで実行する準備
        thread = threading.Thread(  
            target=delayed_file_cleanup,  
        )  
        # デーモンスレッドにする（サーバー終了時にスレッドが残り続けないようにする）
        thread.daemon = True  
        # ファイル削除処理を開始する
        thread.start()  
    # レスポンスの close() を上の cleanup_on_close に差し替える
    #   Django はレスポンスの送信完了後に close() を呼ぶため、そのタイミングで削除処理が始まる
    #   ※差し替えにより、元の close() の処理（開いたファイルを閉じる等）は実行されない
    response.close = cleanup_on_close  
    # ファイルのダウンロードレスポンスを返す
    return response  
```

```python
@api_view(['GET'])  # GET のみ受け付ける DRF のAPIにする
@permission_classes([IsAdministrator])  # 管理者のみ利用可能
def download_file(request):
    # バックアップの保存先（media フォルダ）の絶対パス
    backup_dir = Path(settings.MEDIA_ROOT).resolve()
    # 受け取るのはファイル名だけにする（フォルダの部分は捨てる。例: "../../.env" → ".env"）
    file_name = os.path.basename(request.GET.get('file_path') or '')
    file_path = (backup_dir / file_name).resolve()
    # 名前が空・media フォルダの直下でない・ファイルが無い場合は 404（ほかの場所のファイルは決して開かない）
    if not file_name or file_path.parent != backup_dir or not file_path.is_file():
        return JsonResponse(
            {
                'status': 'error',
                'message': 'ファイルが見つかりません。',
            },
            status=status.HTTP_404_NOT_FOUND,
        )
    # ファイルをダウンロードさせるレスポンスを作成する
    #   as_attachment=True: ブラウザで表示せず、ファイルとして保存させる
    response = FileResponse(
        open(file_path, 'rb'),
        as_attachment=True,
        filename=file_name,
    )
    # 送り終わった時（Django が close() を呼ぶ時）に、まず元の close()（開いたファイルを閉じる）を呼び、
    # そのあとファイルを消す（閉じてから消すので、Windows でも消せる。待つための別スレッドも要らない）
    original_close = response.close

    def close_then_delete():
        original_close()
        try:
            file_path.unlink()
        except OSError:
            pass  # 消せなくてもダウンロードには影響しない

    response.close = close_then_delete
    return response
```

<!-- first-use -->

> **▶ ここで初めて出てくるコード**
>
> - **`.is_file()`**（Python）: `Path` の `.is_file()` は、その場所にファイルがあれば `True` を返すメソッド。フォルダや、何も無い時は `False` です。
> - **`.unlink()`**（Python）: `Path` の `.unlink()` は、そのファイルを消すメソッド。消せない時は `OSError` になります。
> - **`original_close()`**（Python）: この巻のダウンロードの直し方で、`FileResponse` が元から持っていた `close`（開いたファイルを閉じる処理）を、変数 `original_close` に取っておいた物。先にこれを呼んでファイルを閉じてから、ファイルを消します。
> - **`OSError`**（Python）: ファイルを開く・消すなど、OS とのやり取りで起きるエラーのまとめ役。`except OSError:` で、ファイルが無い・使用中で消せない、などをまとめて受け止めます。

```python
  expected = os.environ.get('HELP_PATH', '')

  if not expected or not isinstance(password, str):
```

```python
from django.db import IntegrityError, transaction  # DBの整合性エラー / 複数の書き込みを「全部する・全部しない」にまとめる
from django.core.exceptions import ObjectDoesNotExist  # 該当するレコードが無いときの例外
import functools  # デコレーターを作る時に、元の関数の名前などを引き継ぐ



# ロード関数を「全部入れるか、何も変えないか」にするデコレーター。
#
# ロード関数の中身をデータベースのトランザクション（まとめて確定・まとめて取り消し）の中で動かし、
# 途中で失敗して {'status': 'error'} を返した時は、それまでの削除・登録を全部取り消す。
# （前は 1 行ずつ確定していたので、途中で失敗すると「古いデータは消えたのに新しいデータは半分」になった）
#
# 引数:
#   func: ロード関数（load_kosu_file など）
# 戻り値:
#   トランザクションの中で func を呼ぶ関数
def atomic_load(func):
  @functools.wraps(func)
  def wrapper(*args, **kwargs):
    with transaction.atomic():
      result = func(*args, **kwargs)
      if isinstance(result, tuple) and result and isinstance(result[0], dict) and result[0].get('status') == 'error':
        transaction.set_rollback(True)
      return result
  return wrapper
```

> **▶ ここで初めて出てくるコード**
>
> - **`.wraps()`**（Python）: `@functools.wraps(func)` は、デコレーターの中で作った関数に、元の関数（`func`）の名前や説明を引き継がせる印。付けないと、エラーの表示などで、元の関数の名前が分からなくなります。
> - **`func()`**（Python）: デコレーター `atomic_load` に渡された、元の関数（ロード関数）を呼んでいる所。`func(*args, **kwargs)` の `*args`・`**kwargs` は、「受け取った引数を、全部そのまま渡す」書き方です。
> - **`@functools`**（Python）: `@functools.wraps(func)` の頭の部分。`functools`（関数を扱う道具を集めた、Python に最初から入っている部品）の `wraps` を、デコレーターとして使うという意味です。

### 6.20 B-20 `.gitattributes` のせいで、PDF・Excel などのファイルが壊れる

🟠 早めに ／ 前から残っている ／ ✅ 手元で再現

**どこ:** `.gitattributes`（4 行）

**今:** `* text eol=crlf` で、**全部のファイルを文字のファイル（テキスト）として扱い**、行末の記号を書き換えます。`binary`（そのまま保存）にしているのは `*.png` と `*.ico` だけです。PDF・Excel・圧縮ファイル・フォントの中に、行末の記号と同じ並びのバイトがあると、コミットの時に書き換わって壊れます。

**直し方:**

① `.gitattributes` を、Git が中身を見て判定する形（`text=auto`）にし、壊れやすい種類を `binary` にします。

**場所:** `.gitattributes` の 1〜4 行目（.gitattributes 全体）

今:

```text

* text eol=crlf
*.png binary
*.ico binary
```

直した後（上の行を、全部これに置き換える）:

```text
# 行末記号: 文字のファイル（テキスト）は Git が判定し、作業フォルダでは Windows の CRLF にそろえる
#   （「* text」で全部をテキスト扱いにすると、Excel・PDF・画像・フォントなどの中身が書き換わって壊れる）
* text=auto eol=crlf
# 中身をそのまま保存するファイル（行末記号を変えない・差分を文字で出さない）
*.png binary
*.jpg binary
*.ico binary
*.gif binary
*.svg binary
*.pdf binary

*.xls binary

*.woff binary
```


### 7.6 D-6 HTTPS まわりの設定が足りない

🟡 余裕のある時に ／ 前から残っている ／ 📖 コードから

**今:** Azure App Service は、HTTPS で受けた頼みを、中のアプリへは HTTP で渡します。アプリは「HTTPS で来た」と分からないので、`request.is_secure()` が `False` になります。今は `CSRF_TRUSTED_ORIGINS` に本番の `https://…` を書いてあるので CSRF の確かめは通りますが、HTTPS を前提にした Django の守り（Referer の確かめなど）が働きません。

**直し方:** `CSRF_TRUSTED_ORIGINS` のすぐ後ろに足します。

**場所:** `hozen_another/settings.py` の 313 行目の前（CSRF_TRUSTED_ORIGINS のすぐ後ろ）

足すコード（この行の前に入れる）:

```python

# Azure App Service は、HTTPS で受けたリクエストを、中のアプリへは HTTP で渡す。
# その時に付く X-Forwarded-Proto ヘッダーを見て「本当は HTTPS だった」と分かるようにする
#   （request.is_secure() が正しくなり、CSRF の確かめも HTTPS として行われる）
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
# CSRF トークンの Cookie も、本番（DEBUG=False）では HTTPS の時だけ送る

```

HTTPS だけで使うと決めたら、ブラウザに「この住所は HTTPS だけで開く」と覚えさせる `SECURE_HSTS_SECONDS` も足せます。大きくすると、その間 http で開けなくなるので、小さい値（例: `3600` ＝ 1 時間）から始めます。

## 10. この巻で確かめたこと

### 10.1 確かめ方

- GitHub の `master`（コミット `c7ea392`）を、`git archive` で手元の別のフォルダに書き出しました（アプリのフォルダ・本番・GitHub には、何も書き込んでいない）。前の版の `ec2cedc` との違い（`git diff`）も、1 ファイルずつ読みました。
- アプリに入っているテスト用の設定（`hozen_another/test_settings.py`。データベースはメモリの中だけの SQLite）で、Django のテスト用の `Client` を使って API に頼みを送りました。「ブラウザと同じ流れ」の確かめ（[S-1](#51-s-1-ログインした後の保存削除ログアウトが全部-403-になる直った)）は、CSRF を確かめる状態（`enforce_csrf_checks=True`）で行いました。
- 前の版の直し（164 か所）を、`c7ea392` に 1 つずつ照らし合わせました。50 か所は、もう入っていました（§3）。残りの 114 か所は、`c7ea392` の同じコードの場所に、そのまま当てはまりました（「今」のコードが一字一句同じ）。この 114 か所を、全部、別の写しに入れて、同じことを確かめました。直し方のコードは、その写しに入れた物と同じです（同じ一覧から、この巻のコードの枠を作っている）。
- 画面のテストとビルドは、この PC の `frontend/node_modules` を借りて、写しの上で流しました（[D-8](#78-d-8-サポート安全の直しが終わった部品版のずれ) の版のずれに注意）。
- GitHub Actions の状態は、GitHub の API で読みました（何も変えていない）。
- **本番のサーバー・データベースには、一切触っていません。** 本番で同じことを試さないでください。

## 11. この巻のまとめ

- 前の版でいちばん急ぐと書いた **ログイン後の書き込みが全部 403 になる問題（[S-1](#51-s-1-ログインした後の保存削除ログアウトが全部-403-になる直った)）は直りました。** 他人のデータ（[S-3](#53-s-3-他人のデータを見たり変えたり消したりできる所直った)）・思っていない値の 500（[B-15](#615-b-15-思っていない値が送られると-500-になる直った)）・テスト（[T-1](#81-t-1-csrf-を確かめる状態のテストが-1-つも無い直った)〜[T-4](#84-t-4-テストが-media-に-excel-を作る直した後の動きに合わせるテストが-4-個直った)）も、前の版の直し方のとおりに直っています。
- ただし、**テストだけが先に入り、確かめる側のコードが入っていない所があるため、今の `master` はアプリのテストが 9 個落ちます**（[T-5](#85-t-5-アプリのテストが-9-個落ちるテストだけ先に入った)）。[S-4](#54-s-4-ダウンロードの-api-が渡された場所のファイルをそのまま返して消そうとする)（ダウンロード）・[S-7](#57-s-7-ヘルプ画面の初期化-api総当たり途中の失敗パスワード未設定)（ヘルプ）・[B-8](#68-b-8-データのロードが途中で失敗するとデータが半分だけ消える)（ロード）・[B-10](#610-b-10-ログイン以外の理由でも-401-を返し画面がログイン画面へ飛ぶ)（401 の整理）の直しを入れれば、全部通ります。この 4 つは、安全・データの問題でもあるので、いちばん先に直します。
- Actions は今も止めてあります。**[T-5](#85-t-5-アプリのテストが-9-個落ちるテストだけ先に入った) と [D-1](#71-d-1-github-actions-がテストを流さずに本番へ出す作りのまま)（Actions でテストを流す）を直すまで、動かさないでください。** 今の本番は 9 月 3 日の版のままです。
- リポジトリの Excel（[S-9](#59-s-9-リポジトリに残っている-excel)）は、コードより先に、公開範囲の確認と会社への連絡をします。
- どの直しも、**作業用のブランチで直し、テストを全部流し、手元で確かめてから** master に入れます。テストだけ、コードだけを先に入れないでください。
- 直したら、この巻の該当する節に「済み（日付・コミット）」と書き足しておくと、次の人が助かります。
