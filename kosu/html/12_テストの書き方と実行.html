0. 前提知識：テストとは何か、なぜ書くのか

0.1 テストとは「機械にやらせる動作確認」

テスト（test）とは？ プログラムが「期待どおりに動くか」を確かめるための、別のプログラム。テスト対象の本体コードを呼び出し、「こういう入力を与えたら、こういう結果になるはず」を機械的にチェックします。

たとえば、本アプリのログイン機能には「従業員番号 12345 を送ったらログイン成功する」という期待があります。これを手で確認するなら、毎回ブラウザを開いて、番号を打って、ボタンを押して、画面を見る……という作業が要ります。テストコードを書いておけば、コマンド1つでこの確認を一瞬で・何百回でも やってくれます。

▼ たとえ話：健康診断 テストは、人間の 健康診断 に似ています。体のあちこち（血圧・血液・視力…）を一通り測り、「基準値の範囲内か」を確認します。プログラムも同じで、機能のあちこちに「測定項目（テスト項目）」を置いておき、コマンドを流すたびに 全項目を一斉に検査 します。どこか1つでも基準を外れたら、テストは「ここが異常です」と赤字で教えてくれます。

健康診断を毎年受けるように、テストも コードを直すたびに 流します。そうすれば「気づかないうちに体（プログラム）の別の場所が悪くなっていた」を早期発見できます。

0.2 なぜ手作業ではなくテストコードなのか

確認方法 かかる時間 見落とし 何百回の繰り返し
手作業（毎回ブラウザを操作） 1機能で数分、全機能で数時間 起きやすい（人間だから） 苦痛・現実的でない
テストコード（コマンド1つ） 全部で数秒〜数十秒 起きにくい（毎回同じ手順） 何度でも一瞬

なぜ？ テストが「保守」で最も効く理由 あなたは後任者として、これからこのアプリを 直し続けます。1か所直すと、関係なさそうな別の場所が連鎖的に壊れること（これを デグレード／リグレッション＝後退バグ と呼びます）がよくあります。テストがあれば、修正後にコマンドを流すだけで「壊していないか」が即わかります。テストは「安心して直すための保険」 です。

0.3 本アプリのテストは2種類ある

種類 対象 道具 場所 実行コマンド
フロントのテスト React の画面・部品 Vitest ＋ React Testing Library frontend/src/tests/ npm run test:run
バックのテスト Django のAPI・モデル・関数 Django TestCase ＋ APIClient kosu/tests/ python manage.py test ...

この章では、両方を実物のコードで読みます。まずは「どんなテストでも共通の考え方」である 3ステップ を押さえましょう。

1. テストの3ステップ（準備→実行→検証）

ほぼすべてのテストは、次の3つの段階でできています。英語の頭文字をとって AAA（トリプルA） とも呼ばれます。

1. 準備（Arrange / アレンジ） … テストの前提を整える
                               （データを作る・にせものを用意する・画面を描く）
2. 実行（Act / アクト）        … テストしたい動作を1回だけ行う
                               （ボタンを押す・関数を呼ぶ・APIを叩く）
3. 検証（Assert / アサート）   … 結果が期待どおりかを確かめる
                               （「〜のはず」をチェックし、違えば失敗）

用語: アサーション（assertion） 「〜であるはずだ」という 主張（断言） のこと。テストの心臓です。expect(x).toBe(5)（フロント）や self.assertEqual(x, 5)（バック）のように書き、もし実際の値が主張と違えば、その場でテストは「失敗」になります。

1.1 3ステップを日本語の例で

※説明用の簡易例（本アプリのコードではありません）

【準備】 電卓アプリを開く
【実行】 「2」「＋」「3」「＝」を押す
【検証】 画面に「5」が表示されているはず → 違えば失敗

このたった3段で、1つのテストが完成します。Login.test.tsx も test_backend.py も、すべてこの形の繰り返しです。「いまどのステップを読んでいるか」を意識すると、テストコードが一気に読みやすくなります。

2. フロントのテスト道具：Vitest と React Testing Library

フロントのテストは、2つの道具を組み合わせて書きます。

Vitest（ヴィテスト）とは？ JavaScript/TypeScript 用の テスト実行ツール（テストランナー）。テストファイルを探して実行し、結果（成功/失敗）をまとめて表示してくれます。describe（グループ分け）・it（1つのテスト）・expect（検証）といった「テストを書くための言葉」を提供します。Vite（ヴィート）というビルドツールと相性がよく、速いのが特徴です。

React Testing Library（リアクト・テスティング・ライブラリ。略してRTL）とは？ React の画面を テスト用に仮想で描き、「画面に○○の文字があるか」「ボタンを押したらどうなるか」を、ユーザーの視点で 確認するためのライブラリ。内部の細かい実装ではなく「人が見て・触って分かること」を確認するのが思想です。render（描く）・screen（画面）・fireEvent（操作する）などを提供します。

なぜ「ユーザーの視点」が大事？ 「このボタンの内部関数が呼ばれたか」ではなく「ボタンを押したらエラーが画面に出たか」を確認する方が、実際の使われ方に近く、壊れに強い テストになります。内部の作りを変えても、ユーザーから見た振る舞いが同じなら、テストは通り続けるからです。

2.1 jsdom ―「ブラウザのふり」をする道具

テストはブラウザではなく コマンドライン（黒い画面） で動きます。でも React は本来ブラウザの画面（DOM）を相手にします。そこで jsdom（ジェイエスドム） という「ブラウザの画面のふりをするライブラリ」を使い、コマンドライン上に にせの画面 を用意します。これにより、ブラウザを起動しなくても画面のテストができます（設定は§6で実コードを見ます）。

3. モック（にせもの）という考え方

Login.test.tsx を読む前に、最重要キーワード モック を理解します。

モック（mock）とは？ テスト対象が依存している「外部のもの」を、にせもの（替え玉）に差し替える こと。本物の代わりに、テスト都合のいいように動く偽物を使います。「モック化する」「モックする」と言います。

3.1 なぜモックが必要か

ログイン画面 Login.tsx は、内部で次の3つに 依存 しています。

  1. API通信（api.post(...) でサーバーへ送る）
  2. 画面遷移（useNavigate() で別ページへ移動する）
  3. ロゴ画像（import logo from "../../img/TitleRogo.png"）

テストのときにこれらを本物のまま動かすと、困ったことが起きます。

依存 本物だと困ること モックにすると
API通信 テストのたびに本物のサーバーに繋ぐ必要があり、結果も毎回変わる 「成功を返す/失敗を返す」を テストが自由に決められる
画面遷移 コマンドラインには本物のブラウザ遷移がない 「遷移しようとしたか・どこへか」を 記録だけする にせ関数にできる
画像 テスト環境では画像ファイルを読み込めない 「logo.png という文字列」に置き換えてエラーを避ける

▼ たとえ話：映画の撮影 モックは、映画撮影の スタント（替え玉）や小道具 に似ています。本物の崖から飛び降りる代わりにスタントを使い、本物のお金の代わりに小道具のお札を使います。テストでも「本物だと危険・不便・不安定なもの」を、安全で都合のいいにせものに替えるのです。

3.2 Vitest でモックする道具

書き方 意味
vi.fn() にせの関数（モック関数）を作る。呼ばれた回数や引数を記録してくれる
vi.mock("モジュール名", () => ...) あるモジュール（ファイル）丸ごとを、にせものに差し替える
xxx.mockResolvedValueOnce(値) 「次の1回だけ、成功してこの値を返す」ように仕込む（API成功を演じる）
xxx.mockRejectedValueOnce(値) 「次の1回だけ、失敗してこのエラーを投げる」ように仕込む（API失敗を演じる）
vi.clearAllMocks() モックの記録（呼ばれた回数など）を 全部リセット する

これだけ頭に入れたら、いよいよ実コードを読みます。

4. 実コード全解説：Login.test.tsx 全132行

ここが本章フロント編の核心です。本アプリのログイン画面のテスト frontend/src/tests/MainPage/Login.test.tsx を、1行残らず 読みます。このファイルには「成功・失敗・401遷移・別エラー」という4つの代表テストが詰まっており、フロントのテストの型がすべて入っています。

4.1 インポート部（1〜5行目）

▼ このコードがやること（先に日本語で）: テストを書くのに必要な道具を、各ライブラリから読み込みます。Vitest の言葉（describe など）、RTL の道具（render など）、ブラウザのふりをする道具、そしてテスト対象の Login 画面本体を取り込みます。

// ① Vitestの道具を読み込む
import { vi, describe, it, expect, beforeEach } from "vitest";
// ② RTLの道具を読み込む
import { render, screen, fireEvent, waitFor } from "@testing-library/react";
// ③ テスト用のルーター（後述）
import { MemoryRouter } from "react-router-dom";
// ④ 「画面に○○がある」を確認する追加機能
import "@testing-library/jest-dom/vitest";
// ⑤ テスト対象＝ログイン画面本体
import Login from "../../MainPage/Login";

▶ ここで初めて出てくるコード

  • MemoryRouter（Vitest・Testing Library）: React Router の部品で、URL をブラウザーではなくメモリーの中で持つ物。テストの中で <MemoryRouter> で囲むと、Link や useNavigate を使う部品をそのまま試せます。

1行ずつ見ます。

  • ① import { vi, describe, it, expect, beforeEach } from "vitest"; Vitest から5つの道具を取り出します。
  • vi … モックを作る道具（§3）。
  • describe … テストを グループにまとめる 箱。
  • it … 1つのテスト を書く単位（「〜であること」と読む）。
  • expect … 検証（アサーション）を書く道具。

  • beforeEach … 各テストの 前に毎回 実行する準備処理。

  • ② import { render, screen, fireEvent, waitFor } from "@testing-library/react"; RTL から4つの道具を取り出します。

  • render … React の画面を テスト用に描く（仮想画面に表示する）。
  • screen … 描かれた 画面（仮想DOM）全体 を表すオブジェクト。ここから要素を探します。
  • fireEvent … クリックや入力など、ユーザー操作を発火 させる道具。

  • waitFor … 「ある条件が満たされるまで 待つ」道具（非同期処理の完了待ち）。

  • ③ import { MemoryRouter } from "react-router-dom"; MemoryRouter（メモリールーター）は、テスト専用の にせのルーター（経路管理）。本物のルーターはブラウザのURLを使いますが、テストにはブラウザのURLがありません。そこで「メモリ上だけで動くルーター」で Login を包みます。

なぜ？ Login.tsx の中には <Link to="/help">（リンク）や useNavigate()（遷移）が入っています。これらは「ルーターの中で使う」ことが前提なので、ルーター無しで描こうとするとエラーになります。MemoryRouter で包むことで、ルーターがある状態を再現します。

  • ④ import "@testing-library/jest-dom/vitest"; jest-dom（ジェスト・ドム）という追加機能を読み込みます。これにより toBeInTheDocument()（画面に存在するか）や toHaveTextContent()（この文字を含むか）といった、画面チェック専用の便利な検証 が使えるようになります。/vitest を付けるのは「Vitest向けに登録する」という意味です。

  • ⑤ import Login from "../../MainPage/Login"; テストの主役、ログイン画面本体を読み込みます。../../ は「2つ上のフォルダ」。テストファイルは src/tests/MainPage/ にあり、本体は src/MainPage/ にあるので、2階層上がって MainPage/Login を指します。

4.2 画像のモック（7〜8行目）

▼ このコードがやること: ロゴ画像の読み込みを、にせもの（ただの文字列 "logo.png"）に差し替えます。テスト環境では本物の画像ファイルを処理できないため、エラーを防ぐ目的です。

// モック設定
// 画像 import を文字列に置き換える
vi.mock("../../img/TitleRogo.png", () => ({ default: "logo.png" }));

▶ ここで初めて出てくるコード

  • .mock()（Vitest・Testing Library）: vi.mock("部品の場所", () => ({ … })) は、その部品を、テスト用のにせ物（モック）に取り替えます。本物のサーバーや画像を使わずに試せます。
  • vi.mock("../../img/TitleRogo.png", () => ({ default: "logo.png" })); 「Login.tsx が import logo from "../../img/TitleRogo.png" で画像を読み込もうとしたら、本物の画像の代わりに { default: "logo.png" } を渡せ」という指示です。
  • () => ({ default: "logo.png" }) … 「default という名前で "logo.png" を返す」関数。
  • import logo from "..." の logo には、この default の値（＝文字列 "logo.png"）が入ります。

なぜ default なの？ import 名前 from "..."（デフォルトインポート）で受け取る値は、モジュールの default というキーに入ります。だからモックも default で返す必要があります。画像は本来「画像ファイルへのパス（文字列）」として扱われるので、にせの文字列で十分です。

4.3 API（axios）のモック（10〜19行目）

▼ このコードがやること: API通信を担当する api/axios というモジュールを、丸ごと「にせの通信」に差し替えます。get/post/put/delete の4メソッドを、それぞれ「呼ばれたことを記録するだけのにせ関数」にします。さらに、そのにせモジュールを mockedApi という名前で取り出して、後でテストごとに「成功を返せ／失敗を返せ」と仕込めるようにします。

// api/axios モジュールを丸ごと差し替え
vi.mock("../../api/axios", () => ({
  //   default エクスポート（import api from で受け取る対象）
  default: {
    //   get を にせ関数に
    get: vi.fn(),
    //   post を にせ関数に（ログインで使う主役）
    post: vi.fn(),
    //   put を にせ関数に
    put: vi.fn(),
    //   delete を にせ関数に
    delete: vi.fn(),
  },
}));
// 差し替え後の（にせの）api を取り込む
import api from "../../api/axios";
// 型を any にして mockResolvedValueOnce 等を呼べるように
const mockedApi = api as any;

▶ ここで初めて出てくるコード

  • any（TypeScript）: 「何の型でもよい」という特別な型。型の確かめが効かなくなるので、ふだんは使わず、テストでにせ物を作る時など、どうしても必要な所だけに使います。
  • .fn()（Vitest・Testing Library）: vi.fn() は、呼ばれたかどうか・何を渡されたかを覚える、にせの関数を作ります。

1行ずつ。

  • vi.mock("../../api/axios", () => ({ default: { ... } })) 本アプリの通信モジュール api/axios（07章で見た axios の設定済みインスタンス）を、丸ごとにせものに置き換えます。default の中に4つのメソッドを用意します。

  • get: vi.fn() / post: vi.fn() / put: vi.fn() / delete: vi.fn() それぞれ vi.fn()（にせの関数）にします。にせ関数は 呼ばれた回数・引数を記録 し、後から「何を返すか」を仕込めます。ログインで実際に使うのは post（従業員番号をサーバーへ送る）です。残り3つも、Login.tsx が間接的に読み込んでもエラーにならないよう、念のため用意しています。

  • import api from "../../api/axios"; vi.mock で差し替えた にせの api を取り込みます。vi.mock は「このファイルの中で api/axios を読み込むものは全部にせものになる」効果があるので、ここで取り込む api も自動的ににせものです。

5. getBy / findBy / queryBy の使い分け

§4で getByRole getByLabelText findByRole が出てきました。RTL の要素取得には 3つの系統 があり、使い分けが超重要です。

系統 待つ？ 見つからないとき 主な用途
getBy... 待たない（即取得） すぐエラー（失敗） 「最初から画面にあるはず」の要素
findBy... 待つ（非同期） しばらく待って無ければエラー 「後から現れる」要素（API後に出るエラー等）
queryBy... 待たない null を返す（エラーにしない） 「無いはず」を確認したいとき

5.1 図で覚える

getBy   … 「今ここにある？」即チェック。無ければ即・赤エラー
findBy  … 「現れるまで待つよ」少しずつ何度も探す。時間切れで赤エラー
queryBy … 「あるか無いか教えて」無くても怒らず null を返す

5.2 本アプリでの実例での使い分け

  • screen.getByLabelText("従業員番号")（§4.7④, 4.8④…） 入力欄は 画面を描いた瞬間から存在 します。だから「待たない」getBy でOK。

  • screen.getByRole("button", { name: "ログイン" })（§4.8⑥…） ボタンも最初からあります。getBy でOK。

  • screen.findByRole("alert")（§4.9④, 4.11④） エラー表示は ログイン失敗の後にやっと現れます。最初は無いので、getBy だと「無い！」と即失敗します。findBy で「現れるまで待つ」のが正解。

使い分けの早見フレーズ 「最初からある → getBy」「後から出る → findBy」「無いことを確かめる → queryBy」。この3つを覚えれば、RTLの要素取得で迷いません。

⚠️ よくある失敗: API後に出るエラーを getByRole("alert") で取ろうとして、毎回「要素が見つからない」で落ちる。これは findByRole（待つ）に変えれば直ります。逆に、最初からある要素を findBy で取っても動きますが、無駄に待つので getBy が適切です。

7. バックのテスト道具：Django TestCase と APIClient

ここからバックエンド（Django/Python）のテストに移ります。考え方（3ステップ・モック）は同じですが、道具が変わります。

Django TestCase（テストケース）とは？ Django が用意する テスト用の土台クラス。これを継承（07章の「親クラスを引き継ぐ」）してテストを書きます。最大の特徴は、各テストの前に「まっさらなテスト用データベース」を用意し、テスト後に元に戻す こと。本物のデータを汚さず、各テストが独立して動きます。

APIClient（エーピーアイ・クライアント）とは？ Django REST Framework が用意する にせのブラウザ。self.client.get('/api/...') や self.client.post('/api/...') と書くと、サーバーを起動せずに アプリの中で直接APIを呼べます。フロントの fireEvent（操作を発火）に相当する、「APIを叩く道具」です。

10. APIの 401 / 403 / 200 を確かめるテストの考え方

test_backend.py の中核は 「APIが正しい権限チェックをするか」 のテストです。ここがバックテストの最重要ポイントなので、考え方を整理します。

10.1 3つのステータスの意味

ステータス 意味 いつ返る
200 OK 成功 ログイン済み・権限ありで、正しくデータが返るとき
401 Unauthorized 未認証 ログインしていない（セッションが無い）とき
403 Forbidden 権限不足 ログイン済みだが、その操作の権限が無い とき

401と403の違い（重要） - 401 ＝「あなたが誰か分からない」。ログインしていない状態。→ ログイン画面へ。 - 403 ＝「あなたが誰かは分かるが、これをする権限が無い」。ログイン済みの一般ユーザーが、管理者専用機能を触ったときなど。

たとえ話：401は「入館証を持たずにビルに入ろうとした」（そもそも誰か不明）。403は「入館証はあるが、社長室には入れない」（身元は分かるが権限不足）。

12. バックのテスト設定（test_settings.py）

バックのテストは、本番とは 別の設定 で動かします。hozen_another/test_settings.py（全31行）を読みます。

        #    メモリ上のDB（ファイルに残さない）

# Disable signals during tests to avoid side effects
# ③ 「今はテスト中」フラグ（副作用を抑える目印）
TESTING = True

# Disable django-q cluster requirement for tests
# ④ 非同期タスクの設定
Q_CLUSTER = {
    'name': 'test',
    #    'sync': True ＝ 非同期処理を「その場で即実行」

# Custom test runner that creates tables from models directly (bypasses migrations)

    def __contains__(self, item):

▶ ここで初めて出てくるコード

  • __contains__（Python）: def __contains__(self, item): を書いたクラスの物は、item in 物 と書けるようになります。
  • __getitem__（Python）: def __getitem__(self, item): を書いたクラスの物は、物[item] と書いて中身を取り出せるようになります。

要点を1つずつ。

  • ① from .settings import * 本番の設定（settings.py）を まるごと取り込み、その上で必要な箇所だけ上書きします。「本番とほぼ同じ環境で、テストに都合の悪い部分だけ変える」やり方。

  • ② DATABASES を sqlite3 の :memory: に上書き 本番は PostgreSQL（CLAUDE.md）ですが、テストでは SQLite のメモリDB を使います。

    なぜ？ メモリ上のDBは 超高速 で、テストが終われば 跡形もなく消える。本物のDBを汚す心配がなく、毎回まっさらから始められます。テストの「速さ」と「安全（独立性）」の両立です。

  • ③ TESTING = True 「いまテスト中」という目印。本体コードはこのフラグを見て、テスト中は不要な副作用（メール送信や外部通知など）を抑制できます。コメントの「Disable signals」が示すとおり、シグナル（モデル変更時の自動処理。CLAUDE.mdの signals.py）の暴発を防ぐためにも使われます。

  • ④ Q_CLUSTER の 'sync': True 本アプリは Django-Q で 非同期タスク（バックアップ等）を裏で動かします（CLAUDE.md）。テストでは 'sync': True にして、非同期タスクを その場で即時実行 させます。

    なぜ？ テストで「裏で後から実行される」と、結果を待てず検証できません。sync: True で「呼んだら即その場で実行」にすると、結果をすぐ検証できます。フロントの「モック」と同じ発想（テスト都合に合わせる）です。

  • ⑤⑥ DisableMigrations でマイグレーションを飛ばす 通常、DBの表はマイグレーション（06章の makemigrations/migrate）で作ります。テストでは、それを飛ばして モデル定義から直接、表を作ります。

    なぜ？ コメントにあるとおり、PostgreSQL では許される書き方（max_length 無しの文字列フィールド等）が SQLite では問題になることがあるため、マイグレーションを経由せず「モデルから直接」表を作って回避しています。これにより、メモリ上の SQLite でもテストが安定して動きます。

要するに test_settings.py は: 「本番と似た設定のまま、DBを使い捨て・処理を即時・準備を最速 に切り替えて、テストを高速・安全・独立に回すための専用設定」です。だから実行時に --settings=hozen_another.test_settings で この設定を指定 します（次の §13）。

1. 似た既存テストを見つける          … 同じ種類（表示/成功/権限…）を探す
2. それをコピーして名前を変える       … it("...") / def test_xxx の名前
3. 準備（仕込み）を目的に合わせる     … mock... / data = {...}
4. 実行を目的に合わせる              … 操作する要素・叩くURL
5. 検証を目的に合わせる              … expect / assert の期待値
6. 流して緑になるか確認              … npm run test:run / python manage.py test ...

黄金ルール: 「バグを直したら、そのバグを再現するテストを1つ足す」。これで「同じバグが二度と戻ってこない（リグレッションしない）」ことが保証されます。本アプリの test_backend.py が大量のテストを持つのは、こうして1つずつ「守るべき仕様」を積み上げてきた結果です。

18. この章のまとめ

  • テストは「機械にやらせる動作確認」。健康診断のように、コードを直すたびに流して「壊していないか」を一瞬で確かめる、保守の最後の砦。
  • どんなテストも 3ステップ（準備 Arrange → 実行 Act → 検証 Assert）。検証＝アサーション（「〜のはず」を主張し、違えば失敗）。
  • フロント は Vitest ＋ React Testing Library。Login.test.tsx 全132行を1行ずつ読み、vi.mock（画像・API・navigate のモック化）、describe/it/beforeEach、render/screen/fireEvent/waitFor、getByRole/getByLabelText/findByRole、mockResolvedValueOnce/mockRejectedValueOnce、そして 成功遷移・エラー表示・401遷移・別エラー の各テストを完全に理解した。
  • 要素取得は getBy（最初からある）/ findBy（後から出る・待つ）/ queryBy（無いことの確認） を使い分ける。
  • バック は Django TestCase ＋ APIClient。test_backend.py の土台（make_break_times・BaseTestCase・login ヘルパー）と TestModels を1行ずつ読み、assertEqual/assertIn/assertTrue/assertFalse/assertLessEqual を理解した。
  • APIテストの王道は 「未ログイン→401 / 正しい権限→200 / 権限不足→403」の3点セット。401（誰か不明）と403（権限不足）の違いが肝。作成は201・削除は204も確認する。
  • テストは 専用設定（test_settings.py：使い捨てSQLite・即時実行・マイグレーション省略）で動かす。実行は npm run test:run と python manage.py test --settings=hozen_another.test_settings。✓/OK が出れば全合格。
  • 失敗したら メッセージ（期待と実際の差）を読み、本体を直すかテストを更新するかを判断する。理解せずに消さない。
  • 新テストは似た既存テストをコピーして一部を変える。バグを直したら再発防止のテストを1つ足す。
