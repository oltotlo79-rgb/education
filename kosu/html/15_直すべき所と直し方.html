4. 安全の問題（S）

4.0 何が起きているか

このアプリの API は、Django REST framework の APIView（07 巻）で書かれています。APIView は、何も書かなければ だれからの頼みでも受け付けます。そこで、今は API ごとに、最初の数行で「ログインしているか」「権限があるか」を自分で確かめています。

# 今の書き方（例: kosu/views/member_views.py 15〜34 行目の MemberList。短くまとめ、説明のコメントを足した物）
login_no = request.session.get('login_No')       # セッションから、ログイン中の人の従業員番号を出す
if not login_no:                                  # 無ければ「ログインしていない」
  return Response({'status': 'error', 'message': 'ログイン情報が確認できません。'}, status=status.HTTP_401_UNAUTHORIZED)
member_data = member.objects.get(employee_no=login_no)
if not member_data.authority:                     # 「権限」が無ければ断る
  return Response({'status': 'error', 'message': 'アクセス権限がありません。'}, status=status.HTTP_403_FORBIDDEN)

この書き方だと、書き忘れた API は、だれでも使えます。実際に、画面を表示するための get には書いてあるのに、保存・削除の post・put・delete に書き忘れている API がたくさんあります（S-2）。画面はボタンを出さないので気付きにくいのですが、API は画面を通さなくても呼べます。

さらに、Django REST framework は、このアプリのような「セッションに番号を入れるだけ」のログインの時には、CSRF の確かめをしません（S-5）。

図1: 「ログインしているか・権限があるか」を確かめる場所。今は API ごとに自分で確かめていて、書き忘れた API（赤）は、だれでも使える。直した後は、全部の API の手前に共通の確かめを 1 つ置き、要らない所（ログイン画面など）だけ外す

直し方の方針は、図の右側です。「全部の API の手前で、まず確かめる」部品を 1 つ作り、最初から全部の API にかけて、要らない所（ログイン画面など）だけ外します（S-1）。こうすると、新しい API を足した時に書き忘れても、安全な側（ログインが要る）になります。

"""ログイン中の人と、その人の権限を確かめる部品（全部の API で共通に使う）。

settings.py の REST_FRAMEWORK で「最初から全部の API にかける」設定にするので、
ログインが要らない API（ログイン・ログアウト・ヘルプ）だけ AllowAny を付けて外す。
"""
from rest_framework import exceptions
from rest_framework.authentication import BaseAuthentication, CSRFCheck
from rest_framework.permissions import BasePermission

from .models import member


class LoginNoAuthentication(BaseAuthentication):
  """セッションの login_No から、ログイン中の人（member）を探す。"""

  def authenticate(self, request):
    login_no = request._request.session.get('login_No')
    if not login_no:
      return None                      # ログインしていない → request.user は None
    login_member = member.objects.filter(employee_no=login_no).first()
    if login_member is None:
      return None                      # 人員から消された人 → ログインしていない扱い
    self.enforce_csrf(request)         # ログイン中の人の書き込みは、CSRF トークンも確かめる
    return (login_member, None)

  def enforce_csrf(self, request):
    # DRF の SessionAuthentication.enforce_csrf と同じ確かめ方
    def dummy_get_response(request):
      return None
    check = CSRFCheck(dummy_get_response)
    check.process_request(request)
    reason = check.process_view(request, None, (), {})
    if reason:
      raise exceptions.PermissionDenied(f'CSRF Failed: {reason}')

  def authenticate_header(self, request):
    # これを返すと、ログインしていない時に 403 ではなく 401 になる（画面はログイン画面へ戻る）
    return 'Session'


class IsLoggedIn(BasePermission):
  """ログインしていること。"""
  def has_permission(self, request, view):
    return isinstance(request.user, member)


class HasAuthority(IsLoggedIn):
  """ログインしていて、「権限」が付いていること（人員・班員の画面）。"""
  def has_permission(self, request, view):
    return super().has_permission(request, view) and bool(request.user.authority)


class IsAdministrator(IsLoggedIn):
  """ログインしていて、「管理者権限」が付いていること（管理者・定義の編集の画面）。"""
  def has_permission(self, request, view):
    return super().has_permission(request, view) and bool(request.user.administrator)

▶ ここで初めて出てくるコード

  • .process_view()（Django）: Django のミドルウェアの、画面（ビュー）を動かす直前に動くメソッド。CSRFCheck では、送られてきた合言葉が合っているかを確かめ、合わなければ理由の文を返します。
  • .PermissionDenied()（Django REST framework）: exceptions.PermissionDenied('…') は、「してはいけない」というエラーを起こす物。Django REST framework が受け止めて、403 の返事にします。
  • bool()（Python）: 値を True・False にする関数。空の文字列や None は False、中身があれば True です。
  • BaseAuthentication（Django REST framework）: 「この頼みは、だれからか」を調べる部品の土台。これを受け継いで authenticate を書き、だれか分かったら (その人, None)、分からなければ None を返します。
  • CSRFCheck（Django REST framework）: Django の CSRF の確かめ（CsrfViewMiddleware）を、Django REST framework の中から使うための部品。rest_framework.authentication から読み込みます。
  • BasePermission（Django REST framework）: 「この人に、この API を使わせてよいか」を決める部品の土台。これを受け継いで has_permission を書き、よければ True を返します。False なら 401 か 403 になります。
  • .user（Django）: Django の request.user は、今ログインしている人（していなければ「だれでもない人」）です。request.user.is_authenticated で、ログインしているかが分かります。

import os
from pathlib import Path
from django.conf import settings
from django.http import JsonResponse, FileResponse
from rest_framework import status
from rest_framework.decorators import api_view, permission_classes
from ..permissions import IsAdministrator


@api_view(['GET'])
@permission_classes([IsAdministrator])
def download_file(request):
  backup_dir = Path(settings.MEDIA_ROOT).resolve()               # バックアップの置き場所
  file_name = os.path.basename(request.GET.get('file_name', ''))  # 名前だけにする（../ や C:/… を捨てる）
  file_path = (backup_dir / file_name).resolve()
  if not file_name or file_path.parent != backup_dir or not file_path.is_file():
    return JsonResponse({'status': 'error', 'message': 'ファイルが見つかりません。'}, status=status.HTTP_404_NOT_FOUND)

  response = FileResponse(open(file_path, 'rb'), as_attachment=True, filename=file_name)
  original_close = response.close
  def close_then_delete():          # 送り終わったら、先にファイルを閉じてから消す
    original_close()
    try:
      file_path.unlink()
    except OSError:
      pass
  response.close = close_then_delete
  return response

  • .unlink()（Python）: Path の .unlink() は、そのファイルを消すメソッド。消せない時は OSError になります。
  • original_close()（Python）: この巻のダウンロードの直し方で、FileResponse が元から持っていた close（開いたファイルを閉じる処理）を、変数 original_close に取っておいた物。先にこれを呼んでファイルを閉じてから、ファイルを消します。

10. この巻のまとめ

  • いちばん大きな問題は、API ごとに確かめを書いていて、書き忘れが多い ことです。共通の確かめを 1 つ作って全部の API にかける（S-1）と、今ある漏れが一度にふさがり、これから API を足す時も安全な側になります。
  • 今すぐ 直すのは、ダウンロード（S-4）、共通の確かめ（S-1・S-2）、CORS・Cookie・CSRF（S-5）です。リポジトリの Excel（S-9）は、コードより先に、公開範囲の確認と会社への連絡をします。
  • 不具合（B）は、使う人が困っている物（B-1〜B-6・B-10）から直します。
  • どれも、作業用のブランチで直し、テストを流し、手元で確かめてから master に入れます。master に入れた物は、そのまま本番に出ます。
  • 直したら、この巻の該当する行に「済み（日付・コミット）」と書き足しておくと、次の人が助かります。
